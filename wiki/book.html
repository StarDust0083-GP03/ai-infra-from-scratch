读前说明：不懂 CUDA 也能开始

AI Infra 看起来像一堵缩写墙：GPU、HBM、CUDA、NCCL、TP、FSDP、KV Cache、MIG、RDMA、SLO。它们并不是二十个互不相干的知识点，而是同一条链上不同位置的问题。

这本书从两个普通问题开始：

  1. 一个用户发出提示词后，数据经过哪些系统才变成下一个 token？
  2. 一次训练 step 中，哪些字节留在显存，哪些字节在 GPU 之间移动？

能回答这两个问题，就已经有了 AI Infra 的骨架。

你不需要先会什么#

不要求会写 CUDA kernel，不要求有多卡机器，也不要求先学完整 Kubernetes。书中只在真正需要时引入概念：

  • 解释显存时，再讲 tensor 形状和数据类型；
  • 解释推理吞吐时，再讲 prefill、decode 与 KV cache；
  • 解释多卡时，再讲 collective 和网络拓扑；
  • 解释集群时，再讲 Device Plugin、scheduler 和 operator。

每章都先回答“它解决什么问题”，再看公式和源码。

沿字节和等待连续读下去#

正文反复回到一件事：一个请求当前走到哪一步，为它保存了哪些 tensor，下一步在等谁。显存公式先告诉你装不装得下，Prefill 与 Decode 告诉你计算怎样发生，调度再解释许多请求如何分享有限容量。多卡把等待扩展到 rank，集群把它扩展到作业与副本。

手算例子只使用明确的形状、精度和假设条件。看到数字时，把输入条件一起带走，不把另一个模型的 KV 大小或另一张卡的峰值当作自己的部署结论。失败情景则用于区分症状与原因：同样是慢、OOM 或超时，发生阶段不同，应该测的对象也不同。

01

一条请求穿过哪些系统

用户点击发送后，GPU 并不会立刻开始计算。请求通常要经过网关、服务副本、引擎队列、tokenizer、调度器和 GPU worker。集群控制面则在旁边保证这些组件存在于合适的机器上。

数据面：请求真正走过的路#

1. 网关#

网关处理 TLS、身份、限流、配额和路由。它不应理解 GPU kernel，但需要知道模型名、租户和请求大小，以便拒绝明显超限的输入。

2. API 服务#

服务副本解析 OpenAI 兼容请求或内部协议，应用 chat template，并把文本变成 token IDs。tokenizer 主要在 CPU 上工作。高并发时，CPU tokenizer 也可能成为瓶颈。

3. 引擎调度器#

调度器维护等待和运行中的序列，决定本轮处理谁、处理多少 token、分配哪些 KV block。vLLM 当前源码中，EngineCore、Scheduler 和 KVCacheManager 分别承担运行核心、请求调度和 KV 资源管理。

4. GPU worker#

worker 加载模型并执行 kernel。单卡时它是一个 GPU 进程；张量并行时，一次逻辑推理需要多个 rank 协同。任何一个 rank 卡住，整体步骤都可能等待。

5. 流式回传#

生成 token 经 detokenize 后成为文本增量，再穿过服务与网关回到客户端。客户端看到“流式”，不代表 GPU 每生成一个 token 就发一个独立网络包，中间层可能聚合或缓冲。

请求进入副本，不等于已经得到 GPU 时间#

假设用户发送一篇长文。网关检查身份与长度，API 将文字转成 token，调度器才判断这一轮是否有 token budget 和 KV block。连接已经建立、服务也健康，请求仍可能在引擎等待。若只测 HTTP 建连时间，就会漏掉用户实际感受到的等待。

GPU worker 处理完成后，输出还要经过采样、文本解码和网络缓冲。用户一秒没有收到文字，可能是模型慢，也可能是回传被缓冲。排查时记录各层时间，而不是把最后可见的卡顿全部归给 GPU。

控制面：谁让服务存在#

Kubernetes 或其他调度系统负责选择节点、创建 Pod、挂载模型和重启失败实例。Device Plugin 把节点 GPU 注册成可调度资源。Operator 将“我要一个推理集群”翻译成 Deployment、Service、配置和状态调和。

控制面通常不参与每个 token 的热路径，但它的决定影响数据面：

  • Pod 被放到没有高速互联的 GPU 上，张量并行会变慢；
  • 模型下载没有本地缓存，冷启动会很长；
  • 健康检查太激进，长 prefill 可能被误判为卡死；
  • 扩容只看 GPU 利用率，排队已经上升却不触发。

两个调度器#

这是全书最重要的区分之一。

调度层 调度对象 时间尺度 典型约束
集群调度器 Pod、节点、GPU 秒到分钟 数量、拓扑、队列、优先级
推理调度器 请求、序列、token 毫秒级迭代 token budget、KV block、抢占

请求排队可能发生在网关、服务副本或引擎内部。只看 Kubernetes Pending Pod 无法判断用户为何等待，只看 vLLM 队列也看不到集群是否缺卡。

两个调度层可以分别健康，整体仍然慢#

集群已经给副本分配足够 GPU，但长请求占满 KV，新请求会在引擎里排队。反过来，引擎参数合适，扩容 Pod 因无卡 Pending，增加引擎 token budget 也不能创建新容量。前者要查活跃序列和内存，后者要查资源与拓扑。

控制面修复通常需要秒到分钟，token 调度却每轮都发生。扩容决策必须有提前量，不能指望创建 Pod 像移入一个短请求一样即时完成。

第一个排障方法：画时间线#

一次请求慢，先拆成：

网络与网关 -> 服务排队 -> tokenize -> 引擎排队
-> prefill -> decode 多轮 -> detokenize -> 网络回传

给每段打时间戳，不要先猜 GPU 不够。短请求的延迟常被排队和框架开销主导，长生成才更可能由 decode 主导。

离线与训练路径有什么不同#

批量推理可以提前分桶、容忍更长等待，目标偏总吞吐。训练没有逐请求网关，但多了数据加载、反向传播、优化器和 checkpoint。两者共享 GPU、通信和存储基础，调度目标却不同。

训练为什么没有网关，仍然会等待#

训练 step 先等数据 batch，再做计算和通信，周期性还等待 checkpoint。用户请求队列消失了，但数据队列和 rank 同步依赖仍存在。吞吐低时，沿 batch 从存储到 GPU 的路追踪，和沿在线请求追时间线使用的是同一种方法：找出谁已经准备好、谁还没准备好。

02

最少模型知识：token、tensor 与参数

AI Infra 不要求先会推导注意力公式，但必须能读懂数据形状。显存和通信量最终都来自“有多少个元素，每个元素几字节”。

Token 不是字，也不是固定长度#

Tokenizer 把文本切成词片段并映射为整数 ID。同一句中文在不同模型中可能产生不同 token 数。基础设施关心 token，因为：

  • prompt token 数决定 prefill 工作量；
  • 总上下文 token 数决定 KV cache；
  • output token 数决定 decode 轮数；
  • 计费、限流和吞吐常用 token 表示。

字符长度只能做粗略预估，真正入队前应以目标 tokenizer 计算。

Tensor 是带形状的数字数组#

常见形状记成：

[B, S, H]
  • B：batch 中有多少条序列；
  • S：每条序列有多少 token；
  • H：每个 token 的隐藏向量长度。

例如 [8, 2048, 4096] 的 FP16 tensor 包含 8 × 2048 × 4096 个元素，每个元素 2 bytes，约 128 MiB。还没算任何临时结果。

形状先决定元素数，精度再决定字节数#

把 [8, 2048, 4096] 看成八份序列，每份有 2048 个位置，每个位置有 4096 个数。三个维度相乘得到 67,108,864 个元素，乘 FP16 的 2 bytes 得到 134,217,728 bytes，也就是 128 MiB。若只改为 FP32，元素不变，空间变成 256 MiB。

这是一份 tensor 的账，不是模型全部激活。每层还有其他中间结果，算子可能保留或重用内存；形状算例提供量级起点，不应把它直接乘层数当成准确峰值。

参数是模型长期保存的 tensor#

“7B 模型”通常表示约 70 亿个参数。只看权重下界：

权重字节 = 参数量 × 每参数字节

70 亿参数使用 FP16 或 BF16：

7,000,000,000 × 2 bytes ≈ 13.04 GiB

这不等于一张 16 GiB 卡一定能运行，因为框架、KV cache、workspace 和临时 tensor 也要显存。

数据类型决定字节和数值范围#

类型 常见字节 用途直觉
FP32 4 精度高，训练部分状态常保留
FP16 2 范围较窄，需要关注溢出
BF16 2 指数范围接近 FP32，训练常见
FP8 1 需硬件和缩放策略支持
INT8 1 推理量化常见
INT4 0.5 权重更小，但打包与 kernel 有要求

“每参数 0.5 byte”是逻辑下界。量化 scale、zero point、对齐和打包会增加元数据。

参数量与请求长度分别让哪部分变大#

同一 7B 模型接收短句或长文，长期权重通常不变；变的是输入 tensor、计算量和历史 KV。换更大的模型会增加权重，而增加并发会增加同时存在的运行状态。于是“显存满了”要先判断到底改变了模型还是请求。

FP16 和 BF16 都占 2 bytes，却有不同数值范围与精度。字节数相同不表示训练稳定性相同；部署精度是一份数值与 kernel 合同，容量公式只解释其中的存储部分。

层、头和隐藏维度#

对 KV cache 估算，三个结构参数很重要：

  • 层数 L；
  • KV head 数 Hkv；
  • 每个 head 的维度 Dhead。

GQA 模型的 KV head 数可能小于 query head 数，因此不能总用 hidden size 直接代替。应读取模型 config。

Batch 有两种含义#

训练 batch 常指一次 optimizer step 处理的样本总数，还可能分成 micro-batch 和梯度累积。推理 batch 更动态，某一轮里活跃序列和处理 token 数都可变化。

所以“batch size 32”离开上下文没有意义。至少要说明：

  • 是序列数还是 token 数；
  • 是每卡还是全局；
  • 是 prefill 还是 decode；
  • 是否包含梯度累积。

FLOP 与 byte 是两本账#

模型执行既做计算，也搬数据。只统计 FLOP 会忽略显存和互联，只统计内存又会忽略 tensor core。后面用 Roofline 心智模型判断哪本账先成为上限。

在线 batch 不应被理解为整齐的矩形#

八条请求可能已经分别生成 10、200 或 1000 个位置，引擎会用分页、打包和 metadata 表达变长状态。教学 [B,S,H] 帮助读形状，但真实引擎不一定为每条请求补齐相同最大 S。FLOP 统计问做了多少运算，byte 统计问搬了多少数据，两者必须分别估算。

一个练习#

运行：

python3 examples/infra_lab.py memory --parameters 7 --weight-bits 16

再把 --weight-bits 改为 8。观察权重减少，但 KV cache 不变，因为它由层、KV head、head dim、活跃 token 和 KV 精度决定。

03

GPU 不是更快的 CPU

CPU 擅长少量复杂线程、分支和低延迟响应。GPU 用大量较简单的执行单元同时处理规则数据，擅长矩阵乘和向量操作。把串行 Python 搬到 GPU 上不会自动变快，任务要有足够并行度，数据移动成本也要值得。

一张卡里的四个角色#

计算单元#

CUDA cores 和 tensor cores 执行算术。厂商给出的峰值 FLOPS 依赖数据类型、稀疏条件和特定指令，不能直接当作应用速度。

HBM 或显存#

模型权重和运行 tensor 放在设备显存。容量决定能否装下，带宽决定每秒能搬多少。decode 常反复读取大量权重，因此即使算术不多，也可能被带宽卡住。

Cache 与 shared memory#

更靠近计算单元的小容量高速存储。好的 kernel 会复用数据，减少往返 HBM。FlashAttention 的核心贡献之一就是 IO-aware 分块，减少慢层级的数据移动，而不是近似注意力结果。

互联#

PCIe、NVLink、NVSwitch、InfiniBand 或 RoCE 连接 CPU、GPU 和其他节点。多卡性能由最慢的必要通信路径约束。

Roofline：先判断是哪种上限#

算术强度表示每读取一个 byte 做多少计算：

arithmetic intensity = operations / bytes moved
  • 算术强度低，点落在斜坡，优先减少数据搬运或提高复用；
  • 算术强度高，点接近平台，优先提高 kernel 与 tensor core 利用；
  • 实际性能还会受调度、同步、分支和 launch 开销影响。

Roofline 不是精确预测器，而是阻止错误优化方向的地图。

用一个假设硬件手算 Roofline#

假设有效显存带宽上限为 1 TB/s，目标精度计算上限为 100 TFLOP/s。算术强度为 10 FLOP/byte 的任务，带宽允许约 10 TFLOP/s，远未碰到计算平台；强度为 200 时，带宽给出 200 TFLOP/s，但计算平台只允许 100。上限取两者较小值。

这些是教学数字，不是某张卡的实测。实际 kernel 还受数据布局、并行度和同步影响。若任务在带宽斜坡，增加算术峰值未必有效；减少数据移动或提高一次读取的复用才更贴近瓶颈。

为什么 Decode 容易带宽受限#

每个 decode step 只为每条序列生成少量新 token，却要经过模型全部层并读取权重。batch 太小时，一次读权重只服务少量 token，算术强度低。增大活跃 batch 可提高复用，但会消耗更多 KV cache，并增加排队与尾延迟。

这就是在线推理的基本矛盾：

更大 batch -> 通常吞吐更高
更长等待 -> TTFT 与尾延迟可能更差

CUDA 是什么层#

CUDA 包含编程模型、运行时、编译工具和库。PyTorch、vLLM 等框架通过 CUDA kernel 操作 GPU。日常部署不必自己写 kernel，但要理解：

  • GPU 操作通常异步提交；
  • 测时前后可能需要同步，否则只测到 launch；
  • 不同 stream 可以重叠，但依赖必须显式满足；
  • 第一次调用可能包含编译、图捕获或 cache warmup；
  • allocator 可能保留显存，所以 nvidia-smi 不等于活跃 tensor 总和。

异步提交为什么容易测出虚假的加速#

CPU 发出 kernel 后可能立即返回，GPU 还在计算。只用主机时钟围住 Python 调用，可能主要测到提交开销。应使用适当 CUDA 事件或同步边界测实际 GPU 工作，并区分 warmup 与稳定运行。

同步也会改变实验环境：逐个算子强制同步可能破坏原本重叠。先明确测的是单算子还是端到端吞吐，再选计时方式，不把两者结果混在一张表里。

看哪些硬件指标#

指标 回答的问题
SM / tensor core 利用 计算单元是否有工作
HBM 带宽利用 是否在大量搬显存数据
显存占用 容量还有多少余量
PCIe / NVLink 流量 多卡或 CPU-GPU 搬运是否重
功耗与频率 是否降频或受功率限制
kernel 时间与空隙 GPU 是否在等待 CPU 或调度

“GPU 利用率 100%”本身不能说明效率。一个低效 kernel 也能让卡一直忙。

第一条性能纪律#

先记录工作负载，再记录硬件：模型版本、精度、输入输出长度分布、并发、batch 策略、GPU 型号、拓扑和软件版本。没有这些上下文的性能数字无法复现。

卡一直忙，为什么请求还很慢#

GPU utilization 高说明采样期间设备有工作，不说明每秒完成多少有用 token。反复重算、低效内存访问或通信 kernel 都可能让卡忙。结合吞吐、HBM 流量和 kernel 时间判断，再看是否存在 CPU 等待空隙。性能结论需要工作负载形状作为背景，不能只比较一条利用率曲线。

04

显存账本：模型到底占多少

显存不足不是一个原因，而是一张账单的总和。先把账分栏，再决定量化、分片、减 batch 还是缩短上下文。

推理账本#

权重#

weights ≈ parameters × bits / 8

这是最稳定的一项。量化能降低它，但 scale、打包和某些层保持高精度会产生额外开销。

KV Cache#

它随活跃 token 数增长，而不是只由模型大小决定。相同模型在并发 1 和并发 100 下，KV 需求可能差两个数量级。

激活与 workspace#

一次 forward 的中间 tensor、attention workspace、采样和通信 buffer。它们随 batch、token 数、kernel 和并行策略变化。

运行时保留#

CUDA context、allocator cache、CUDA graph 内存池、编译产物和碎片。服务通常不能把权重加 KV 算到显存容量的 100%。

训练账本#

训练需要：

  • 权重；
  • 梯度；
  • 优化器状态，例如 Adam 的一阶和二阶矩；
  • 混合精度下可能存在 FP32 master weights；
  • forward 激活，供 backward 使用；
  • 通信 bucket、临时 tensor 和 allocator 余量。

一个常见教学估算是混合精度 Adam 每参数约 16 bytes：2 bytes 权重、2 bytes 梯度、4 bytes master weight、8 bytes 两个 FP32 moment。实现不同，不能把 16 当作定律。

70 亿参数按 16 bytes 估算，训练状态约 104.31 GiB，还没算激活。这解释了为什么单卡能推理的模型，训练可能需要多卡分片。

权重放得下，不代表服务容量足够#

以一张假设 24 GiB 卡为例，7B 的 16 位权重下界约 13.04 GiB。扣除权重后的十余 GiB，还要给 KV、激活、workspace 和运行时留位置。若只按权重判断可接多少请求，就忽略了随上下文和并发增长的主项。

训练还需梯度与优化器状态，因此同一模型从推理切到训练，账本发生结构变化。降低请求并发能减少推理 KV，却不能消除 Adam moments；选择措施前先确定要减少哪一栏。

激活为什么难用一个倍数表达#

激活取决于 batch、序列长度、隐藏维度、层数、attention 实现和哪些 tensor 被保存。它与参数量不总是线性同倍增长。长序列训练中，激活可能成为主项。

Activation checkpointing 只保存部分边界，backward 时重算中间结果，以计算换显存。它不会减少权重或优化器状态。

已分配、已保留与可用#

PyTorch caching allocator 会保留释放后的块供后续复用：

  • allocated：活跃 tensor 实际占用；
  • reserved：allocator 向 CUDA 申请并保留；
  • free：设备报告未被当前进程保留的部分。

看到 OOM 时，要同时看峰值 allocated、reserved、碎片和失败分配大小。只在 OOM 后调用清 cache，通常治不了仍被活跃 tensor 占用的问题。

释放 tensor 后，reserved 为什么没有立刻下降#

Python 不再持有一个 tensor，allocator 可以把其块留给后续分配，而不立即还给驱动。因此 allocated 降了、reserved 没降，可能是正常缓存。仍被引用的 tensor 则不能靠 empty_cache 消失。

加载即 OOM 多半先查权重与加载峰值；长请求运行后 OOM 再查 KV 与临时空间；长时间逐步增长则查引用与释放路径。三种症状都叫 OOM，减少同一个参数未必解决。

OOM 排查顺序#

  1. 记录失败时的 batch、序列长度和并发。
  2. 区分加载时 OOM、首次 forward OOM、稳定运行后 OOM。
  3. 查看权重、KV、激活或临时 workspace 哪项随负载增长。
  4. 检查是否有 tensor 引用泄漏或请求未释放。
  5. 再选择量化、减 token budget、分片、checkpointing 或扩卡。

随机调 gpu_memory_utilization 只是在移动边界，不说明哪项失控。

用计算器建立量级感#

python3 examples/infra_lab.py memory \
  --parameters 7 \
  --weight-bits 16 \
  --layers 32 \
  --kv-heads 8 \
  --head-dim 128 \
  --context 8192 \
  --concurrent-requests 8

默认输出的 8 GiB KV 是“每条请求都用满 8192 token”的上界场景。真实容量规划应使用长度分布和峰值并发，而不是把最大上下文乘平均并发。

预算要留给峰值，而不只是平均#

平均上下文很短，少量长输入也可能在同一时刻占据大量块。容量估算应设代表性长度分布，再压测突发与极端组合。分页减少预留浪费，没有消除有效 token 和 workspace 的实际空间。

计算器输出是理论量级，未模拟 allocator、kernel 临时结果和所有并行 buffer。预测接近容量上限时，应更谨慎地增加余量，而不是把公式多保留几位小数当成精度保证。

一条安全规则#

容量估算必须留下余量，并在目标软件版本上压测。公式决定是否值得尝试，实测决定是否上线。

05

推理的两幕：Prefill 与 Decode

自回归模型不是一次吐出整段答案。它先读取全部提示词建立内部状态，然后一轮一轮生成后续 token。这两段在 GPU 上的形状不同，指标也不同。

Prefill 做什么#

假设 prompt 有 2000 个 token。Prefill 会让这些 token 通过模型各层，计算注意力并写入 KV cache。它能形成较大的矩阵乘，并行度较高，常更接近计算密集。

Prefill 的直接用户指标是 TTFT，也就是从请求进入系统到第一个输出 token 出现的时间。TTFT 包含的不只是 prefill：

TTFT = 网关 + 排队 + tokenize + prefill + 首 token 回传

因此 TTFT 高时不能直接断言 prefill 慢。

Decode 做什么#

第一个 token 生成后，新 token 被追加到上下文。下一轮只新增一个位置，但它需要读取历史 KV，并经过模型所有层。过程重复到停止条件。

用户感受到的生成流畅度常用：

  • TPOT：每个输出 token 的平均时间；
  • ITL：相邻 token 的延迟，可看分布；
  • output tokens/s：单请求或系统总生成吞吐。

如果中途某几轮突然变慢，平均 TPOT 可能掩盖卡顿，应看 ITL 分位数和时间序列。

读取长题目和续写长答案，是两种压力#

长 prompt 的多个位置可以在 prefill 中并行处理，但生成的新位置依赖前一轮结果，单条序列不能一次并行写出全部答案。将许多序列一起 decode，能提高跨请求并行度，却没有消除每条序列内部的顺序依赖。

因此长输入短答案常把压力放在首 token 之前，短输入长答案则可能首 token 很快、后续占卡很久。总耗时相近的两种请求，对调度和产品体验要求不同。

为什么不能只优化一个阶段#

增大 prefill chunk 可以更快吃完长 prompt，却可能让 decode 请求等待更久。优先 decode 可改善正在生成用户的流畅度，却让新请求 TTFT 上升。

调度器必须在以下目标间取舍：

  • 新请求尽快拿到首 token；
  • 已开始的请求稳定生成；
  • GPU 保持高利用；
  • KV cache 不超容量；
  • 长请求不能饿死短请求，反之亦然。

Chunked Prefill#

长 prompt 不必在一个 iteration 全部处理。可以拆成 chunk，与 decode token 共享每轮 token budget。这样减少一次巨大 prefill 阻塞，但增加调度轮数和策略参数。

max_num_batched_tokens 一类配置本质上在控制每轮工作量。设置大通常偏吞吐，设置小可能偏交互延迟，但结果依赖模型、硬件和长度分布。

切小 prefill 怎样帮助正在生成的用户#

假设当前有十条序列等待下一 token，新长 prompt 一次占用很大的迭代工作量，它们会等本轮结束。把 prompt 拆成 chunk，调度器可以在轮次之间给 decode 留份额，减少长输入连续阻塞。

切分也有代价：更多轮次与管理，且新请求读完整 prompt 才能生成首 token。不能同时保证所有长度的 TTFT、ITL 和最大吞吐都最优，需要按真实流量确定优先目标。

Prefill/Decode 分离#

更大规模服务可让不同 worker 分别处理 prefill 和 decode，再传输 KV。优点是两类负载可独立扩缩和调优，缺点是需要高速 KV 传输、路由和故障处理。

判断是否值得分离前先量化：

  • prefill 与 decode 各自占多少 GPU 时间；
  • KV 传输量和互联带宽；
  • 长 prompt 是否真的干扰 decode；
  • 分离后的空闲和排队是否更少。

复杂架构不能凭示意图证明更快。

一个简单类比#

Prefill 像读完题目并做笔记，Decode 像每次只写一个字但不断翻阅笔记。题目长会推迟开写，答案长会延长逐字生成。

分离前先算 KV 交接的成本#

Prefill worker 处理完以后，decode worker 需要历史 KV。其传输量由上下文、层数、KV heads 和精度决定，不是只发几个 token ID。长文的计算节省若被网络传输吃掉，拆开两组 worker 可能更慢。

因此先测两阶段 GPU 时间和传输量，再比较独立调度的收益。低流量下两组都可能空闲，多增加一条故障与路由链，也应计入采用成本。

观测建议#

至少分别记录：prompt tokens、output tokens、queue time、prefill time、decode time、TTFT 和 TPOT。只记录总延迟无法解释是长输入、长输出还是排队造成。

06

KV Cache：上下文为什么越来越贵

注意力层生成新 token 时需要参考之前位置的 key 和 value。重复计算全部历史很浪费，所以推理引擎把每层历史 K/V 保存下来。这就是 KV cache。

先记公式#

对常见 Transformer，单个 token 的 KV 下界约为：

KV bytes/token
= 2 × layers × kv_heads × head_dim × bytes_per_element

前面的 2 表示 K 和 V。全部活跃序列：

total KV ≈ bytes/token × active tokens

例：32 层、8 个 KV heads、head dim 128、BF16：

2 × 32 × 8 × 128 × 2 = 131,072 bytes/token

也就是每 token 128 KiB。总共 131,072 个活跃 token 时，理论 KV 正好约 16 GiB。

Active tokens 是什么#

它是当前仍在服务中的所有序列已缓存 token 总和，不等于每秒输入 token，也不等于配置的最大上下文。一个完成的请求释放 KV 后，block 可给新请求复用。

容量规划应关注分布：

  • 同时活跃多少请求；
  • 每条请求当时已经走到多长；
  • prefix cache 是否共享前缀 block；
  • speculative decoding 是否增加临时状态；
  • KV 使用什么精度。

容量统计是一张随时间变化的照片#

一条请求读完 2000 token、又生成 100 token，缓存覆盖约 2100 个位置；另一条只到 500。即使二者最大上下文都设置 8192，当前有效 KV 不是两个最大值相加。请求完成后释放或进入受管理缓存，后续占用又会变化。

按本章 128 KiB/token 的例子，一条 8192 token 序列理论约 1 GiB，八条都走到该长度约 8 GiB。这个算例说明为什么上下文和并发要一起看，不能把最大值乘平均并发当成可靠峰值。

连续大块为什么浪费#

如果为每条请求预留最大上下文的连续区域，短请求会留下大量内部浪费，不同长度释放后还可能形成外部碎片。请求长度不可预测，使传统连续分配很难保持高利用。

PagedAttention 借鉴虚拟内存分页：逻辑上连续的 KV 可以放在不连续物理 block，block table 负责映射。请求增长时按需增加 block，结束后归还。

它减少碎片和预留，不改变每个有效 token 必须保存 KV 的事实。

Block 大小的权衡#

  • block 大：表更小、管理开销低，但最后一个 block 浪费更多；
  • block 小：碎片少，但元数据、分配和 kernel 处理更复杂。

实际引擎还要考虑对齐、kernel 支持和 prefix cache，因此不是越小越好。

block table 怎样保持逻辑连续#

请求的第 0、1、2 个逻辑块可以对应物理池中的不同位置，attention kernel 根据映射访问，而不是要求显存连续。请求增长时只补下一块，其他请求释放的块可以重新利用。这减少因最大长度预留和不连续空洞造成的浪费。

最后一块仍可能未填满，metadata 与访问也有成本。分页优化的是分配组织，没有让同一个有效位置的 K/V 凭空变小；KV 精度和头数才影响公式里的单位大小。

Prefix caching#

很多请求共享相同 system prompt 或文档前缀。若 token 与模型配置完全匹配，可复用已有 KV block，减少重复 prefill。

它不是普通文本 cache：chat template、token IDs、模型版本、LoRA、位置和多模态输入都可能影响可复用性。cache key 不完整会得到错误结果。

抢占与重计算#

KV 不足时，引擎可能暂停低优先级序列，释放或换出其 cache，之后重算或恢复。这样能避免立即拒绝请求，但会增加延迟和重复计算。监控 preemption 数量比只看 OOM 更早发现容量压力。

前缀共享与最终答案缓存的差别#

相同 token 前缀能复用对应计算，后续问题不同仍要继续 prefill 或 decode。模型版本、位置处理或 adapter 变化后，即使文字相同也不一定可复用。命中率高只说明复用机会多，最终答案质量与输出速度还受剩余计算影响。

抢占后重算又可能重复读取同一段历史，提升可用性却降低有效吞吐。观察 block 使用率、抢占和重复计算，才能知道服务是否接近容量压力，而不必等到 OOM。

常见误区#

  • 最大上下文从 32K 改到 128K，不代表必须立即预留四倍 KV，但允许单请求增长到更大上限。
  • 量化权重到 INT4，不会自动量化 KV。

连续批处理：GPU 如何同时服务很多人

传统静态 batch 等一组样本全部完成再换下一组。在线生成的请求长短差异很大，如果等待最长请求，短请求完成后的计算槽位会空着。

iteration-level scheduling#

自回归 decode 天然分轮。推理引擎可以在每轮重新决定 batch：

  1. 找出仍在运行的序列；
  2. 接纳等待请求或 prefill chunk；
  3. 检查 token budget 和 KV block；
  4. 生成本轮模型输入；
  5. GPU 执行；
  6. 更新序列状态，释放完成请求。

这就是连续批处理的核心。它不是把 HTTP 请求简单合成一个列表，而是在生成过程中不断重组工作。

三个约束#

Token budget#

一轮最多处理多少 token。Decode 序列通常各贡献一个新位置，chunked prefill 可能贡献许多位置。

Sequence 数量#

活跃序列越多，调度和 metadata 开销越大，也占更多 KV。即使 token budget 还有余量，也可能受最大序列数限制。

KV block#

新请求只有能分配需要的 block 才能前进。KV 压力会触发等待、抢占、重算或拒绝。

这一轮有 token 预算，为什么还是进不了新请求#

假设一轮允许 128 个 token，20 条 decode 序列各占一个位置，理论还剩 108。新 prompt 可以切入这部分，但只有 KV 池能提供需要的块、序列数没到上限时才能执行。三个约束限制不同对象，空着一项不代表其他项也有余量。

下一轮某条请求结束，它的计算位置和可释放 KV 才能给新请求。连续批处理因此需要随结果更新资源，不是把到达的 HTTP 请求一次拼起来后始终保持 batch 不变。

策略不是只有 FIFO#

引擎可考虑到达顺序、优先级、已完成进度、请求长度和 SLA。不同策略会改变公平性：

  • 优先短请求可降低平均延迟，长请求可能饥饿；
  • 优先 decode 可保持流畅，新的长 prompt TTFT 上升；
  • 优先已运行请求可减少抢占，但高优请求响应不够快。

产品应定义优先级语义，引擎参数只是实现手段。

为什么吞吐和延迟会冲突#

等待更多请求形成大 batch，可提高权重复用和 GPU 效率，但每个请求先在队列里多等。低流量下强行等待 batch 往往得不偿失，高流量下不做 batching 又浪费 GPU。

服务需要在真实到达率下找工作点，而不是只跑“无限并发”吞吐 benchmark。

最大吞吐实验为什么不代表真实等待#

持续灌满请求可以测接近饱和时的 token 吞吐，却无法说明低流量用户等多久。为了攒大 batch 额外等待，在饱和时不明显，在每秒只有少量请求时可能成为主要延迟。

评测应同时给出到达率、长度分布和延迟分位数。短任务优先降低平均值，却可能让长任务反复被推迟；加优先级后还要检查饥饿与租户公平，不能只盯总体 tokens/s。

试着修改 token_budget：

  • 预算太小，长 prefill 需要更多轮，TTFT 上升；
  • 预算变大，prefill 更快，但真实系统中一次 iteration 可能更长；
  • block 太少，模拟会没有进展，对应真实系统的 KV 容量压力。

读调度源码时追一条请求的资源变化#

从等待队列选中请求，查看本轮分了多少 token、申请了哪些 block；执行后再看计数推进、完成释放或抢占。调度输出与模型执行结果分开核对，才能发现“选中了但没推进”或“结束了却没释放”。玩具模拟器只演示这种关系，没有真实 kernel 和网络时间，不能据此预测某张 GPU 的性能。

Benchmark 应记录什么#

模型加载、精度与量化

模型能放进显存，只是部署的第一关。加载时间、权重格式、量化 kernel、硬件支持和输出质量共同决定是否可用。

冷启动发生了什么#

典型顺序：

读取配置 -> 创建模型结构 -> 读取权重分片
-> CPU 解码或映射 -> 搬到 GPU -> 转换/量化
-> 分配 KV 与 workspace -> 编译或捕获图 -> warmup

模型文件在对象存储、网络盘、本地 SSD 和 page cache 中，冷启动时间会完全不同。第二次启动更快，可能只是操作系统 cache 命中，不代表存储设计已经解决。

权重格式#

安全、可分片、支持 memory mapping 的格式更适合大模型。加载器还要处理：

  • 参数名到模型层的映射；
  • tensor parallel rank 只读取自己的分片；
  • tied weights；
  • 量化 scale 与元数据；
  • 模型架构自定义代码的信任边界。

不要在生产环境无审查执行模型仓库的远程代码。

量化到底减少什么#

权重量化主要减少权重存储和搬运：

FP16 7B ≈ 13.04 GiB
INT8 7B ≈ 6.52 GiB + metadata
INT4 7B ≈ 3.26 GiB + metadata

它可能允许更大 batch 或更多 KV，也可能提高 decode 的有效带宽。但量化还会增加反量化、scale 读取和特定 kernel 要求。

权重压缩以后，剩下的空间去哪里#

7B 权重从 16 位降到 4 位，理论从约 13.04 GiB 降到 3.26 GiB，但还需 scale、某些高精度层与运行空间。节省部分可以容纳更多 KV，也可以作为峰值余量。它并没有自动把 KV 和激活都变成 4 位。

模型文件较小还可能降低读取量，但加载器可能要转换格式或生成适配 kernel。磁盘体积、设备常驻体积与启动峰值是三个数字，分别记录才能解释为什么文件已变小而启动仍然 OOM。

为什么更小不一定更快#

  • 小 batch 下 kernel launch 与解包开销占比高；
  • 某硬件没有高效目标精度指令；
  • 算子回退到慢实现；
  • 只有部分层量化，频繁转换；
  • prefill 原本计算受限，低精度 kernel 未充分优化；
  • 请求受排队或网络限制，权重速度不是瓶颈。

量化必须在目标 GPU、长度和并发上 benchmark。

精度是系统合同#

训练常在 FP32、BF16、FP16、FP8 间混合。推理可进一步使用 INT8/INT4 权重和低精度 KV。每次降低精度都要回答：

  1. 哪些 tensor 降低？
  2. 在哪里累加？
  3. scale 如何产生和保存？
  4. 哪些层保持高精度？
  5. 质量如何评估？
  6. kernel 与硬件是否支持？

“模型是 INT4”不够，至少要说明量化方法、group size、activation/KV 精度和运行时。

精度合同要覆盖输入到 kernel 的整条路#

权重格式声明 INT4，运行 kernel 需要正确打包布局和 scale，累积又可能用更高精度。某一环不兼容，可能加载失败、回退慢路径或影响数值结果。仅核对文件名带 quant 不足以证明部署正确。

质量验证用代表性的真实问题，性能验证用目标长度和并发；两者各自固定基线。若推理更快却使关键任务失败率上升，压缩没有获得产品净收益。

模型加载的分布式问题#

多卡模型有两种常见方向：

  • 每个 rank 从存储读取自己的 shard；
  • 少量 rank 读取，再通过网络广播或 scatter。

前者给存储带来并发读取压力，后者给节点内或节点间网络带来压力。最佳方案取决于 checkpoint 布局、文件系统和拓扑。

热更新与滚动发布#

大模型启动慢，不能把普通无状态 Web 服务的滚动参数原样照搬。需要考虑：

  • 新副本完成权重加载和 warmup 后再接流量；
  • 同时启动太多副本会打爆对象存储；
  • 旧副本要排空长生成请求；
  • 模型版本、tokenizer 与 chat template 必须一致；
  • 回滚时旧权重和镜像仍可获取。

滚动更新为什么需要额外容量#

旧副本仍在处理长生成，新副本同时下载、加载和预热，切换期会占用两套资源。readiness 不应仅表示端口打开，要确认模型、KV 和必要 warmup 已准备。否则流量切过去，首批用户承担全部冷启动。

对多 rank 模型还需整组版本一致，不能让半组旧权重与半组新权重共同执行。版本、精度、adapter 和索引缓存一起切换，并保留已验证的回退路径。

多卡不是一个开关

模型装不下一张卡，或一张卡吞吐不够时，需要切分工作。切分方向不同，省下的显存、产生的通信和适合的拓扑都不同。

数据并行 DP#

每组 GPU 拥有完整模型，处理不同数据。

  • 推理：多个副本服务不同请求，扩大总吞吐；
  • 训练：每卡处理不同 micro-batch，再同步梯度；
  • 优点：概念简单，副本间热路径可相对独立；
  • 约束：单副本仍要装下模型，训练还要同步梯度。

在线服务的“4 个副本”通常属于 DP 思路，不代表一次请求使用 4 卡。

张量并行 TP#

把一层里的大矩阵按行或列切到多卡。每层都可能需要 AllReduce 或 AllGather。

  • 解决单卡装不下或单卡计算不足；
  • 通信频繁，适合节点内高速 NVLink/NVSwitch；
  • TP 度过大时，每卡矩阵变小，通信与 launch 开销占比上升；
  • head 数、hidden size 等通常要能被 TP 度整除。

两卡切矩阵，与两卡各跑请求有什么不同#

假设矩阵 W 按输出列切成 W1、W2，两卡读取同一输入，得到不同输出片段，再按后续计算要求拼接或通信。一次请求需要两卡配合，这是 TP。两卡各持完整 W，分别接不同用户，则是副本式 DP，不需要把一次结果拼起来。

因此增加副本主要扩大总吞吐，TP 主要改变单副本容量与执行路径。把已有四卡服务改成四个副本，前提是每张卡都能容纳完整模型与运行状态。

流水线并行 PP#

把不同层放到不同 stage，激活沿 stage 传递。

  • 每卡只保存部分层；
  • 通信频率比层内 TP 低，但存在 pipeline bubble；
  • 推理单请求要依次经过所有 stage，延迟增加；
  • micro-batch 和 stage 平衡决定利用率。

节点间互联较慢时，PP 有时比跨节点 TP 更合适，因为传输的是 stage 边界激活，而不是每层 collective。

上下文并行 CP#

把长序列维度分到多卡，解决单卡 attention 激活或 KV 压力。它需要处理 attention 的跨卡信息交换，适合超长上下文训练和特定推理场景。

专家并行 EP#

MoE 模型只激活部分 experts。EP 把专家分到不同卡，token 通过 AllToAll 路由到目标专家。

性能依赖 token 分布是否均衡。某些专家过热会让其他 GPU 等待，所以 router load balance 是基础设施问题，也是模型问题。

并行可以组合#

一个大训练任务可能写成：

world_size = DP × TP × PP × CP × EP

并非所有维度都独立，实际框架会构造多维 device mesh。选择顺序通常先考虑：

  1. 单卡能否装下；
  2. 节点内有哪些高速互联；
  3. 节点间带宽和延迟；
  4. 模型结构是否 MoE、是否长上下文；
  5. batch 是否足够填满 pipeline 和 DP。

device mesh 的坐标决定谁和谁通信#

以 DP=2、PP=2、TP=2 的简化八卡布局为例，每个 rank 有三个坐标。TP 通信发生在同一 DP、PP 坐标内，PP 传输连接相邻 stage，DP 同步连接对应模型部分。编号相邻不必然表示物理互联最好，还要映射真实拓扑。

CP 与 EP 的组合在不同框架中可能共享或依赖其他维度，不能无条件将五个参数相乘当作 GPU 数。先理解每个 group 的成员与数据归属，再核对框架的 mesh 规则。

一个 8 卡例子#

如果 70B 权重 FP16 约 130 GiB，单张 80 GiB 卡放不下。可在一个 8 卡节点使用 TP=2 或 TP=4，让每卡只保存部分权重，再视吞吐需要复制 DP 组。

但不能只做除法。还要给 KV、workspace 和通信 buffer 留空间，并检查每层 collective 是否被互联支持。

推理与训练的同名差异#

TP、PP 在两者中概念相近，但调度目标不同：

  • 训练追求稳定大 batch 吞吐，通信形状规律；
  • 在线推理 batch 动态、序列长度不同，还要管理 KV；
  • 训练 PP 用 micro-batch 填流水线，推理 PP 要考虑逐 token latency。

不要把训练 benchmark 的并行配置直接复制到在线服务。

只做权重除法会漏掉通信和峰值#

130 GiB 权重切到两卡，理想每卡约 65 GiB，还要留 KV、workspace 与通信 buffer。TP 也不是保证每个 tensor 都严格均分，一些状态可能复制。模型能加载只证明容量第一关通过，接下来应测长上下文和多请求峰值。

多卡变慢时分别看每卡计算是否太小、每层通信是否昂贵以及 stage 是否空闲，避免再增加卡数放大同一瓶颈。

Collective：GPU 之间怎样交换数据

多卡程序不是八个独立进程各算各的。每个 rank 只持有局部数据，需要通过 collective 形成全局结果。NCCL 提供针对 NVIDIA GPU 与互联优化的 collective 实现。

四个最常见操作#

AllReduce#

每个 rank 有一份输入，先做 sum/max 等归约，每个 rank 都得到同一结果。数据并行同步梯度常用。

AllGather#

每个 rank 持有一个 shard，交换后每个 rank 得到完整集合。FSDP 在计算某层前组装参数常用。

ReduceScatter#

先归约，再把结果分片留在各 rank。FSDP 梯度分片常用。它可避免 AllReduce 后每卡保留完整结果。

AllToAll#

每个 rank 都向所有 rank 发送不同部分。MoE token 路由常用，对网络和负载均衡敏感。

用两个 rank 区分归约与收集#

rank 0 有 [1,2]，rank 1 有 [3,4]。sum AllReduce 后两者都拿到 [4,6]；AllGather 则让两者拿到各自输入组成的集合，没有做相加。ReduceScatter 在相同简化输入下先形成和，再让各 rank 留不同片段，比如分别得到 [4] 与 [6]。

AllToAll 则可让每个 rank 将输入分成给不同目标的部分，交换后每个目标得到来自各源的片段。操作名规定了数据关系，不是随意交换几个名称就能获得相同结果。

Ring 的直觉#

AllReduce 可以拆成 ReduceScatter 加 AllGather。Ring 算法让每个 rank 只和邻居交换 chunk，多轮后完成聚合与分发。它能较好利用带宽，但轮数随 rank 增加，低延迟小消息可能更适合 tree 等算法。

NCCL 会依据消息大小、拓扑和配置选择算法与 protocol。应用通常调用语义，不手写环。

拓扑比 GPU 数量更重要#

八张卡可能是：

  • 同一 NVSwitch 域；
  • 分属两个 PCIe root complex；
  • 跨两个节点，经 InfiniBand 或 RoCE；
  • 网络路径还与其他作业共享。

同样 TP=8，在这些拓扑上的结果完全不同。部署前应查看 nvidia-smi topo -m、NIC 亲和和 NCCL topology log。

同步等待#

collective 需要所有参与 rank 以兼容顺序加入。一个 rank 因数据加载、CPU 抖动或 kernel 变慢，其他 rank 会在通信点等待。表面上看是 NCCL 慢，根因可能在最慢 rank 之前。

排查 hang 时检查：

  1. 所有 rank 是否调用了相同 collective；
  2. tensor shape、dtype、count 是否一致；
  3. 是否有 rank 更早抛异常；
  4. 网络接口和权限是否正确；
  5. 超时是否掩盖真实首错；
  6. 日志时间线中哪个 rank 最先偏离。

所有进程都活着，collective 也可能永远等不到#

若 rank 0 调 AllReduce，rank 1 因条件分支跳过它，其他 rank 等不到匹配操作。若它们顺序或 tensor 形状不一致，同样可能出错。这类问题与网络带宽不足不同，升级网卡无法修复。

先按统一 run ID 对齐所有 rank 的日志，找到第一次分歧。某 rank 在通信前 OOM，其他日志最后显示 NCCL 超时，首错仍是显存。通信处等待只告诉你依赖未满足，没有直接证明通信库是根因。

通信量如何影响并行选择#

TP 往往每层通信，要求低延迟高带宽；PP 主要在 stage 边界传激活；DP/FSDP 在反向传播中同步梯度或参数 shard；EP 使用 AllToAll。

不要问“哪种 collective 最快”，要问：

  • 消息多大；
  • 每 step 几次；
  • 能否与计算重叠；
  • 走节点内还是节点间；
  • 最慢 rank 是否稳定。

Overlap 不是免费#

通信与计算重叠需要二者资源相对独立，并满足依赖。通信 kernel 也会使用 GPU 资源和内存带宽。过度切小 bucket 会增加 launch 与同步开销，bucket 太大又推迟通信开始。

大带宽为什么救不了大量小消息#

用简化模型 时间 ≈ 固定延迟 + 字节数 / 有效带宽。假设延迟 10 μs、带宽 100 GB/s，传 1 KB 的数据时间仅约 0.01 μs，几乎全在固定开销；传 100 MB 则数据部分约 1 ms。真实 collective 有多轮和不同链路，但这个量级说明：切小 bucket 能更早启动，却可能把固定开销重复很多次。

有效 overlap 要看仍在计算的部分是否依赖该通信结果，以及通信是否争用 GPU 和 HBM。时间轴显示并发，不代表端到端 step 一定缩短，应测最终耗时。

训练循环与训练显存

训练基础循环只有四步：取数据、forward、backward、optimizer step。大模型训练系统的复杂性来自每一步都可能跨多卡，并且状态大到不能完整复制。

for batch in dataloader:
    optimizer.zero_grad()
    loss = model(batch)
    loss.backward()
    optimizer.step()

Forward#

输入 token 经过 embedding 和每层 Transformer，得到 logits 与 loss。为 backward 计算梯度，框架通常保留部分中间激活。

Backward#

自动微分按计算图反向计算参数梯度。Backward 不是 forward 的简单倒放，它可能需要读取保存激活、重算 checkpointed 区域，并在数据并行 rank 间同步梯度。

Optimizer Step#

AdamW 读取权重、梯度和两个 moment，更新参数。优化器状态体积大，且是训练 checkpoint 的主要组成部分之一。

Micro-batch、Global batch 与累积#

global batch
= micro batch per GPU × data parallel degree × accumulation steps

梯度累积让每卡用较小 micro-batch 多跑几次 forward/backward，再做 optimizer step。它降低单次激活峰值，但增加每个 step 的串行 micro-step 数。

必须记录 batch 的口径，否则学习率和吞吐都无法比较。

一次 optimizer step 究竟看过多少样本#

每个 DP rank 的 micro-batch 为 2，DP 度为 8，累积 4 次后更新，则 global batch 为 64。TP 或 PP rank 协同处理同一份模型工作，不能再把它们当作额外独立样本乘进去。比较吞吐和学习率时，必须使用相同 batch 口径。

累积降低单次激活峰值，但梯度要在更新前正确累计，loss 缩放与同步策略也要匹配。不能简单重复四次普通循环而每次都清梯度并 step，那会成为四次不同的优化器更新。

训练显存四大项#

  1. 模型参数；
  2. 梯度；
  3. 优化器状态；
  4. 激活。

前 3 项主要随参数量增长，激活主要随 micro-batch、序列长度、层和实现增长。FSDP/ZeRO 主要分片前 3 项，activation checkpointing 主要减少第 4 项。

Activation Checkpointing#

普通做法保存中间激活，用空间换 backward 速度。Checkpointing 只保存选定边界，backward 时重新 forward 该段。

少存激活 -> 显存下降
重新计算 -> step 时间上升

选择粒度太粗，重算多；太细，边界和调度开销增加。应按层或算子成本 profile。

重计算省下的是激活，而不是所有训练状态#

forward 保存每层中间结果方便 backward，但占显存；checkpointing 只留边界，反向需要时重新算该段。参数、梯度与 optimizer moments 仍存在，所以状态主导的 OOM 不会只靠重算消失。

选择区域时看保存字节与重算成本。很便宜又很占空间的中间结果适合重算，昂贵区域则可能拖慢 step。随机操作与实现细节也需正确处理，数值训练不能只验证程序没报错。

Mixed Precision#

模型计算可用 BF16/FP16/FP8，部分归约和优化器状态保留更高精度。混合精度的目标不是“所有 tensor 都变小”，而是在数值稳定、硬件吞吐和显存间取平衡。

FP16 训练常需要 loss scaling 防止小梯度下溢。BF16 指数范围更大，但尾数精度较低。具体策略由模型、硬件和框架决定。

step 变快，还要确认每步工作没有变少#

缩短序列或减少 global batch 会降低 step 时间，但改变了处理的数据量。tokens/s、有效样本数和 loss 曲线一起比较，才能判断优化是否保留训练语义。混合精度也要观察数值异常，速度提升不应以模型无法收敛为代价。

GPU 空隙可能来自 dataloader、通信或 checkpoint。将一次 step 拆成取数、前向、反向、更新和保存，再找最长等待段，比先替换某个 kernel 更容易解释结果。

训练吞吐看什么#

  • samples/s 或 tokens/s；
  • model FLOPs utilization，但要统一计算口径；
  • step time 及 data/forward/backward/optimizer/communication 分解；
  • straggler rank；
  • checkpoint pause；
  • loss 和梯度健康度。

只追求 GPU 利用率可能把数据错误、数值发散和 checkpoint 失败藏起来。

分片、重计算与并行组合

单卡显存装不下训练状态时，第一反应不应是盲目增加 GPU。先确认要切的是数据、参数、激活、序列还是模型层，因为每一种切法引入不同通信。

从复制到完全分片#

普通数据并行在每个 rank 复制权重、梯度和优化器状态。FSDP 与 ZeRO 将这些状态按 rank 分片。

ZeRO 的教学分级#

  • Stage 1：分片 optimizer state；
  • Stage 2：再分片 gradient；
  • Stage 3：再分片 parameter。

现代框架的具体接口和内部实现不一定直接使用这些名字，但这个递进帮助理解：省得越多，按需组装与通信越多。

FSDP2 的直觉#

每个 rank 平时保存参数 shard。某层计算前 AllGather 形成需要的参数，完成后可 reshard。Backward 同样需要参数，并通过 ReduceScatter 得到分片梯度。

关键调优点：

  • shard group 大小；
  • 哪些 module 作为一个 FSDP unit；
  • prefetch 与通信计算重叠；
  • forward 后是否 reshard；
  • mixed precision 和 CPU offload；
  • state dict 与 checkpoint 格式。

过小的 unit 会产生大量小 collective，过大又提高峰值显存。

分片后的常驻显存与计算峰值不同#

假设总参数 16 GiB，四个 rank 理想各常驻 4 GiB。某个 unit 大小也是 4 GiB，若计算前另分配完整参数 buffer，这一时刻就会同时存在常驻 4 GiB 和完整 buffer 4 GiB。预取下一 unit 还可能继续增加占用。这里是简化分配算例，实际生命周期依实现而异；关键是峰值不能只用总参数除以四。

FSDP unit 越大，一次组装越大；越小，collective 次数越多。粒度选择要看峰值与通信时间的共同曲线，省掉常驻状态只是优化的一部分。

3D 并行#

大规模训练常组合 DP/FSDP、TP 和 PP：

DP/FSDP：切训练样本或训练状态
TP：切每层矩阵
PP：切模型层

Megatron-LM 进一步支持 CP、EP 等维度。device mesh 给每个 rank 坐标，例如 (dp, pp, tp)，每类 collective 只在对应维度 group 内发生。

为什么节点内优先 TP#

TP 每层通信，最需要低延迟高带宽。因此通常先把 TP group 放在同一 NVLink/NVSwitch 域，再把 PP 或 DP 扩到节点间。具体仍取决于硬件拓扑和模型形状。

如果 scheduler 把一个 TP group 的 Pod 分散到普通网络节点，程序可能能启动，但性能严重下降。

Pipeline Bubble#

PP stage 必须等待前一 stage 的激活。用多个 micro-batch 交错可填流水线，但开始和结束仍有空泡。stage 计算不均衡时，最慢 stage 决定节拍。

优化方向：

  • 平衡每个 stage 的层与计算；
  • 增加合理 micro-batch 数；
  • 使用 1F1B 等 schedule；
  • 避免某 stage 独占 embedding 或 loss 的额外开销；
  • 监控每 stage 时间，而非只看全局 step。

流水线空泡不是 GPU 没有被分到任务#

只看两个等时 stage 的 forward：一个 micro-batch 需要两段时间，各卡只忙其中一段。四个 micro-batch 流水执行，A 在第 1 至 4 段处理，B 在第 2 至 5 段处理，总共五段，每卡忙四段，理想利用率为 80%。真实训练还有反向、通信和调度依赖，不能照搬这个比例，但它说明增加 micro-batch 怎样摊薄起止空泡。

因此 PP 利用率与 micro-batch 数、stage 平衡和 schedule 相关。只看集群给齐了多少卡，无法判断流水线是否填满；还要查看每个 stage 的计算与空闲时间。

CPU Offload 的真实代价#

把参数或 optimizer state 放到 CPU 可省 GPU 显存，但通过 PCIe 搬运。若搬运不能与计算重叠，GPU 会等待。CPU 内存带宽、NUMA、pinned memory 和网络也成为系统部分。

Offload 是容量方案，不是免费扩容。

选型顺序#

  1. 用 activation checkpointing 处理激活峰值。
  2. 用 FSDP/ZeRO 分片训练状态。
  3. 模型单层或算子仍太大时引入 TP。
  4. 整体层数继续扩展时引入 PP。
  5. 长序列或 MoE 再考虑 CP/EP。
  6. 每增加一维，都用 profile 确认通信与空泡。

这个顺序不是定律，但避免一开始就构造难以调试的五维并行。

怎样让并行选择成为可解释的实验#

先确认 OOM 主项，激活大则试重算，长期训练状态大则试分片；单层仍过大再研究 TP，层数扩展再研究 PP。每次保留更简单对照，记录峰值、通信字节和 step 时间。

offload 把问题转移到 CPU 内存与 PCIe，若搬运不可重叠，节省显存的同时会增加等待。复杂 mesh 能扩大容量，但故障定位与 checkpoint reshard 也更难，应计入运维成本。

数据管道与 Checkpoint

昂贵 GPU 等数据，是最容易被误认为“模型慢”的问题之一。训练系统还必须定期保存足够状态，以便故障后恢复，而不是从第 0 步重来。

数据路径#

对象存储 / 文件系统
  -> shard 列表
  -> worker 读取与解码
  -> tokenize / pack
  -> host memory
  -> H2D copy
  -> GPU batch

每一段都可能产生背压。GPU 空闲时先看 dataloader queue 和 copy 时间，不要立即改模型 kernel。

Sharding 与顺序#

数据并行 rank 应读取不同样本，又要保证：

  • epoch 覆盖正确；
  • shuffle 可复现；
  • resume 后不大量重复或漏数据；
  • worker 数变化时语义明确；
  • 不同长度样本 packing 策略一致。

只保存 global step 不一定能恢复数据位置。dataloader 或 sampler state 也是 checkpoint 的一部分。

从同一 step 恢复，为什么还可能读到不同数据#

global step 只表示完成了多少更新，不完整描述哪个 shard、sample 或随机排列已被消费。恢复时若 sampler 从头开始，程序能继续，却可能重复大量样本；改变 worker 数也可能改变切分。等价恢复需要数据位置和随机状态与模型状态一起对应。

输入 packing 还影响有效 token 数。相同样本数若使用不同长度合并规则，batch 形状和训练吞吐都会变化。数据版本与读取策略属于运行合同，不应只记录模型 commit。

Checkpoint 保存什么#

一次可恢复训练通常需要：

  • 模型参数；
  • optimizer state；
  • learning-rate scheduler；
  • 当前 step；
  • RNG state；
  • data loader/sampler state；
  • loss scaler 或其他数值状态；
  • 并行与模型配置；
  • 代码和数据版本引用。

漏掉 RNG 与数据位置，程序仍能继续跑，但不再是等价恢复。

分布式 Checkpoint#

大状态不应由 rank 0 收集后写一个巨型文件，这会造成内存峰值和单点瓶颈。分布式 checkpoint 让各 rank 写 shard，并保存可描述全局 tensor 的 metadata。

恢复到不同 world size 时，需要 reshard。格式应表达全局 shape 和 shard placement，而不是把当前 rank 编号写死成长期合同。

一致性与原子提交#

一个可用 checkpoint 应满足“要么完整可见，要么不可见”。常见过程：

  1. 各 rank 写临时 shard；
  2. 校验完成和大小；
  3. 写 metadata；
  4. 最后提交完成标记或原子重命名；
  5. 更新 latest 指针。

若只看目录存在就恢复，可能读到一半成功的 checkpoint。

完成标记为什么要最后写#

四个 rank 只有三个 shard 写完，目录已经存在但 checkpoint 不完整。恢复端应读取已提交 metadata 与完成状态，而非猜目录里有哪些文件。临时对象可保留用于诊断，但不能更新 latest 指针让新任务误用。

异步保存也需要稳定快照：训练继续修改 GPU 参数时，后台应写已 stage 的一致数据，不能拿变化中的 tensor 引用边读边存。CPU 内存和拷贝时间是缩短 GPU 暂停所付出的代价。

同步与异步保存#

同步 checkpoint 停止训练直到写完，简单但产生 pause。异步方案先把 GPU 状态 stage 到 CPU，再后台写存储，缩短 GPU 停顿。

代价是额外 CPU 内存、拷贝带宽和并发控制。训练继续修改参数时，后台必须写稳定快照，不能引用正在变化的 tensor。

保存频率怎么算#

checkpoint 间隔是成本权衡：

期望丢失工作 ≈ checkpoint interval / 2

间隔越短，存储和 pause 越多；越长，故障重算越多。还要考虑故障率、恢复时间、作业价值和存储带宽。

推理也需要持久化吗#

模型权重是推理的主要持久状态，在线请求通常不靠 GPU checkpoint 恢复。长时异步任务可在应用层保存输入、已生成位置、随机状态或业务进度，但跨引擎恢复 KV cache 更复杂，未必值得。

保存频率在正常开销与失败损失之间取舍#

每分钟都存可以减少故障回退，却可能让存储和 CPU staging 长期繁忙；每几小时存一次，正常更快，失败时损失更多计算。先测一次保存成本、故障频率和可接受回退，再设间隔，不照搬另一个集群的默认值。

恢复到不同 world size 还要求格式描述全局 tensor 与 shard 位置。实际演练加载、恢复数据位置并做小步验证，比“文件大小正确”更能证明备份可用。

Kubernetes 怎样看到 GPU

Kubernetes 默认认识 CPU、内存和普通设备，但不会自动发现 NVIDIA GPU。Device Plugin 在每个节点运行，向 kubelet 注册可用设备，并在 Pod 分配时返回设备、挂载和环境配置。

Extended Resource#

Pod 常这样请求 GPU：

resources:
  limits:
    nvidia.com/gpu: 1

GPU 这类扩展资源是整数资源，通常写在 limits。不能像 CPU 一样请求 0.25 张物理 GPU。共享需要额外机制，例如 MIG、time-slicing 或 MPS，它们的隔离语义不同。

Device Plugin 的职责#

  • 发现健康 GPU 或 MIG 设备；
  • 向 kubelet 注册资源名与数量；
  • 监控设备健康变化；
  • Allocate 时返回设备节点、CDI、mount 或环境；
  • 暴露配置的共享策略。

它不负责选择哪个节点。节点选择由 scheduler 根据资源和约束完成。

Scheduler 知道多少#

默认 scheduler 看到某节点有 8 个 nvidia.com/gpu，某 Pod 要 2 个。它不天然知道：

  • 两卡是否有 NVLink；
  • GPU 是哪个型号和显存；
  • 当前模型是否已在本地 cache；
  • 某卡上 KV cache 是否热；
  • 这 8 卡是否要作为一个 gang 同时给同一作业。

型号可通过 node labels 和 affinity 表达，拓扑与 gang 常需要插件或专用 scheduler。

资源数字怎样一步步变成容器可访问的设备#

插件发现设备并向 kubelet 报告，节点状态呈现扩展资源，scheduler 据此选择节点；到容器启动阶段，Allocate 返回访问设备需要的信息。节点选择与具体设备暴露是两段工作。Pod Pending 与容器里看不到 GPU，可能发生在不同环节。

默认资源计数只回答够不够张数，不回答这两张卡是否处于最佳互联域。型号标签、亲和与拓扑机制补这些条件，模型所需 KV 容量和热缓存则还在引擎层。

MIG、Time-slicing 与 MPS#

MIG#

把支持的 GPU 硬件切成隔离实例，拥有相对明确的计算和显存份额。适合稳定小负载，但 profile 固定，重配置有运维成本。

Time-slicing#

多个容器轮流使用同一 GPU，提高低利用任务的共享率，但通常不提供显存隔离保证。所有参与者的显存总需求仍受物理卡限制。

MPS#

允许多个 CUDA 进程更细粒度共享 GPU 执行资源，能改善并发，但隔离、兼容和故障域需要评估。

不要把三者统称“虚拟 GPU”。先写出隔离、性能和故障需求。

DaemonSet 与节点准备#

Device Plugin 通常以 DaemonSet 运行在 GPU 节点。完整节点还需要驱动、container runtime 配置、监控 exporter 和标签发现。GPU Operator 可以自动化部分生命周期，但自动化不会消除版本兼容矩阵。

应固定并验证：

  • driver 与 kernel；
  • CUDA runtime 与容器镜像；
  • Device Plugin 配置；
  • MIG 模式；
  • container toolkit；
  • NCCL 和网络插件。

共享份额不应被当成显存承诺#

time-slicing 可以让更多进程轮流使用设备，但它们的显存需求仍叠加在物理卡上。两个各需要 20 GiB 的任务不能因配置了两个共享槽，就自动在 24 GiB 卡上共存。调度数字与物理隔离语义必须分别理解。

MIG 给出硬件分区，profile 限定容量与计算；MPS 改善进程并发，却有自身兼容与故障边界。选择先看稳定容量、隔离和运行模型需求，再看可声明多少逻辑资源。

一个 Pod 能用多卡，不等于多节点#

单 Pod 请求 8 GPU 通常使用同一节点内设备。多节点训练通常是多个 Pod，每个 Pod 若干 GPU，再通过 rendezvous 组成 world。它需要 gang scheduling、稳定网络和 rank 配置。

排障顺序#

  1. nvidia-smi 在节点是否正常；
  2. Device Plugin Pod 是否健康；
  3. Node allocatable 是否出现 GPU 资源；
  4. Pod request/limit 和 selector 是否正确；
  5. scheduler event 为什么 Pending；
  6. 容器内设备与 driver library 是否可见；
  7. 应用是否选择正确 local rank。

把“Pod Pending”和“容器内 CUDA 错误”分开，它们属于调度与运行两个阶段。

用故障所在层选择检查命令#

主机看不到设备先查硬件与驱动；主机正常但容器看不到，查 runtime 和设备分配；节点没呈现资源，查 plugin 注册和健康；Pod 有卡而模型挂起，再查 rank、通信和软件。不要从所有症状一律重启模型开始。

多节点作业还需 rendezvous 和 group 配置，每个 Pod 得到本地 GPU 后才能共同组成 world。分配成功不是训练已就绪，健康检查应覆盖这个协作层。

批作业调度：为什么要一起开跑

一个 32 GPU 训练作业常由 4 个 Pod 组成，每个 Pod 要 8 GPU。如果只启动其中 3 个，进程会等待第 4 个 rank，已经占用的 24 GPU 也做不了有效训练。这就是 gang scheduling 要解决的问题。

普通逐 Pod 调度的问题#

假设集群有两个各需要 4 个 Pod 的作业，当前只有 6 个空槽。普通 scheduler 可能各放 3 个：

Job A: 3 / 4 已启动，等待
Job B: 3 / 4 已启动，等待
空槽: 0

两个作业都无法开始，却占满资源。批调度器需要以 PodGroup 或 Job 为整体判断是否满足最小成员数。

Gang Scheduling#

只有能同时满足 minMember 或资源下界时才让作业进入运行，否则先排队。这避免半启动死锁，但会产生资源碎片与等待，需要队列和 backfill 策略配合。

一起获得资源，不等于同一瞬间开始计算#

Gang 调度为作业满足协作资源下界，防止半组长期占卡；Pod 之后仍要拉镜像、准备数据和 rendezvous。某个成员启动慢，其余 rank 依旧等待。调度准入解决资源协作，训练 runtime 解决进程协作，两个阶段应分别观测。

minMember 也应符合真实角色：某些辅助任务不必和训练 worker 同时计算，不能机械把全部 Pod 数当作门槛。模板先定义哪些成员是开跑必要条件。

Volcano 的基本对象#

  • Job：批作业生命周期和任务角色；
  • PodGroup：一组需要协同调度的 Pod；
  • Queue：组织配额、权重和优先级；
  • Scheduler plugins：gang、priority、DRF、binpack 等策略；
  • Controllers：把 Job 期望状态调和成 Pod 与 PodGroup。

Volcano 不替代训练框架。它决定何时、在哪里给 Pod 资源，TorchTitan/Megatron 仍负责 rank 内计算与通信。

队列、公平与利用率#

FIFO#

容易理解，但一个超大作业可能阻塞后面能立即运行的小作业。

Priority#

高优作业先运行，需定义是否允许抢占以及被抢占作业如何恢复。

DRF#

Dominant Resource Fairness 根据用户最稀缺资源份额协调多资源公平。GPU 集群还可能区分型号和拓扑，单一计数并不够。

Binpack#

尽量把任务塞紧，空出完整节点给大 gang。它提高可调度性，但热点、功耗和故障域集中也要考虑。

Backfill#

大作业等待完整资源时，可让预计较短的小作业临时填空，但必须确保不会延误已承诺的大作业。需要运行时估计或最大时长合同，AI 训练时长往往不准，因此策略要保守。

公平、碎片和等待为什么不能同时简单最大化#

让小作业先跑，可能提高即时利用率，却推迟需要完整节点的大作业；为大作业保留槽位，又可能出现暂时空闲。Binpack 尝试留下整节点，DRF 关注资源份额，目标不同。空闲 GPU 不必然证明调度器无效，还要看将来承诺与拓扑要求。

Backfill 依赖时长估计。小任务超出预计，就可能侵占大作业开始窗口，因此需要最大运行时或可抢占合同。不能只按用户自报“很快”判断。

抢占不是 kill -9 就结束#

抢占前应给训练任务时间保存 checkpoint。需要协调：

  1. scheduler 发出终止或驱逐；
  2. 作业捕获信号并停止接收新 step；
  3. 完成一致 checkpoint；
  4. Pod 退出释放 GPU；
  5. 重新调度后从 checkpoint 恢复。

宽限期太短会丢进度，太长会拖慢高优作业。

拓扑约束#

多卡作业除了数量，还可能要求：

  • 同一节点或同一 NVSwitch 域；
  • 节点靠近同一网络 leaf；
  • GPU 型号一致；
  • 本地 NVMe cache 已有数据；
  • 避开同一故障域或维护节点。

约束越多，调度越难。平台应提供少量经过验证的资源模板，不让每个用户手写复杂 affinity。

抢占回收的是资源，损失的是已做计算#

宽限期应容纳一致 checkpoint，但高优作业也不能无限等待。平台先定义信号、保存时限和未完成处理，再测试训练框架是否响应。只发送终止信号不保证 optimizer、数据位置和模型状态已经落盘。

重新调度时沿用最近完整 checkpoint，并记录损失步骤与原因。这样才能比较优先级政策的真实成本，而非只统计资源多久被释放。

在线服务：网关、队列、副本与扩缩容

把模型进程放进 Deployment 只是起点。在线推理要同时处理流量波动、长短请求、模型版本、冷启动和 GPU 成本。

数据面组件#

Gateway#

负责认证、租户配额、输入限制、模型路由和协议。超长 prompt 应尽早拒绝，避免进入昂贵 GPU 队列后才失败。

Replica#

接收请求、tokenize、维护连接并和引擎通信。一个 replica 可能绑定一个 GPU worker group，不一定是一 Pod 一 GPU。

GPU Worker Group#

TP 或 PP 场景中，多进程共同服务一次请求。健康检查要关注整个 group，不能只看 API 进程端口存活。

Queue#

队列吸收短时突发，也制造等待。必须有长度、超时、优先级和拒绝策略。无限队列只会把过载伪装成高延迟。

路由的三个层次#

  1. 模型路由：请求需要哪个模型或 adapter；
  2. 副本路由：哪个副本有容量、cache 或匹配硬件；
  3. 引擎调度：本轮执行哪些序列和 token。

简单 round-robin 不知道各副本队列和请求长度。更智能路由可看正在运行 token、KV 压力或 prefix locality，但状态采集过慢也会误导。

两个副本排队条数相同，剩余工作也可能不同#

副本 A 等五个短 prompt，副本 B 等五篇长文，request count 相同却不是同样工作量。再看正在 decode 的输出长度和 KV 压力，才能估计接入新请求的代价。缓存亲和可能省 prefill，但把全部同前缀请求送到一个副本又会制造热点。

路由需要同时考虑可用容量与局部复用。采集状态有延迟，多个路由器也可能同时选择“最空”副本，应测试突发，不只测试稳定平均流量。

Autoscaling 看什么#

CPU Web 服务常按 CPU utilization 扩容，GPU 推理更适合组合：

  • waiting requests 或 queued tokens；
  • TTFT 分位数；
  • active sequences 与 KV utilization；
  • GPU memory/compute 指标；
  • 到达率和输出 token 速率；
  • 冷启动时间与最小副本。

GPU 利用率低可能是请求少，也可能是 CPU tokenizer、网络或同步瓶颈。单指标扩缩容容易振荡。

冷启动决定提前量#

新副本可能要下载几十到数百 GiB 权重、加载到 GPU、编译 kernel 和 warmup。若冷启动 8 分钟，等 SLO 已经崩了再扩容毫无帮助。

可采用：

  • 节点本地模型 cache；
  • 预热池或最小副本；
  • 分阶段 readiness；
  • 按流量周期预扩容；
  • 限制同时冷启数量，保护存储；
  • 小流量 canary 完成后再全量。

扩容来不及的时候，队列必须有上限#

新副本预热需要数分钟，当前过载请求不会因创建 Pod 立即得到服务。网关应按时限拒绝或降级，不能无限排队直至用户都超时。扩容依据到达率、排队 token 和冷启动趋势提前触发，最小副本承担低流量响应。

同时启动太多副本可能压垮模型存储，把八分钟冷启动变得更长。预热缓存与限并发下载属于扩容链的一部分，不能只看 replicas 数增加了多少。

KubeRay 与 Operator 模式#

KubeRay 用 CRD 表达 RayCluster、RayJob 和 RayService，operator 持续调和期望状态。它适合需要 Ray 分布式运行时的训练、数据或服务任务，但不是所有 vLLM 部署都必须引入 Ray。

选 operator 的理由应是生命周期和拓扑管理，而不是“AI 项目都应该上 Ray”。单节点模型服务用普通 Deployment 可能更简单。

滚动升级的 drain#

长生成请求不适合被立即杀掉。升级流程应：

  1. 新副本加载和 warmup；
  2. readiness 后接少量流量；
  3. 旧副本停止接新请求；
  4. 等活跃请求结束或达到 drain deadline；
  5. 保存必要状态并退出；
  6. 保留快速回滚能力。

需要明确客户端重试是否会重复计费或重复业务副作用。

容量规划的单位#

用 token 而不是 request 作为主要工作量单位。100 个“你好”与 100 个 100K prompt 完全不同。至少按 prompt/output 长度分桶，分别测 TTFT、TPOT 和 tokens/s。

缩容为什么要先停止接新请求#

若直接删除正在生成的副本，客户端会得到部分答案并可能重试。drain 先将它移出接入集合，等待活跃任务完成或达到 deadline，再释放 group。长请求仍需要明确最大等待和失败语义，不能让一条生成永久阻塞升级。

Worker group 多卡协作时，健康与 drain 应按整组判断。API 端口还活着不代表每个 rank 可计算，单个坏 rank 也可能拖住全部请求。

可观测性、SLO 与成本

可观测性的目标不是把每个 exporter 指标搬进 Dashboard，而是能从用户问题一路定位到队列、引擎、GPU、网络或存储。

用户层指标#

TTFT#

首 token 延迟，受网关、排队、tokenize 和 prefill 共同影响。交互式应用通常对它最敏感。

TPOT / ITL#

生成阶段每 token 时间或 token 间隔。看 p50、p95、p99 和时间序列，避免平均值掩盖卡顿。

E2E latency#

从请求开始到完成。它强烈受输出长度影响，应按输入输出 token 分桶。

成功率与取消率#

区分限流、队列超时、客户端取消、引擎错误、OOM 和内容策略拒绝。把所有非 200 合并会失去行动方向。

引擎层指标#

  • waiting/running/preempted requests；
  • input/output tokens/s；
  • KV cache utilization 与 block 分配失败；
  • prefix cache hit；
  • iteration time；
  • prefill/decode token 数；
  • scheduler time、model execution time、sampling time。

当 TTFT 上升时，先看 queue time 还是 prefill time。若 queue 上升但 GPU tokens/s 没变，容量已饱和；若 GPU 有大量空隙，瓶颈可能在 CPU 或通信。

同样 TTFT 上升，可能需要完全不同的行动#

队列时间升高、引擎吞吐稳定，可能已到容量上限，需扩容或限制输入；prefill 时间随长文变大，可能需要分桶或调 chunk；GPU 有空隙而 tokenizer 繁忙，则要修 CPU 路径。总延迟只显示症状，分段指标才提供行动依据。

ITL 也要按请求观察。系统平均输出速率很好，一部分长请求仍可能频繁被抢占，用户感到停顿。吞吐指标与体验指标分别保留，不用总体平均值替代所有租户的尾延迟。

GPU 与系统指标#

  • SM、tensor core、HBM 带宽；
  • 显存 allocated/reserved；
  • NVLink/PCIe/NIC 流量和错误；
  • 功耗、温度、频率、ECC/Xid；
  • CPU、NUMA、pinned memory；
  • 磁盘与对象存储吞吐；
  • Pod restart 和节点压力。

指标要与 run/request trace 关联，否则只能看到“卡忙”，不知道服务了哪种请求。

Little's Law#

稳定系统中：

L = λ × W
  • L：系统内平均请求数；
  • λ：平均到达率；
  • W：平均停留时间。

它帮助做量级检查：每秒到达 10 请求，平均停留 2 秒，系统内约有 20 个请求。若实际队列持续增长，输入率已超过完成率，扩容、限流或降级必须发生。

Little's Law 的时间范围要对应同一个系统#

若 L 统计引擎内活跃与等待请求，W 也应统计进入引擎到离开的时间，而不能拿完整网络耗时代入。到达率和平均值也需来自相近稳定窗口；队列持续增长时，不能用短时数据假装系统已有稳定工作点。

它适合量级核对，不自动给出所需 GPU 数。知道平均同时有二十条请求，还要了解它们的长度、prefill 与 decode 组成以及每副本可服务能力。

SLO 不能只有一个数字#

一个可操作的 SLO 示例：

  • 对 prompt 低于 2K、输出低于 512 的交互请求；
  • 月度 99.9% 成功；
  • p95 TTFT 小于 1.5 秒；
  • p95 TPOT 小于 60 ms；
  • 排除用户主动取消，但不排除服务端过载拒绝。

先定义流量类别和测量窗口，再谈目标。超长上下文应有独立 SLO 或异步产品形态。

成本指标#

只看每 GPU 小时价格无法比较系统。更有用：

cost per 1M input tokens
cost per 1M output tokens
cost per successful request class

还要计入闲置、冷启动、重复计算、模型下载、存储和跨区流量。低利用率副本可能是为了低 TTFT 保留的必要容量，不应简单视为浪费。

成本分母也应该代表有用结果#

过载重试与抢占重算都消耗 GPU，却没有增加同等数量的成功请求。只按总处理 token 计算成本，可能把重复工作当高效率。可以同时统计计费量、有效输出和成功请求类别，解释成本变化来自量化、利用率还是失败减少。

低流量保留预热副本会提高每 token 成本，却可能是低 TTFT 的必要代价。比较政策时固定 SLO 与流量，而不是让较慢系统凭关闭全部备用容量获得便宜结论。

Cardinality 警告#

不要把 request ID、完整 prompt、用户 ID 或任意模型参数放进 metrics label。高基数会拖垮监控系统，也可能泄露敏感数据。细粒度信息进入受控 trace/log，指标保留有限维度。

一张最小 Dashboard#

  1. 到达率、完成率、拒绝率；
  2. TTFT/TPOT/E2E 分位数；
  3. waiting/running 与 KV 使用；
  4. input/output tokens/s；
  5. GPU compute/memory/bandwidth；
  6. 错误按阶段分类；
  7. 副本数、冷启动和版本；
  8. 每百万 token 成本。

先保证每个图能回答一个运维问题，再增加面板。

故障恢复：把失败当作正常路径

GPU 会报错，节点会重启，网络会抖动，对象存储会限流。AI 作业昂贵且运行时间长，可靠性不能依赖“再跑一次试试”。

先划分故障域#

故障域 例子 典型处理
请求 非法输入、超长上下文 拒绝或降级，不重启服务
进程 OOM、Python 异常 失败请求或重启 worker
GPU Xid、ECC、掉卡 隔离设备，迁移工作负载
节点 驱动、内核、网络 cordon/drain，替换节点
rank group 某 rank hang 整组失败或弹性恢复
存储 checkpoint 半写 回退到最近完整版本
控制面 operator/scheduler 故障 leader election 与状态调和

把所有错误都交给 Pod restart，会造成无限 crash loop，也可能重复副作用。

首错比连锁错误重要#

分布式作业中，一个 rank OOM 后，其他 rank 常在 NCCL collective 超时。最终日志可能全是通信错误，但第一因是 OOM。

需要聚合所有 rank 的时间线，保留最早异常，并给 run 一个统一 ID。清理时不要让 teardown 错误覆盖首错。

最后报错的进程，不一定是首先失败的进程#

rank 2 在 forward 时 OOM，rank 0 等待 collective，稍后才记录超时。仅打开 rank 0 日志会误判网络；按统一运行与步骤标识对齐日志，能发现通信之前已有异常。时钟偏差也要考虑，事件依赖关系比孤立时间戳更可靠。

故障处置先止住扩散，再保留首错。清理阶段的异常不要覆盖最早记录；重启前保存必要 GPU、模型、batch 和拓扑信息，避免下一次只有同一句“超时”。

在线推理的重试#

模型生成通常可重试，但要区分：

  • 首 token 前失败：客户端可安全重试的概率较高；
  • 已流出部分文本：重试会产生不同续写或重复内容；
  • 调用外部工具：必须有业务幂等键；
  • 计费已发生：需定义去重和退款语义。

网关、客户端和服务端同时自动重试会形成放大风暴。每层必须限制次数、退避并传播 attempt 信息。

训练恢复#

可靠恢复路径：

  1. 检测 rank 或节点故障；
  2. 终止或重建一致 worker group；
  3. 找到最近完整 checkpoint；
  4. 验证配置、world size 和数据位置；
  5. reshard 并加载状态；
  6. 小步健康检查后恢复正式训练。

只验证 checkpoint 文件存在不够，应定期做恢复演练。未被恢复过的备份不能算可靠。

恢复的第一步，是找到完整且匹配的状态#

最近文件未必最近可用 checkpoint，须核验提交、metadata、代码与并行配置。恢复数据位置和 RNG 后，先做少量 step 检查 loss、通信和保存，再恢复大规模运行。若 world size 改变，确认格式与数据策略支持 reshard。

恢复演练还应模拟缺一个 shard、节点失联与旧版本状态。正常训练能保存文件，仅证明写路径部分可用，没有证明出事时读路径能重新建立一致 worker group。

Operator Reconciliation#

Kubernetes operator 不需要记住每个命令是否成功。它反复比较期望状态与实际状态，再采取动作。

期望 3 个副本，实际 2 个 -> 创建 1 个
期望版本 v2，实际仍有 v1 -> 继续滚动
资源已删除 -> 清理下属对象

这种模式适合控制面，但不适合直接重放业务副作用。控制器动作必须幂等，并通过 status 与 finalizer 表达进度和清理。

GPU 健康与隔离#

遇到持续 Xid/ECC/通信错误时，不要只重启容器。节点层应：

  • 记录 GPU UUID 和错误码；
  • 标记设备或节点不可调度；
  • 收集诊断后重置或维修；
  • 避免新作业反复落到坏卡；
  • 验证恢复后再解除隔离。

Device Plugin 可上报设备健康，但平台仍需要节点处置流程。

控制器可以重新创建 Pod，不能直接重放业务#

期望三副本实际两个，重复调和可以收敛；生成已经发送半段文字，再从头生成则不一定保持用户语义。外部工具写操作更需要幂等和结果查询。控制面可恢复组件，数据面还需请求状态与失败合同。

持续设备错误应隔离对应 GPU 或节点，否则新 Pod 反复落回同一坏卡。先收集诊断再解除隔离，将健康验证纳入恢复，而不是以容器重新变 Running 作为结束。

Runbook 最少包含#

  • 用户症状与告警条件；
  • 快速判断是请求、服务、GPU、网络还是存储；
  • 需要采集的日志、指标和拓扑；
  • 可安全执行的缓解动作；
  • 哪些动作会丢请求或训练进度；
  • 回滚和升级联系人；
  • 事后需要补的测试与容量修复。

“重启看看”只能是有边界的临时缓解，不是根因。

端到端：设计一个小型 AI 平台

假设团队有 8 台服务器，每台 8 张同型号 GPU，需要支持内部训练作业和一个在线聊天模型。不要一开始就搭建所有组件，先写工作负载合同。

第一步：定义负载#

在线推理：

  • 一个 7B 模型；
  • 95% prompt 小于 8K，少量到 32K；
  • 目标 p95 TTFT 小于 2 秒；
  • 流量白天高，夜间低；
  • 允许限流，不允许无限排队。

训练：

  • 8、16 或 32 GPU 作业；
  • 单次运行数小时到数天；
  • 可被低频抢占，但必须 checkpoint；
  • 数据和 checkpoint 在对象存储。

这一步没有框架名，但决定后面的选择。

六十四张卡，不等于六十四张随时可借的卡#

在线副本需要长期保留与预热，训练 gang 需要连续拓扑，维护节点与故障余量也会减少可用池。先决定在线最低保障、训练可借范围和回收时间，再估算队列容量。否则白天扩推理时，所有卡可能已被不可中断的大作业占住。

少量 32K 请求不能只藏在平均长度里，它们会占更多 KV 并影响其他请求。可以设独立限额或流量类别，明确长上下文如何获得容量，而不是任由它们与短交互争抢。

第二步：节点层#

每个 GPU 节点固定 driver、container toolkit、Device Plugin 和监控 exporter。用标签描述 GPU 型号、互联域和本地 cache 状态。先做节点验收：单卡计算、节点内 NCCL、跨节点 NCCL、存储读取与故障上报。

第三步：训练队列#

用 Volcano 或等价批调度能力表达 PodGroup、队列和优先级。提供少量模板：

  • 8 GPU 单节点；
  • 16 GPU 双节点；
  • 32 GPU 四节点。

模板绑定拓扑、镜像、网络和 checkpoint 约定，减少用户自行组合错误。

第四步：推理服务#

7B 模型若单卡可容纳，先用单卡副本做数据并行扩容，避免无必要 TP。每个副本使用连续批处理和分页 KV。网关按模型与租户路由，限制 prompt 和 max tokens。

容量不足时按顺序检查：

  1. 权重与 KV 是否有合理余量；
  2. 当前瓶颈是 queue、prefill 还是 decode；
  3. 增加单卡副本能否线性提高总吞吐；
  4. 模型确实放不下时再引入 TP；
  5. 跨节点 TP 是否值得通信成本。

用两种流量找到第一版副本工作点#

先测短交互类，再测长 prompt 类，各自逐步增加到达率，记录 TTFT、ITL、KV 与等待。将满足目标的区间当作每副本工作点，而不是把最大吞吐值直接用于承诺。再混合两类，验证长请求没有破坏短请求目标。

算容量时保留一个副本或节点故障的余量，并将冷启动时间放进扩容计划。离线显存计算只排除明显装不下的方案，真正服务能力需目标硬件和模型验证。

第五步：扩缩容#

最小副本保证低流量 TTFT。扩容信号使用 queued tokens、TTFT 和活跃序列，GPU 利用率只作辅助。模型 cache 预热到候选节点，限制同时冷启动数。

缩容先 drain，不接新请求，等待当前生成完成或 deadline。夜间可降低副本，但不能让第一个请求承担完整模型下载时间。

第六步：可观测与成本#

每个请求记录模型版本、输入输出 token、queue/prefill/decode 时间和结果类别。每个训练 run 记录代码、数据、并行配置、GPU 拓扑和 checkpoint。

周报只需要回答：

  • SLO 是否达成；
  • 哪类请求或作业占最多 GPU 时间；
  • 排队来自容量还是调度碎片；
  • 每百万 token 成本如何变化；
  • 最大故障损失了多少训练进度。

用本地实验室算第一版容量#

python3 examples/infra_lab.py memory \
  --parameters 7 \
  --weight-bits 16 \
  --context 8192 \
  --concurrent-requests 8

结果显示权重和 KV 的理论小计，再预留运行时空间。它不能替代 vLLM benchmark，但能快速发现“配置在容量上根本不可能”。

调度模拟：

python3 examples/infra_lab.py simulate

修改源码中的 token budget 和 block 数，观察 TTFT 与完成时间。真实引擎更复杂，但仍围绕预算、KV 和公平性做选择。

上线顺序#

  1. 单卡离线正确性；
  2. 单卡固定长度 benchmark；
  3. 单卡真实长度分布；
  4. 单节点多副本或 TP；
  5. 故障注入和恢复；
  6. 小流量在线；
  7. 扩缩容与滚动升级；
  8. 多节点和批调度。

每一步留下基线和回滚点。一次性把模型、量化、并行、scheduler 和集群全部换掉，出了问题就无法定位。

最小平台也要演练一条完整失败路径#

暂停一个训练 worker，确认整组停止、完整 checkpoint 被选中、数据位置恢复；移除一个推理副本，确认路由停止接入、用户收到明确结果且其他副本未过载。分别记录回退计算量与恢复时间。

若这些路径没跑过，增加更多 operator 只会增加未知项。先让少数模板的启动、保存、恢复与升级可靠，再扩模型和并行配置，平台的约束才能被团队真正理解。

最终架构原则#

  • 字节账本先于采购；
  • workload 先于框架；
  • 单卡基线先于多卡；
  • 拓扑先于并行度；
  • 队列时间先于 GPU 利用率；
  • 恢复演练先于“高可用”声明；
  • 简单可测的系统优于组件齐全的系统。
