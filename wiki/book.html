读前说明：不懂 CUDA 也能开始

一座档案馆准备开放两项服务：白天让读者询问馆藏资料，夜间用新增的校对文本训练模型。负责系统的工程师发现，模型文件能放进 GPU，服务却仍会排队；夜间作业拥有足够卡数，有时又停在通信步骤。这两件事会贯穿本书。

我们关心的对象有明确的尺寸和生命周期：一份权重在设备上驻留，一段上下文逐渐增加，一组梯度等待交换，一份检查点尚未写完。把这些对象和等待它们的进程对应起来，才能解释容量、速度与故障。

你不需要先会什么#

可以从普通 Python 程序和 HTTP 服务的经验出发。遇到 tensor 时，我们会数元素；遇到 collective 时，我们会写出各个参与者拿到什么；遇到 Kubernetes 时，我们只追踪一个资源申请如何落实到设备。无需先完成 CUDA 或分布式系统课程。

学习过程中也不用购买 GPU。纸上算例可以发现单位错误和资源约束，标准库实验可以检验调度规则。它们无法测出显存带宽、网络拥塞或真实模型的答案质量，后面会把这些限制写在对应实验旁边。

沿字节和等待连续读下去#

档案问答先把扫描材料转换成输入 token，模型读取输入，保存后续生成所需的状态，再逐步产出文字。每多接待一位读者，就可能多一份同时存活的 KV；每换一个并行方案，就可能改变这些状态存放在哪个 rank。

夜间训练还会保留激活、梯度和优化器状态。读到训练章节时，请继续追问同一个具体问题：这块内存要活到何时，哪个计算会消费它？到了集群章节，再给问题加上位置：它依赖的 GPU、网络和存储现在是否可用？

数字均带假设。书中的虚构硬件和负载只为便于核算，不代表档案馆真实部署，也不构成产品性能承诺。

本书怎么验证#

七个本地仓库承担不同的核对职责。阅读正文无需先打开它们；需要确认实现时，再按附录中的入口查找。

三条阅读路线#

第一次接触 AI Infra#

从请求经过的组件开始，读完单卡的字节账，再进入多卡通信。每章完成一个小动作：画一段时间线、算一份 tensor，或写出某个 rank 的输入输出。暂时跳过源码目录也不影响主线。

只想部署推理服务#

先定位首字等待和生成速度，再读显存、分页与连续批处理。随后补上加载、多卡和服务集群。若模型必须跨卡运行，通信章节也属于上线前知识，不能只调 HTTP 并发。

正在做训练平台#

从状态占用与训练循环入手，把数据位置、同步点和保存边界标到一步训练上。再读分片、作业队列和恢复。能启动一个作业只是起点，还需证明它在节点失败后能继续使用正确的数据与优化器状态。

图怎么看#

新版图解分别采用时间泳道、内存格子、输入输出矩阵和恢复状态机，不把所有问题都画成串联方框。图内的数量仅对应正文算例。

读图时分清三类连接：数据被搬到另一个位置，任务被安排执行，状态被持久保存。它们对延迟和恢复的影响不同。图中两条路径汇合，也不自动表示两边处于同一个事务。

示例的边界#

离线实验入口仍是：

python3 examples/infra_lab.py memory --parameters 3 --context 6144
python3 examples/infra_lab.py simulate
python3 examples/infra_lab.py check

计算器采用 GiB，除法分母是 2**30。模拟器的时间单位是调度轮，没有隐含“每轮等于几毫秒”。它使用人为给定的请求，演示预算、入队和释放，不复刻 vLLM 或任何 GPU。

如果你把公式用于实际采购，先换成目标模型配置，再补测工作区峰值、加载峰值与余量。显示很多小数位不会让缺失的开销自动出现。

01

一条请求穿过哪些系统

读者请求“比较两份航海日志里的气压记录”。系统已经接受连接，屏幕却迟迟没有文字。这个现象至少涉及接入、分词、引擎等待、模型计算与回传，不能仅凭客户端计时判断是哪一层忙。

数据面：请求真正走过的路#

1. 网关#

入口为读者确认身份，检查可用模型与额度，并把请求送到适当副本。限流应同时考虑请求条数和输入大小。十个短问题与十份长篇档案的工作量差异很大，仅按连接数限流会掩盖后者的压力。

2. API 服务#

服务将角色消息套入目标模型的聊天模板，再分词形成整数序列。模板版本也会改变 token 数，因此预估长度和最终入队长度可能不同。若 CPU 分词已经积压，增加 GPU 的调度预算并不能消除这段等待。

3. 引擎调度器#

一份输入只有同时满足本轮计算预算、序列上限和 KV 空间条件，才有机会被选中。vLLM 的 EngineCore 驱动引擎循环，Scheduler 决定工作分配，KVCacheManager 管理相关内存资源。它们操作的是请求状态，不负责给 Kubernetes 分配节点。

4. GPU worker#

worker 根据调度结果执行模型。采用张量并行时，多张卡共同完成一个逻辑步骤；不能把它理解成每张卡独立回答一位读者。某个参与者尚未到达通信点，其他参与者即使计算完成也可能继续等待。

5. 流式回传#

采样后的 token 经文本解码形成增量，经应用协议返回浏览器。一个 token 可能只构成半个可显示片段，代理也可能合并若干增量发送。应分别记录设备生成时间和客户端收到时间，检查缓冲造成的间隙。

请求进入副本，不等于已经得到 GPU 时间#

假设教学轨迹中，请求在 0 ms 被入口接受，18 ms 分词完成，直到 96 ms 才进入第一次模型执行。18 到 96 ms 的 78 ms 属于引擎排队。服务的存活检查全部正常，也不会使这段等待消失。

若设备在 140 ms 已生成首个可用片段，而浏览器到 200 ms 才显示，另有 60 ms 位于设备之后。应检查文本拼接、应用刷新和反向代理缓冲，不能把这 60 ms 再记为 prefill。

控制面：谁让服务存在#

副本运行前，需要节点、设备、模型文件和网络服务。控制器根据期望状态创建或修复这些资源，调度器挑选合适节点，Device Plugin 协助 kubelet 暴露设备。准备过程发生在请求热路径之外，却决定副本是否真正可接流量。

例如新副本已经处于 Running，但仍在读取权重。若此时过早宣布 Ready，入口会把读者送入一条尚不能执行的路径。反过来，存活探针若把正常长初始化误认为死锁，会使加载永远无法结束。

两个调度器#

决策问题 执行者 可观察结果
哪个节点承载这组进程 集群调度层 Pod 被绑定或继续 Pending
这轮给哪份输入多少计算份额 引擎调度层 请求被执行、暂停或留在队列

前者面对 GPU 数量、标签与拓扑，后者面对 token 和 KV 块。两个等待队列应分别测量；把它们统称“服务排队”会使扩容和调参混在一起。

两个调度层可以分别健康，整体仍然慢#

档案馆有两个空闲节点，但引擎副本数固定，空闲卡不会自动参加现有副本的计算。另一种情况是全部副本都已就绪，却被长上下文占据 KV，入口仍不断积累请求。第一种需要改变服务容量，第二种要检查负载和引擎资源边界。

引擎的一轮选择能很快改变；创建新副本还要等待设备与权重。扩容应基于未来一段时间的压力，并配合有界排队，不能把控制面的动作当作即时救援。

第一个排障方法：画时间线#

为同一请求 ID 记录入口接受、分词完成、首次被调度、首个生成片段、最后生成片段和客户端结束。计算相邻时间点的差，而非把每层各报的“总耗时”相加，后者可能重复计算重叠区间。

上例中的 78 ms 排队可以与活跃 KV、等待 token 一起查看。若分词耗时增长而引擎空闲，则应回到 CPU 和输入处理链。时间线让优化动作对应到一段可验证的等待。

离线与训练路径有什么不同#

夜间批量整理档案时，任务可以按长度分桶，延后短任务的交付换取更好的设备复用。训练则用数据 batch 驱动，不逐条等待读者提问，还会进行反向计算、参数更新和状态保存。它们共享设备，却不应沿用同一组用户延迟目标。

训练为什么没有网关，仍然会等待#

如果校对数据尚未从对象存储读出，GPU 会等待下一批；若一个 rank 读盘较慢，同步训练中的其他 rank 还可能在 collective 处等它。应把数据可用、计算开始和同步结束画到各 rank 的泳道上，才能区分慢网络和慢输入。

源码入口#

从 vllm/v1/engine/core.py 追请求进入引擎，再看 vllm/v1/core/sched/scheduler.py 如何产生本轮工作。涉及块的申请和释放时转到 vllm/v1/core/kv_cache_manager.py。准备设备的代码则在 k8s-device-plugin/internal/plugin/，服务调和可从 kuberay/ray-operator/ 查起。读这些路径时，以同一对象的创建、使用和释放串联调用关系。

02

最少模型知识：token、tensor 与参数

把一批档案送进模型前，需要回答两个量化问题：要处理多少位置，每个位置存多少数。模型术语在容量规划中最终都要落到这两个数量上。

Token 不是字，也不是固定长度#

同样一份带旧地名、数字和标点的航海日志，不同 tokenizer 可能给出不同数量的 ID。按字符数设置输入限额只是入口保护，实际计算与计费应使用目标 tokenizer 的结果，包括聊天模板带来的额外位置。

输入 token 影响读取工作，输出 token 影响生成轮数，已经保留的位置影响 KV 占用。容量记录至少应把输入与输出分列；“总长相同”的两种请求不一定有相同延迟。

Tensor 是带形状的数字数组#

[B, S, H] 可以表示 B 份序列、每份 S 个位置、每位置 H 个隐藏数值。取 [3, 512, 2048]，共有 3,145,728 个元素。这里的三个维度描述一份中间结果，不等于模型拥有这些参数。

形状先决定元素数，精度再决定字节数#

这份结果若使用 BF16，每元素 2 bytes，共 6,291,456 bytes，即 6 MiB；若改存 FP32，则为 12 MiB。换精度没有改变形状，增加序列长度才会改变位置数。

真实执行还可能存在转置、打包或临时副本。用形状乘元素字节数可求逻辑内容下界，要估峰值，还需确认这些副本是否同时活着，不能只看最后留下的那份结果。

参数是模型长期保存的 tensor#

假设教学模型含 30 亿参数，按 16 位保存，权重下界为 3e9 * 2 / 2**30，约 5.59 GiB。请求变短并不会让这份权重同步缩小。

检查模型配置和权重文件比只看“3B”标签可靠。嵌入是否共享、量化元数据和保留高精度的层都会改变实际加载大小。文件在磁盘上的尺寸也不能直接替代运行时峰值。

数据类型决定字节和数值范围#

表示 内容空间下界 规划时还要问什么
FP32 4 bytes / 数 哪些累加与状态需要保留它
BF16、FP16 2 bytes / 数 指数范围和舍入是否适合任务
FP8 1 byte / 数 是否有匹配硬件、缩放与 kernel
INT8 1 byte / 数 缩放粒度与校准如何设置
INT4 半 byte / 数 如何打包，额外元数据多大

半 byte 是逻辑记账方式，设备不必逐个半字节访问。低比特格式往往成组存储，并带尺度信息，实际字节数会高于这个下界。

参数量与请求长度分别让哪部分变大#

同一个模型回答一句目录查询与处理整卷日志，权重不变，输入处理和历史状态不同。把模型换大则首先改变权重与每步计算；提高同时在线人数则增加并存的请求状态。定位显存增长时应记录究竟是哪一个维度发生了变化。

BF16 与 FP16 的存储尺寸相等，但可表达的范围不同。容量相同并不能推导出数值行为相同，精度切换后仍需检查溢出、异常值和任务输出。

层、头和隐藏维度#

注意力会在多层保存 key 和 value。估算缓存时要知道层数、KV head 数以及每头维度。教学模型若有 24 层、4 个 KV head、每头 96 维，不能因为 query head 更多就把 KV head 也填成 query head 数。

这些值通常可从模型 config 查到。滑动窗口、混合注意力或其他架构可能使缓存规则不同，后文的公式会明确限定为常规全注意力情形。

Batch 有两种含义#

训练的一次更新可能累积多个 micro-batch，并由多个数据并行副本共同提供样本。在线推理的一个调度批次，则可能同时包含新输入块和已经开始生成的序列。

记录“batch 为 12”时，补写单位与范围：12 份样本、12 个活跃序列，还是 12 个 token？是每个数据副本、每卡，还是整个更新？缺少这些说明就无法复算资源需求。

FLOP 与 byte 是两本账#

一次矩阵计算既要执行运算，也要从存储取数。两种实现即使算出同一结果，也可能有不同的数据搬运量；同一个 kernel 在不同 batch 下又可能有不同复用。运算量除以搬运字节量得到算术强度，下一章据此判断可能的限制。

在线 batch 不应被理解为整齐的矩形#

三位读者当前各保留 70、190 和 510 个位置。引擎可以用变长打包和块表描述它们，不必为每人都分配一个长度 510 的完整矩形。数学符号 [B,S,H] 帮我们理解维度，不能据此断言实际分配一定包含填充后的全部槽位。

一个练习#

运行同一组输入，只改变权重精度：

python3 examples/infra_lab.py memory --parameters 3 --weight-bits 16 --context 6144
python3 examples/infra_lab.py memory --parameters 3 --weight-bits 8 --context 6144

权重下界应减半，KV 项应保持不变。再把上下文改为 12288，检查 KV 项加倍而权重不变。若你的结果不满足这两点，先查参数是否被误用，不急着解释硬件行为。

03

GPU 不是更快的 CPU

档案预处理程序逐文件解析复杂格式，模型计算却对大批规则数组执行相似运算。这两部分适合的处理器不同。把 Python 文件循环放到拥有 GPU 的机器上，不会使它自动变成并行设备计算。

一张卡里的四个角色#

计算单元#

执行单元擅长让许多数据使用相似指令，tensor core 对支持的矩阵运算提供专门路径。型号表中的峰值必须连同精度、稀疏性和运算口径阅读。模型未使用对应路径时，这个峰值不会转化为实际吞吐。

HBM 或显存#

设备要从这里读取权重与状态。容量是能同时保留多少内容，带宽是能多快搬出内容，两者不能互换。扩大容量可以放入更多上下文，却不保证每一步读历史状态的耗时更少。

Cache 与 shared memory#

较近的存储适合保存一小块反复使用的数据。kernel 通过分块避免同一内容反复往返大显存。FlashAttention 的 IO 优化可从这个角度理解：调整精确注意力的计算组织，减少中间结果的慢层级读写，而非用近似答案代替原问题。

互联#

主机和设备之间、设备彼此之间以及节点之间各有传输路径。请求跨越哪一条路径，要看实际进程和数据放置。机器有很多 GPU，并不保证任意两张卡间都拥有同样的带宽和延迟。

Roofline：先判断是哪种上限#

用目标精度的计算上限，与带宽乘算术强度所得上限比较，取较小者。算术强度是运算次数除以所选择存储层级的搬运字节数；分母口径必须一致。

这给出理想天花板，实际还会损失在启动、依赖、访存模式和并行度上。远低于两条上限时，不应立即宣布是“计算受限”，可能是数据或任务根本没持续送到设备。

用一个假设硬件手算 Roofline#

设有效带宽为 0.8 TB/s，计算平台为 64 TFLOP/s。强度为 20 FLOP/byte 时，带宽给出的上限为 16 TFLOP/s；强度为 160 时给出 128 TFLOP/s，但最终仍被 64 限制。转折点是 80 FLOP/byte。

图和数字不对应真实产品。把第一个任务换到仅提高计算峰值的设备上，其理想上限仍可能是 16；如果减少一半搬运而不增加运算，强度翻倍，才可能抬高这段上限。

为什么 Decode 容易带宽受限#

生成阶段常常只推进少量新位置，却需要访问大量模型权重和已有 KV。小 batch 下，一次权重读取服务的 token 少，复用不足，运算强度可能偏低。扩大活跃集合能够提高复用，但同时占用更多缓存和执行时间。

实际结果依赖架构与长度。长上下文的注意力读取也会变重，不能把所有 decode 都简化成只读权重。应在目标长度分布上查看 kernel 与内存流量。

CUDA 是什么层#

CUDA 提供设备编程、执行和库支持，上层框架借它提交 GPU 工作。主机通常把任务放入 stream 后继续运行，依赖关系决定哪些任务可重叠。第一次执行还可能有初始化、编译和图捕获，不能混入稳定阶段的计时。

allocator 保留的内存以及图执行需要的地址稳定性，同样属于这一运行环境。只观察 Python 变量是否消失，无法判断设备是否已完成工作或驱动是否收回空间。

异步提交为什么容易测出虚假的加速#

假设主机提交耗时 30 微秒，设备计算耗时 2 毫秒。只测调用返回可能得到接近 30 微秒，漏掉真正工作。单次设备耗时可用适当的 CUDA 事件测量，端到端延迟则需要在正确边界等待完成。

每个算子后强制同步虽然容易计时，却会破坏原来的重叠。比较方案前明确是在测单算子、完整步骤还是持续吞吐，并让两边采用同一口径。

看哪些硬件指标#

把指标配成问题一起看。设备占用高时，看单位时间完成的有效 token；HBM 流量高时，看是否重复读取或重算；设备空隙多时，看 CPU 供给与同步；频率下降时，检查功率、温度和硬件限制。跨卡步骤变慢，还要测必要互联的流量与等待。

显存占用只能描述容量，不能回答内存控制器是否繁忙。单一 utilization 曲线也无法分清有用矩阵运算和等待相关的 kernel。

第一条性能纪律#

为档案问答建一份固定负载说明：输入长度分位数、输出上限、请求到达方式、模型与精度、软件版本、卡型和拓扑。每次只改变有明确假设的一项，并同时保存延迟与吞吐结果。

卡一直忙，为什么请求还很慢#

如果某方案通过频繁抢占和重算让设备始终忙碌，读者仍可能迟迟等不到答案。比较完成请求数、有效输出 token、重算量与排队时间，才能判断利用率提高是否有收益。忙碌时间是资源消耗，交付结果才是工作产出。

来源入口#

硬件层级与计时限制可查 NVIDIA 的 GPU Performance Background、CUDA C++ Best Practices Guide 和 PyTorch CUDA semantics。Roofline 原始技术报告解释上界模型；FlashAttention 论文可用于核对注意力中的 IO 分块推导。使用资料中的数字前，先确认其设备、精度和实验条件。

04

显存账本：模型到底占多少

馆藏问答在加载时只用掉部分显存，几位读者提交长卷宗后却发生 OOM。模型没有变大，增长的是同时存活的请求状态。处理这类问题，需要将常驻内容、随负载变化的内容和执行峰值分开记账。

推理账本#

权重#

参数个数乘存储位数再除以 8，得到权重内容的字节下界。30 亿参数按 16 位约占 5.59 GiB；压成 8 位约为 2.79 GiB，尚未加入量化尺度、对齐和保持高精度的部分。

KV Cache#

每条仍在运行的序列都可能增加历史 key/value。并发数和每条序列的已缓存长度要一起统计。两种流量拥有相同请求数，也可能由于长度差异产生完全不同的缓存压力。

激活与 workspace#

模型执行会产生当前批次的中间结果，kernel 和通信还需要工作缓冲。这些空间未必长期驻留，却可能决定某一次 forward 能否成功。增加每轮 token 预算会改变这部分峰值。

运行时保留#

设备上下文、分配器缓存和图执行内存池也占空间。有些保留可以复用，有些属于不能轻易让出的运行条件。设备总容量减去权重，并不等于允许 KV 用满的容量。

训练账本#

反向计算要使用激活，更新参数要使用梯度与优化器状态。一个用于说明量级的混合精度 Adam 方案为：低精度参数 2 bytes、梯度 2 bytes、主参数 4 bytes、两份 FP32 moment 共 8 bytes，即每参数 16 bytes。

30 亿参数据此需要约 44.70 GiB，还未加入激活和临时空间。具体实现可能没有独立主参数，梯度精度也可能不同，应按真实 tensor 清点，不能把 16 bytes 当作训练通用常数。

权重放得下，不代表服务容量足够#

取一张假设的 16 GiB 卡，扣除 5.59 GiB 权重，再预留 2 GiB 给运行时与峰值，约剩 8.41 GiB。这个余额只是 KV 规划的起点，不是已经证明能服务任意长请求。

如果改做训练，仅长期状态的教学估算就超出这张卡。此时降低在线并发无法解决优化器占用；需要重新考虑训练状态分片、精度或模型规模。

激活为什么难用一个倍数表达#

样本数量、序列长度、层宽以及算子保存哪些结果都会改变激活。注意力实现若避免物化某些大矩阵，峰值也会变化，所以“参数显存乘某倍数”无法覆盖所有形状。

激活检查点只留部分边界，反向时重新执行部分 forward。它减少的是被舍弃的中间结果，并不自动减少参数、梯度或 Adam moment。采用前应测显存下降和重算增加的时间。

已分配、已保留与可用#

在 PyTorch 中，allocated 描述活跃 tensor 占用，reserved 描述分配器保留的空间。驱动所见可用容量还受其他进程与运行时影响。三者不是同一层的计数，比较前要统一时间点。

OOM 信息中的失败分配大小也值得保留：无法再申请一个大连续工作区，与累计小块持续增长，排查方向不同。必要时采集峰值和内存快照，而非只在故障后截取一行 nvidia-smi。

释放 tensor 后，reserved 为什么没有立刻下降#

用完的块可能留在进程分配器里，供下一轮使用。allocated 下降而 reserved 稳定通常符合缓存设计。若列表、闭包或结果缓存仍引用 tensor，它根本没有释放，清理空闲缓存也不能回收这部分。

可用三个时点做实验：刚加载后、第一轮长输入后、请求结束后。如果结束后活跃占用持续递增，就检查请求资源和引用生命周期；若只在大输入时出现峰值，应先看当前执行形状。

OOM 排查顺序#

先保存失败请求的实际 token 数、并发、精度和运行配置。再区分权重读取转换时失败、首次执行失败，还是多轮运行后失败。沿对应阶段查找同时存活的对象，确认它是否按预期释放。

找到增长项后再选动作：权重可考虑量化或分片，KV 可限制总活跃长度，激活可减每轮工作量或重算。只调显存利用比例可能推迟报错，却不能证明增长已受控。

用计算器建立量级感#

python3 examples/infra_lab.py memory \
  --parameters 3 --weight-bits 16 \
  --layers 24 --kv-heads 4 --head-dim 96 \
  --context 6144 --concurrent-requests 6

每 token 的常规 KV 下界为 36 KiB。六条请求若都缓存到 6144 个位置，共 36,864 个位置，对应 1.265625 GiB。这是显式最大长度组合，不含分页尾块、工作区或前缀共享。

预算要留给峰值，而不只是平均#

平均读者只提交几百 token，并不能排除几份长卷宗同时到达。容量测试应包含这种组合，并检查运行中生成使长度继续增长的情形。用平均上下文乘平均并发只能描述某个平均状态，无法证明峰值安全。

一条安全规则#

计算书面预算时，列出未建模的项；做上线验收时，测量同一软件版本上的加载、长输入、突发和退出后的峰值。只有预测与这些观测能相互解释，才继续提高负载。

05

推理的两幕：Prefill 与 Decode

读者给出一份日志，要求生成一句日期摘要；另一位只给一个题目，却要生成长篇目录。它们分别把工作集中在读取和续写阶段，不能只用总 token 数判断执行体验。

Prefill 做什么#

模型先处理已有输入，在各层形成后续生成需要的 K/V。输入的多个位置可以组织成较大的矩阵工作，通常具有较多并行机会。因果掩码仍然约束每个位置可读哪些前文，批量处理并未允许它看到未来答案。

首字时间还包括接入、分词和调度等待。若长卷宗的 prefill 实际只占首字等待的一小部分，继续优化这一段会遇到明显收益上限，应先按请求时间线拆解。

Decode 做什么#

后续新位置依赖先前已经选出的 token。每轮用新位置的输入和已有缓存完成模型计算，再采样决定下一个 token，直到停止标记或长度上限。多个请求可以一起推进，但单条序列的生成依赖仍在。

相邻输出间隔可以用 ITL 的分布描述，单请求平均生成时间可用 TPOT 描述。若输出超过一个 token，常见计算口径为 (最后 token 时间 - 首 token 时间) / (输出数 - 1)，具体看测量工具定义。短输出不适合盲目比较这个平均数。

读取长题目和续写长答案，是两种压力#

设教学负载甲有 6000 输入、80 输出，乙有 300 输入、1800 输出。甲可能在开口前花较多时间；乙可能很快开始，却连续占据许多生成轮次。相同总耗时也可能呈现完全不同的用户感受。

把请求按输入和输出二维分桶，能看出首字与持续生成分别受谁影响。仅按总长度分桶会把这两种负载混在一起。

为什么不能只优化一个阶段#

正在生成的读者希望下一片段准时到达，新来的读者希望尽快开口。若本轮给新长输入过多计算，已有生成可能被推迟；若一直照顾生成，新输入会在队列里等待。

产品需要分别指定首字和生成间隔目标，并考虑长输入不能永久挨饿。调度器只能在这些目标和资源边界之间取舍，无法通过单个 batch 参数同时消除所有等待。

Chunked Prefill#

引擎可把长输入分几轮处理，让尚未完成的输入工作与生成共同使用每轮 token 预算。这样能控制单轮工作量，代价是更多调度边界以及长请求跨轮驻留。

例如 max_num_batched_tokens 影响每轮可处理的位置数，而不直接给出这一轮耗时。相同 token 数放在不同模型和形状下，执行时间仍会变化，需要测量而不能把预算当作毫秒限额。

切小 prefill 怎样帮助正在生成的用户#

假设本轮有 6 条生成序列，各需推进 1 个位置，另有 960 个输入位置待处理。预算设为 102 时，先为生成分配 6，再给输入 96。输入大约需要十次这样的份额才能读完，期间生成有机会持续推进。

这只是调度账，没有声称一轮固定多长。若极小分块引入很多管理和执行开销，总吞吐可能下降；应测首字改善是否值得这些成本。

Prefill/Decode 分离#

分离部署把输入处理和持续生成安排到不同工作组，完成输入处理后再交接历史状态。两边可以采用不同并发和扩缩策略，但也引入状态传输、配对路由和交接失败的处理。

采用前应证明混合执行确实造成干扰，并测量交接后的排队。负载较低时，两组分别空闲可能比一个共享池更浪费，新增链路也会增加运维复杂度。

一个简单类比#

整理档案时，先为一份日志建立索引，再根据索引逐条写注释，类似两类不同形状的工作。这个类比只说明先读取、再依赖历史推进，不能用来推导注意力运算或真实内存占用。

分离前先算 KV 交接的成本#

沿本书模型，6144 个位置、每位置 36 KiB，交接约为 216 MiB 的逻辑 KV。若可用链路吞吐仅 3 GiB/s，忽略其他开销的传输下界也约为 70 毫秒。传几个 token ID 无法替代这份历史状态。

还需加入源端整理、目标端分配、网络竞争和失败清理。只有独立调度节省的等待与计算超过这些代价，分离才可能带来净收益。

观测建议#

给每条请求保留输入长度、输出长度、入队等待、输入阶段执行时间和生成间隔。标注是否分块、是否命中前缀缓存以及是否发生状态交接。这样才能区分“读取变快”“不再排队”和“后续写得更平滑”三种不同改善。

06

KV Cache：上下文为什么越来越贵

模型在续写一份日志时，还要参考之前的位置。为避免每次从头建立全部历史状态，引擎保留注意力层的 key 和 value。缓存有收益，也有随长度与并发增长的空间成本。

先记公式#

对使用常规全注意力、每层配置相同的模型，可以从这条下界开始：

每位置 KV 字节 = 2 × 层数 × KV头数 × 头维度 × 元素字节

本书教学配置为 24 层、4 个 KV head、每头 96 维、每元素 2 bytes，得到 36,864 bytes，即 36 KiB / 位置。6144 个位置对应 216 MiB。公式中的 2 计入 K 和 V，不能在下一步又重复乘一次。

混合注意力、滑动窗口、不同缓存精度以及并行切分需要分别处理。不能把模型 hidden size 无条件填入 KV head 维度的乘积。

Active tokens 是什么#

这里关注当前仍需保留的历史位置总数。它与输入速率不同，也不等于最大允许长度乘全部用户数。序列持续生成会增大历史，完成、取消或抢占则可能释放或改变其缓存归属。

前缀共享时，多条逻辑序列可能引用相同物理块。因此逻辑位置计数适合说明工作长度，物理块计数更接近实际占用；监控中应写清二者口径。

容量统计是一张随时间变化的照片#

在某个时点，三条请求各缓存 900、1500 和 2700 个位置，共 5100 个，逻辑 KV 约 179.30 MiB。即使三条的允许上限都为 6144，也没有理由把当前有效内容记成 18,432 个位置。

下一轮每条增加一个位置，计数又发生变化。要评估容量，既看这种随时间的实际曲线，也要准备允许长度同时接近上限的压力组合。

连续大块为什么浪费#

若每条请求启动时都拿走整个最大长度区域，短回答结束前会长期占住未使用部分。长短请求穿插退出，又会留下不便复用的连续空洞。

分页把逻辑连续性与物理位置分开。请求增长时领取下一块，用块表把逻辑块号映射到物理池；结束时归还可释放块。它改善分配，不会免除有效 K/V 的存储。

Block 大小的权衡#

块越大，映射表和分配动作通常越少，但尾部未填满的槽位可能更多。块越小，尾部浪费下降，元数据和访问组织则更细碎。实际引擎还受 kernel 支持、对齐和复用粒度限制。

改变块大小后，不能只看尾块百分比，还要测执行性能与管理成本。节约少量显存而显著增加访问开销，可能降低服务的有效容量。

手算分页的最后一块#

设每块 8 个槽位，三条不共享的序列长度为 9、14、20。它们需要 2、2、3 块，共 56 个槽位；有效位置为 43 个，未写入槽位为 13 个。

按每槽 36 KiB，逻辑内容为 1548 KiB，完整块容量为 2016 KiB，相差 468 KiB。这里没有计入块表等开销，目的在于明确内容字节与分配字节的区别。

block table 怎样保持逻辑连续#

序列第二个逻辑块无须挨着第一个物理块。kernel 根据块表查找正确位置，后续生成只扩充需要的映射。若物理块被其他序列引用，还需维护引用与释放规则，不能因某一请求结束就立即回收共享内容。

检查一个缓存错误时，可以先核对逻辑位置对应的块号，再确认物理块是否仍归该内容使用。映射存在不代表缓存键正确，内容有效性是另一层条件。

Prefix caching#

多位读者可能使用相同馆藏说明前缀。若对应 token、模型状态和位置条件一致，其前缀计算可被复用。缓存匹配必须覆盖影响结果的配置，如模型版本、adapter、模板和相关多模态输入。

跨租户复用还涉及隔离和侧信道，不能仅凭字符串相同就默认开放。内容键、可读范围和回收策略都应属于缓存设计。

抢占与重计算#

当空间紧张，引擎可能暂停一条序列并释放部分状态，稍后重新计算。这样可让其他请求继续，却把已做工作再次消耗一遍。请求没有 OOM，并不证明系统没有内存压力。

观察抢占次数、被重算的位置数和生成间隔，能比只看错误率更早发现资源不足。具体是否换出、重算或拒绝，取决于引擎版本与策略。

前缀共享与最终答案缓存的差别#

命中共同前缀只省掉对应输入计算。两个读者后续问题不同，系统仍要分别处理后缀和生成，不能直接复用最终答案。命中率提高后，若生成阶段占绝大部分时间，端到端收益也可能有限。

同样地，压缩权重不会自动压缩 KV。容量实验改变精度时应写清到底改变了哪类 tensor，避免把两个独立动作合并成“模型更小”。

源码阅读路线#

先在 vllm/v1/core/kv_cache_manager.py 找申请与释放，再用 vllm/v1/core/block_pool.py 理解物理块管理。配置和尺寸相关逻辑可查 vllm/v1/core/kv_cache_utils.py，实际读取方式则进入 vllm/v1/attention/。

阅读时带一条会增长、共享、取消的测试序列，核对每个时点的引用和块数，比孤立阅读数据结构更容易发现生命周期。

常见误区#

提高允许上下文，只是允许请求增长得更长，不必然意味着启动即按全长分配。设备还有空闲空间，也不证明引擎配置的块池还有可用块。前缀命中节省的是部分计算，分页节省的是分配浪费，两者都不能使无限长并发变得免费。

07

连续批处理：GPU 如何同时服务很多人

目录查询只需几个输出位置，档案摘要可能要生成几百个。若整批请求必须等最长的一条结束才换人，已经完成的短任务会留下不可利用的空位。连续批处理在执行边界重新选择工作，让这些位置及时被接替。

iteration-level scheduling#

每轮开始，引擎根据上轮结果移出已完成项，评估等待项，安排新的输入或生成位置。随后分配缓存、组装设备输入，执行后再更新长度和停止状态。

这个循环对单条序列仍遵循自回归依赖，但批次成员可以改变。所谓“动态”体现在每轮重组，不是把一个 HTTP 请求重复提交给多个副本。

三个约束#

Token budget#

本轮处理的位置总数有上限。已有生成序列通常各贡献一个新位置，一段输入块可能贡献许多位置。预算限制的是工作数量，并不保证各轮耗时相同。

Sequence 数量#

同时维护的序列数影响 metadata、调度和状态容量。即使本轮 token 尚有预算，达到序列数上限后也可能不能接纳新请求。监控要分开显示两个计数。

KV block#

执行新增位置前，需要有相应缓存空间。尾块可用槽位与是否需要领取新块也有区别。KV 受限时，增加 token 预算未必能带来任何进展。

这一轮有 token 预算，为什么还是进不了新请求#

假设本轮预算 48，已有 5 条生成序列，占用 5 个位置。等待中的输入可取 24 个位置，但块池只剩一块，无法容纳它所需的全部新块。剩余 43 个计算名额并不能代替内存。

已有请求结束并归还可回收块后，新请求才可能进入。还要检查共享引用或缓存保留，不能把逻辑结束数直接当作立刻释放的物理块数。

策略不是只有 FIFO#

到达顺序容易解释，却未必满足所有延迟目标。短任务优先可能改善平均完成时间，代价是长卷宗等待更久；优先保障正在生成的请求，则可能推迟新读者的首字。

为避免高优任务持续涌入导致饥饿，可以设置等待老化、配额或保留份额。具体规则要按服务目标制定，并用可重放的请求序列验证；仅把参数标成“高优”，无法说明长任务会等多久。

为什么吞吐和延迟会冲突#

更大的批次可能提高权重复用，但为凑批新增的等待会进入用户延迟。低到达率下，等待凑满往往比实际计算更久；高到达率下，积压本身又会形成大批次。

有效工作点应满足目标长度分布下的首字、生成间隔和成功率，再比较吞吐。不能先把设备灌满，再用最大输出速度代表所有流量。

最大吞吐实验为什么不代表真实等待#

封闭式固定并发测试中，一条结束立即补一条，到达节奏随服务完成而变化。开放式固定到达率测试则可能不断积压。两种测试回答的问题不同，应记录采用哪一种，并检查是否存在遗漏过载等待的测量偏差。

例如平均到达很低却偶有集中导入，稳定阶段高吞吐不足以证明突发首字达标。应保留突发形状和队列长度曲线。

python3 examples/infra_lab.py check

新版实验用“目录快问、日志摘录、长卷校对”等虚构请求，记录逐轮处理位置与块占用。轮数只比较调度规则，不换算真实时间。

vLLM 源码地图#

读调度源码时追一条请求的资源变化#

从等待请求开始，记下选中时已处理长度、本轮分配位置数与新增块数；执行结果返回后再检查长度是否前进，停止时检查资源如何退回。若选中却无进展，查执行或更新；若完成后占用不降，查释放及缓存引用。

模拟器也应遵循这些不变量，但它没有设备输入布局、通信或真实 kernel，不能代替引擎性能实验。

Benchmark 应记录什么#

为每次实验固定模型与精度、模板、输入输出分布、到达方式、并发上限、每轮预算、块池和缓存策略。结果同时给出完成请求速率、有效输入输出 token 速率及延迟分位数。增加重试、拒绝和取消统计，防止靠丢弃困难请求获得漂亮平均数。

08

模型加载、精度与量化

档案问答的进程已经启动，却还不能接待读者。模型文件必须被识别、读取、转换并放到正确设备，执行路径还要完成预热。服务发布需要测量这一整段准备时间，不能只测容器启动。

冷启动发生了什么#

配置首先决定模型结构和加载方式，随后读取权重分片，建立参数映射，将内容送入设备，并准备缓存与工作区。某些运行方式还会编译 kernel、捕获图或执行预热。不同阶段可能重叠，也可能产生暂时同时存在的副本。

把存储来源写入启动日志。远端对象、本地 SSD 和操作系统页缓存的表现不同；第二次启动较快可能只是缓存命中。扩容设计应包含真正冷启动，而非只复用一台已热的节点。

权重格式#

加载器需要知道每个 tensor 属于哪个参数，哪些权重共享，以及当前 rank 应拿到哪个切片。可分片和可映射的格式有利于控制读取量，但格式支持并不保证框架采用最省内存的路径。

模型仓库中的自定义代码还构成执行边界。进入生产前固定版本，核查需要运行的代码及文件来源。权重下载成功不能替代供应链检查。

量化到底减少什么#

以 30 亿参数计算，16 位内容约 5.59 GiB，8 位约 2.79 GiB，4 位约 1.40 GiB。这些只是理想权重内容，实际还需 scale、打包信息和未量化层。

若原工作受权重搬运限制，减少读取字节可能加快生成；若省下的空间用作 KV，也可能增加可服务的并发。两种收益要分别验证，不能从文件缩小直接推出速度按比例提高。

权重压缩以后，剩下的空间去哪里#

假设从 16 位切到 8 位，理论节省约 2.79 GiB。可以将一部分留作工作峰值余量，另一部分扩大缓存池，但 KV 精度若不变，每个历史位置仍需原来的字节。

加载过程中还可能先建立高精度副本再转换。因此磁盘文件尺寸、稳定驻留尺寸和转换峰值应单列测量。若只看量化文件大小，就可能在首次启动时遇到意外 OOM。

为什么更小不一定更快#

低比特内容需要匹配的打包布局与高效 kernel，某些路径还会做反量化。若目标设备不支持高效实现，或算子回退、频繁转换，节省的读取可能被额外工作抵消。

还要先确认瓶颈位置。排队或 CPU 分词主导的短请求，不会因权重读取改善而同比加速；输入阶段与生成阶段也可能对同一种量化有不同收益。

精度是系统合同#

一份可复现配置应说明权重表示、量化方法与分组方式、激活和 KV 精度、累加精度，以及目标 kernel 和设备支持。只写“低比特模型”无法判断它减少哪类占用。

质量检查与速度检查都需基线。档案中的日期、数字、少见地名和引用可能对精度变化敏感，不能只用几个日常问候验证可用性。

精度合同要覆盖输入到 kernel 的整条路#

例如权重按组保存 scale，加载器必须以相同分组解释内容，kernel 又需对应布局。错配可能直接报错，也可能悄悄走不同执行路径。确认配置被接受后，还要检查实际选择的实现。

对代表性任务比较输出错误与异常数值，同时用相同长度和到达过程比较延迟。一个速度改善结论不能顺带证明任务质量未变。

模型加载的分布式问题#

各 rank 独立读取分片会把压力放到存储，集中读取再分发则把压力转到网络和分发者。是否值得预先切片，还取决于权重布局是否与实际 TP、PP 配置匹配。

同时启动很多工作组时，本地每组的加载很快也可能形成远端读取风暴。应限制准备并发、观察存储吞吐，并把失败重试的放大量计入容量。

热更新与滚动发布#

新版本必须完成加载、执行检查和必要预热后才进入就绪集合。旧版本停止接新请求，再为仍在生成的请求留出排空窗口。模型、tokenizer、聊天模板和 adapter 应作为一致版本组合交付。

更新计划也应保留旧镜像、权重与配置。仅修改服务标签而旧文件已经删除，并不具备真正可执行的回滚路径。

滚动更新为什么需要额外容量#

两个旧副本各自占卡，新副本预热时还需要自己的设备。如果没有额外容量，就必须接受分批减少在线能力或预先调整发布方案。maxSurge 之类参数不会凭空生成 GPU。

多 rank 副本要整组准备和切换。不能把一组中的部分 rank 升级后，仍让它们共同处理请求；版本一致性必须覆盖组内所有参与者。

源码入口#

从 vllm/model_executor/model_loader/ 检查配置怎样选择读取与映射路径，再到 vllm/model_executor/layers/quantization/ 核对量化表示与执行条件。训练相关可查 torchtitan/quantization/ 及 torchtitan/models/。先找实际被选中的实现，再阅读底层细节，避免分析一条根本没启用的优化路径。

09

多卡不是一个开关

夜间校对模型装不进一张卡，白天问答又需要更多吞吐。这是两类需求：前者可能要拆开一个模型，后者可能只要复制更多独立副本。先确定切分对象，才能知道哪些卡必须共同参与同一步。

数据并行 DP#

不同副本处理不同样本或请求。在线推理时，副本通常独立完成自己的请求，主要扩大总服务能力；同步训练时，各副本在更新前还要对梯度达成一致。

每个未分片副本仍需完整模型。因此增加 DP 不能解决单份模型装不下的问题，训练中还要为梯度同步付出通信成本。

张量并行 TP#

把同一层的矩阵运算拆给多个参与者。每张卡产生完整逻辑结果的一部分，中间需要按算子布局进行归约或收集。它减少部分每卡权重和计算，却增加频繁的层内通信。

矩阵尺寸、注意力头和 kernel 对划分有具体要求。TP 越大，每张卡的工作可能越小，通信与启动成本占比反而升高，因此不是越多越快。

两卡切矩阵，与两卡各跑请求有什么不同#

设输入长度为 6，矩阵输出宽度为 10。把输出列切成两组，每卡得到宽度 5 的结果，后续计算需要按布局组合，单个请求离不开双方。若两卡都保留完整宽度 10 的矩阵，各处理不同日志，则是独立副本。

故障影响也不同：前者丢一张卡会破坏这个逻辑副本，后者通常只损失一个独立服务者。部署与健康检查要按实际副本边界设计。

流水线并行 PP#

把层划为多个 stage，激活依次传递。每个 stage 只保留自己的层，但单条数据仍要经过完整顺序。多个 micro-batch 可交错填流水线，开始和结束阶段仍会有空泡。

选择 stage 时既看参数大小，也看实际计算耗时。均分层数不保证均分工作，嵌入、输出头和不同层结构都可能造成失衡。

上下文并行 CP#

超长序列可以沿位置维度拆分，使每个参与者保存或计算部分序列。注意力仍需获得跨分片的信息，因此需要专门交换与计算组织。它并非把一句话机械拆成几个互不相关的小问题。

具体能减少哪些激活或 KV、怎样通信，要核对目标框架和模型实现，不应凭名称推导全部状态都均分。

专家并行 EP#

MoE 将专家分布到不同设备，router 决定 token 发往哪些专家，执行后再组合结果。常见传输涉及 AllToAll 类型的数据分发。

如果很多 token 集中到少数专家，某些设备会成为热点，其他设备即使有空也要等待。容量评估应包含实际路由分布与失衡，而非只用平均专家负载。

并行可以组合#

简单的 DP、TP、PP 布局可用三个坐标表达。例如 (数据副本, stage, 张量分片) 确定一个 rank 的职责。长序列和 MoE 加入后，维度的依赖与分组规则由框架决定，不能不加条件地相乘所有缩写。

先列每张卡保存哪些参数、处理哪些样本，再列它属于哪些通信组。随后把这些组映射到节点内外的真实链路。

device mesh 的坐标决定谁和谁通信#

假设 DP=2、TP=2，每个副本内部的两卡执行层内通信，两个副本中对应分片还可能在训练中同步。编号连续只是命名，不能保证物理上相邻。

把频繁通信的 TP 组放到快链路内通常更合理，但仍要实测。设备数量满足乘积只是必要条件，拓扑和显存峰值同样约束布局。

一个 8 卡例子#

考虑教学模型含 180 亿参数，16 位权重下界约 33.53 GiB，目标卡各有 24 GiB。单卡放不下，理想 TP=2 时每卡权重约 16.76 GiB，剩余还要容纳缓存与工作区。

八张卡可以候选组成四个两卡副本，但这只是待测试布局。若组内互联差，或长输入峰值超过余额，仍需调整并行、精度或负载。图中的八卡不对应特定产品。

推理与训练的同名差异#

训练往往用规律 micro-batch 持续执行，在线服务则不断接入、退出和改变长度，还要保护用户延迟。相同 TP 和 PP 名称不会使两者拥有相同最佳参数。

训练可用许多 micro-batch 填流水线；在线单请求的每个生成位置都需经过各 stage，其逐 token 延迟可能不理想。应分别评估吞吐与单请求体验。

只做权重除法会漏掉通信和峰值#

上例每卡 16.76 GiB 只是理想权重分摊。某些参数或状态可能复制，层内归约还需 buffer，缓存能否均分也依赖实现。加载成功后，还需测长上下文、批次峰值与必要 collective 的时间。

若增加卡后更慢，检查每卡工作是否变得过小、通信频率是否过高，或 stage 是否不平衡。继续增加同类资源可能放大原来的等待。

在 megatron/core/parallel_state.py 追进程组构造，在 megatron/core/tensor_parallel/ 与 megatron/core/pipeline_parallel/ 看实际工作划分。TorchTitan 的维度说明位于 torchtitan/distributed/parallel_dims.py，推理组管理可从 vllm/distributed/ 查起。带着一组具体 rank 坐标阅读，核对每次通信的参与者。

10

Collective：GPU 之间怎样交换数据

分片后的计算只有局部结果。某一步需要完整参数，另一步只需各方贡献的和，还有一步要把 token 送到不同专家。这些数据关系由 collective 定义，NCCL 等实现负责在设备和链路上高效完成。

四个最常见操作#

AllReduce#

每个参与者提供同形状输入，按照约定操作归约，随后每方得到完整归约结果。例如 sum 用于合并梯度贡献。结果是和还是均值，取决于操作与后续缩放，不能从名称直接假定平均。

AllGather#

各方提供自己的片段，所有参与者获得按顺序组成的集合。它搬运和组合内容，不替你做逐元素加法。分片参数在某些计算前需要这种组装。

ReduceScatter#

先把各方贡献归约，再把结果拆开分给参与者。每方只留一个结果片段，可以避免人人长期保存完整归约内容，常用于分片梯度。

AllToAll#

每个源为不同目标准备不同片段，交换后各目标收到来自多个源的数据。MoE token 路由可使用这类关系。输入输出大小和分布规则需要各方匹配，数据偏斜也会影响耗时。

用两个 rank 区分归约与收集#

rank 0 输入 [2,7]，rank 1 输入 [5,1]。sum AllReduce 让双方都得到 [7,8]；AllGather 则得到按 rank 顺序排列的 [2,7,5,1]。

同样的输入做两等份 ReduceScatter，可使 rank 0 留下 [7]、rank 1 留下 [8]。若按一元素一目标做 AllToAll，rank 0 收到 [2,5]，rank 1 收到 [7,1]。这四种结果足以检查你是否把“收集”和“归约”混用。

Ring 的直觉#

一种 AllReduce 实现先通过多轮交换完成分片归约，再分发已归约片段。环中各参与者主要与邻居传输，适合利用链路带宽，但启动轮数会随参与者数量增长。

具体算法还可能采用树或其他结构。消息尺寸、拓扑和协议共同影响选择，应用通常声明数据语义，不应把某次内部使用 ring 当成永久 API 合同。

拓扑比 GPU 数量更重要#

四个参与者可能位于同一高速交换域，也可能跨两个普通以太网节点。逻辑操作相同，必要传输路径却不同。先用 nvidia-smi topo -m 等工具确认 GPU、CPU 和 NIC 的邻近关系，再结合通信日志核对实际接口。

尤其要区分空闲独占测试和共享网络下的训练。链路标称速度不等于该作业可用吞吐，NUMA 和网卡亲和也会引入额外路径。

同步等待#

参与者必须以兼容的顺序调用操作，并满足对应形状、精度和计数规则。某个 rank 在到达通信前读数据很慢，其他 rank 的等待会出现在 collective 区间，但根因可能不在通信库。

排查时按运行 ID 对齐各 rank 的时间线，查最早异常与首次顺序分歧。接口选择和权限也是条件，但不应跳过应用侧的一致性检查。

所有进程都活着，collective 也可能永远等不到#

若 rank 0 等待梯度 AllReduce，rank 1 却因分支进入下一次参数 AllGather，两个进程都存在也不能匹配完成。另一个常见轨迹是某 rank 先 OOM，其他参与者稍后才报告通信超时。

恢复日志应保留首错与后续连锁错误的顺序。把最后一条 timeout 当作首因，可能导致反复调整网络却从未修复内存或控制流问题。

通信量如何影响并行选择#

层内 TP 通信频繁，PP 在 stage 边界交换激活，分片训练会组装参数与归约梯度，EP 还需分发 token。比较方案应列每步调用次数、消息大小、参与组和物理路径。

同样一 GiB 数据，一次大传输与成千上万次小传输耗时不同；可重叠部分也不同。因此“总通信字节更少”是有用线索，却不足以单独决定最快配置。

Overlap 不是免费#

通信若能在不相关计算进行时启动，可以缩短关键路径。前提是后续计算暂不需要结果，且两者争用的资源不会抵消收益。通信 kernel 也可能消耗设备执行和内存带宽。

bucket 细分有助于更早启动，却增加固定开销；bucket 太大又会推迟开始。应比较完整训练步骤的耗时，不能只凭两条 trace 在时间上交叠就宣布加速。

大带宽为什么救不了大量小消息#

用教学近似 耗时 = 启动延迟 + 字节 / 吞吐。设固定开销 8 微秒、吞吐 40 GB/s，发送 4 KB 的数据项约 0.1 微秒，固定部分占主导；发送 40 MB 的数据项约 1 毫秒，带宽影响更明显。

真实 collective 有多轮交换，这里仅展示量级。若将大批内容切成许多极小 bucket，可能把 8 微秒反复支付。调优应同时观察启动次数与关键路径。

源码入口#

从 nccl/src/collectives.cc 看操作入队，再看 nccl/src/enqueue/。拓扑规划在 nccl/src/graph/，传输选择在 nccl/src/transport/，诊断相关代码可查 nccl/src/ras/。需要把模型切分与通信语义连接时，参考 megatron/core/tensor_parallel/mappings.py，先确认参与组与张量布局再深入设备实现。

训练循环与训练显存

夜间校对任务用人工修订的档案片段训练模型。一次参数更新要经过取样、前向计算、反向求导和优化器更新。把这些动作的边界画清楚，才能区分数据等待、激活峰值和状态占用。

下面是说明累积顺序的伪代码，不是可直接运行的训练器：

清空本轮梯度
重复 K 次：取 micro-batch，计算并缩放 loss，累积梯度
按分布式策略完成需要的梯度同步
检查数值状态，执行一次参数更新

Forward#

模型将输入位置转换为预测分布，并根据目标计算 loss。自动微分需要某些中间结果，因此 forward 结束后并非只留下一个 loss 数值。哪些结果保存、哪些可重算，决定后续激活内存。

样本掩码、padding 和目标移动也影响训练语义。一个更快但读错目标的 forward 不能算性能优化。

Backward#

自动微分沿依赖关系计算梯度，读取保存结果或重新计算部分区域。分布式方案还可能在梯度就绪后逐批启动同步，而非等全部反向结束才开始通信。

观察到反向阶段很长时，要区分本地求导、重计算和同步等待。不同原因对应不同动作，不能全部归到“反向约为前向两倍”的粗略经验。

Optimizer Step#

以 AdamW 为例，更新需要参数、梯度及 moment，还可能有高精度主参数。更新边界通常也推动学习率计划和步数计数。若数值异常导致跳过更新，要明确这些计数怎样处理。

只保存模型权重可以用于某些推理场景，却不足以在同一优化状态继续训练。恢复需要的内容将在数据与检查点章节展开。

Micro-batch、Global batch 与累积#

简单同步数据并行下，一次更新的样本数等于每数据副本的 micro-batch 乘数据并行度，再乘累积次数。TP 或 PP 参与者共同处理同一份模型工作，不应再次乘入独立样本数。

累积允许每次前向使用较小输入，从而减少单次激活峰值。梯度要跨 micro-step 保留，loss 缩放和同步时机也要匹配，否则可能改变有效更新。

一次 optimizer step 究竟看过多少样本#

设每个数据副本一次处理 3 份校对样本，共 4 个副本，累积 5 次，则更新前共处理 60 份样本。若每份恰好含 1024 个有效位置，对应 61,440 个有效 token。

每个 micro-step 都清梯度并更新，会变成五次不同更新，不再等价于这个 global batch。实际变长数据还应按有效 token 而非固定样本长度复核。

训练显存四大项#

参数决定模型当前值，梯度记录本轮更新方向，优化器状态记录更新历史，激活支持本轮求导。前几项大体跟参数量相关，激活更直接依赖 micro-batch、序列形状及实现。

长期状态主导时考虑分片，激活主导时考虑缩小输入或重算。最好通过测量和对象清点确认主项，而不是根据模型标签预判。

Activation Checkpointing#

选择边界保存少量结果，其余中间状态在反向需要时重新计算。它以额外运算换取更小保存集合，边界和分组粒度决定收益及成本。

采用后需比较峰值与完整 step 时间，还要确认随机性和数值路径按框架要求处理。某些区域计算昂贵却节省有限，不适合一概开启最大力度重算。

重计算省下的是激活，而不是所有训练状态#

若本轮激活峰值为 8 GiB，而参数、梯度和优化器状态共 40 GiB，即使去掉大部分激活，40 GiB 仍然存在。这个教学账解释了为什么重算不能修复所有训练 OOM。

应优先分析占用大、重新生成成本相对低的中间结果。重算区域扩大后，还需复查数据供给和通信重叠是否改变了关键路径。

Mixed Precision#

计算、累加、梯度和优化器可以采用不同精度。FP16 可能需要 loss scaling，BF16 具有不同指数范围和尾数精度，FP8 又依赖硬件及缩放方案。没有一条“全部转低精度”的规则适用于所有训练。

记录溢出、跳步、梯度范数和 loss，检查速度变化是否伴随训练不稳定。字节数下降只是其中一项结果。

TorchTitan 的训练骨架#

先从 train.py 及训练引擎追一步运行，再按职责进入 components/data、优化器组件、distributed、components/checkpointer 和可观测相关模块。目录组织属于版本事实，具体调用应以本地快照为准。

用一张步骤表记录何时取数、何时同步、何时更新及保存，比按目录逐文件通读更容易保留整体执行关系。

step 变快，还要确认每步工作没有变少#

把有效长度从 2048 减到 1024 会让步骤变短，但也可能把处理量减半。比较时保留 global batch、有效 token 数与训练目标，报告 tokens/s 和质量曲线，而不是仅展示 step 毫秒数。

保存间隔变化也会影响平均吞吐。只截取两次 checkpoint 之间最平稳的区间，不能代表完整作业成本。

训练吞吐看什么#

一起记录有效 token 或样本速率、step 分解、各 rank 的尾部耗时、保存暂停和数值健康。若报告 MFU，说明运算量估算口径。吞吐数字必须能解释实际处理量，并能覆盖失败、保存和恢复的正常运维成本。

分片、重计算与并行组合

档案模型训练需要的状态超过单卡容量时，要先确定是长期训练状态还是本轮激活过大。不同切分方案降低不同项，并会改变数据交换与恢复方式。

从复制到完全分片#

普通数据并行让每个副本保存完整训练状态。将优化器、梯度乃至参数拆给多个 rank，可以减少每个参与者长期保留的内容，但使用时可能需要重新组装。

ZeRO 的教学分级#

Stage 1 从优化器状态分片开始，Stage 2 再划分梯度，Stage 3 进一步划分参数。这个递进用于理解省下什么、使用时补回什么，不意味着所有现代接口都直接以 stage 命名。

完整方案还涉及何时通信、哪些状态保持高精度以及怎样保存。不能只从级别编号推断所有实现细节。

FSDP2 的直觉#

参数以 shard 驻留，需要执行某个 unit 时收集相应内容，完成后按策略重新分片。反向也有参数需求，并将梯度归约成分片形式。预取可以把部分通信提前，但会延长更多 buffer 同时存活的时间。

unit 粒度是关键取舍：小 unit 缩小一次组装，却增加操作次数；大 unit 减少管理，却可能抬高峰值。应把显存与通信时间放到同一张实验表里。

分片后的常驻显存与计算峰值不同#

设总参数内容 12 GiB，四个 rank 理想各持 3 GiB。若本次需要额外组装一个 2 GiB unit，按“shard 与组装 buffer 同时存在”的教学假设，瞬时至少涉及 5 GiB 参数相关空间；预取下一 unit 可能再增加占用。

实际实现可能复用或释放部分空间，这个数字不是 FSDP 的固定保证。重要的是画出生命周期，不能仅把 12 除以 4 当作设备峰值。

3D 并行#

DP 或 FSDP 处理样本与训练状态，TP 切层内工作，PP 切层序列。组合时，每个 rank 同时属于多种组，但每次通信只在对应组内进行。

给 rank 写出 (dp, pp, tp) 坐标，再为每个维度列成员，能检查是否有错误交叉。长序列和 MoE 增加的维度要遵循框架分组约束，不能只做卡数乘法。

为什么节点内优先 TP#

TP 经常在层内交换，频率较高，通常更依赖低延迟高速链路。让这种组留在同一快互联域，再把其他维度跨节点扩展，是常见起点，但仍需结合矩阵大小与设备拓扑测试。

调度器若只满足张数而把必要参与者放到慢链路两端，程序可能正确运行却明显变慢。作业提交应表达拓扑需求，而非仅依靠 rank 编号。

Pipeline Bubble#

stage 只能在前置激活可用后执行。多个 micro-batch 可以交错前进，起步与收尾仍有空闲；计算最慢的 stage 还会决定持续节拍。

优化时检查实际 stage 时间、跨界传输和调度策略。层数均分不等于耗时均分，输出头或特殊层可能使某一 stage 成为瓶颈。

流水线空泡不是 GPU 没有被分到任务#

仅考虑三个等时 stage 的前向流水线，六个 micro-batch 需要八段时间才能全部通过。每个 stage 忙六段，理想忙碌比例为 75%。卡已经分配成功，空泡来自依赖。

真实训练还包括反向、调度和通信，这个比例不能直接预测。它仅说明增加 micro-batch 可摊薄起止成本，也说明应观察执行泳道而非只看资源占有。

CPU Offload 的真实代价#

把某些状态放到主机可以减小设备常驻空间，但数据要经过主机内存和 PCIe 等路径。若所需状态未能及时搬回，设备会停等；NUMA、固定页内存和同时进行的数据加载也会影响结果。

因此 offload 是转移容量需求的方案。实验必须同时记录设备节省、CPU 占用、传输量和步骤延迟，不能把 CPU 当作无成本的显存延伸。

选型顺序#

依据占用主项选择最少复杂度的候选：激活峰值先尝试合适重算或输入形状调整，长期状态考虑分片，单层难以容纳时研究 TP，层序列扩展时研究 PP。CP 与 EP 则需要对应的长序列或专家结构需求。

这是一条排查路线，不是强制算法。每增加一维，都应保留较简单方案的对照，并证明新增通信与运维成本有实际收益。

怎样让并行选择成为可解释的实验#

写下假设，例如“optimizer 状态主导，分片应降低常驻而增加通信”。固定数据和 global batch，测常驻、峰值、通信与有效吞吐。若结果不符，先检查实际启用路径与被遗漏的 buffer。

同时演练当前 mesh 的 checkpoint 保存和恢复。能完成一次高吞吐运行，却无法在故障后重新放置状态，仍不是可靠训练方案。

源码入口#

TorchTitan 的并行组织可查 torchtitan/distributed/ 和模型对应的 torchtitan/models/*/parallelize.py。Megatron 侧先看 megatron/core/parallel_state.py，再按问题进入 megatron/core/pipeline_parallel/ 或 megatron/core/distributed/。阅读顺序应从组成员和数据归属出发，再到具体通信实现。

数据管道与 Checkpoint

训练需要持续送入正确数据，也需要把可恢复状态交给存储。两条链分别决定设备是否空等，以及失败后会退回哪里。文件写出来和训练能够恢复，是不同的验收标准。

数据路径#

校对文本从远端分片进入读取 worker，经过解码、分词或 packing，在主机内存形成 batch，再传到设备。任何一段供给不足都可能让后面停顿。

可分别测远端读取、worker 处理、就绪队列和主机到设备拷贝。若就绪队列长期为空而设备有空隙，应先检查供给；如果队列充足却传输迟缓，再看内存、拷贝与依赖。

Sharding 与顺序#

数据并行副本需要有明确的样本分配，避免无意重复或遗漏。shuffle 种子、epoch、分片清单和 packing 规则共同决定数据顺序，worker 数变化也可能改变读取方式。

这些配置应与数据版本一起保存。吞吐比较中若同时改变 packing，样本数相同也不一定代表有效 token 数相同。

从同一 step 恢复，为什么还可能读到不同数据#

第 420 次更新结束，不足以说明第几个分片的哪个位置被消费。若模型恢复到这里，而 sampler 回到开头，程序可以继续运行，却会重新读取旧样本。

恢复合同要说明数据游标、随机状态和已预取数据怎样处理。对于无法做到严格等价的流式数据，明确允许重复或跳过的范围，而不是用“已 resume”掩盖差异。

Checkpoint 保存什么#

可继续训练的状态通常包含参数、优化器、步数和学习率计划，还要考虑 RNG、数值缩放、数据位置以及模型与并行配置。代码和数据版本引用用于解释这份状态属于哪种运行。

参数文件只够回答“模型现在是什么值”，不足以回答“下一次应读什么、怎样更新”。保存前按恢复目标列清单，避免到事故后才发现缺了关键状态。

分布式 Checkpoint#

让单个 rank 汇总全部状态，可能造成巨大的内存峰值和写入瓶颈。分布式保存由多个参与者写各自分片，metadata 描述全局 tensor 与片段位置。

若计划改变 world size 恢复，格式和恢复器必须支持重新切分。长期格式不能只留下“rank 3 的文件”而失去全局形状和归属含义。

一致性与原子提交#

一次保存可先写临时对象，再确认分片与元数据满足完整性条件，最后发布提交记录。读取方只选择已经提交的版本，latest 也应指向可用版本。

底层存储的重命名和一致性语义不同，不能假设对象存储具有本地文件系统一样的原子操作。协议必须按实际存储能力实现。

完成标记为什么要最后写#

假设八个分片只完成七个，目录和多数文件都已出现。若恢复器凭目录名选最新，就会读到不完整状态。提交记录要在完整性验证后才可见，失败尝试不应覆盖已知可用的指针。

校验还要覆盖预期对象集合、尺寸或校验值，以及 metadata 是否匹配。仅检查“存在八个文件”无法排除写错内容或混入旧分片。

同步与异步保存#

同步方案在保存完成前暂停训练，边界清晰但会产生停顿。异步方案先形成稳定快照并完成必要 staging，再由后台写出，缩短设备等待。

如果后台直接读取继续变化的参数，得到的可能不是任一真实步骤的状态。稳定快照需要额外内存、拷贝和并发控制，多个保存任务堆积时也必须有背压。

保存频率怎么算#

若故障在两个保存点之间近似均匀发生，单次失败平均丢失工作约为间隔的一半。间隔变短能减少回退，却提高正常保存开销；真实决策还要加入故障率、恢复时间与任务价值。

可以先测一次保存暂停和写出持续时间，再为候选间隔估计正常成本与失败损失，最后用演练修正假设。不能只复制别处的 cron 周期。

推理也需要持久化吗#

在线引擎往往通过重新加载模型恢复服务，不对每条生成维护可搬迁的 GPU 检查点。长时档案处理任务可以在应用层保存输入、已完成单元和业务结果，再在失败后重试未完成部分。

若要从生成中途精确续写，还涉及历史状态、采样随机性和引擎格式，复杂度明显更高。先确认业务是否确实需要这种语义。

保存频率在正常开销与失败损失之间取舍#

设一次同步暂停 30 秒，间隔 30 分钟，粗略正常暂停比例约 1.67%；改为每 10 分钟保存则约 5%。在均匀失败假设下，单次平均回退从 15 分钟降到 5 分钟。这个教学比较没有加入后台写入和恢复耗时。

最终应实际加载保存结果，核对步数、下一批数据和优化器状态，并执行几步验证。保存日志的成功消息只能证明某个保存路径返回，不能替代恢复验收。

源码入口#

数据与保存可从 torchtitan/components/data/、torchtitan/components/checkpointer/ 追起，Megatron 的分布式状态格式在 megatron/core/dist_checkpointing/。结合 PyTorch Distributed Checkpoint 文档，按状态声明、规划、写入和重分片顺序阅读，确认目标版本实际支持的恢复条件。

Kubernetes 怎样看到 GPU

节点装好了 GPU，并不意味着 Kubernetes 已经能分配它。设备需要被发现、报告为资源，并在容器启动时获得正确访问条件。资源计数与模型真正可运行之间还有多层合同。

Extended Resource#

一个档案批处理容器可以声明：

apiVersion: v1
kind: Pod
metadata:
  name: archive-indexer
spec:
  restartPolicy: Never
  containers:
    - name: worker
      image: registry.example.org/archive-worker:validated
      resources:
        limits:
          nvidia.com/gpu: 2

镜像地址为教学示意，不能直接作为可拉取镜像。这里申请的是两个整数量资源，并不意味着默认允许 0.5 张物理卡。共享方案需要另外配置并说明隔离语义。

Device Plugin 的职责#

插件发现设备、跟踪健康状态，向 kubelet 注册资源，并在分配时提供设备可访问所需的信息。实际可通过设备节点、环境、挂载或 CDI 等机制完成，依配置和版本而异。

插件不替集群选择节点，也不判断模型的 KV 是否足够。它使设备成为可分配对象，应用运行条件仍由其他层共同保证。

Scheduler 知道多少#

调度器能依据节点报告的数量和 Pod 的约束选择放置位置。默认资源名本身通常不包含显存大小、模型热缓存或任意两卡之间的高速互联关系。

型号和位置需求可借标签、亲和与拓扑机制表达，成组启动还需作业级调度支持。不要把 nvidia.com/gpu: 2 读成“自动给我最适合这个 TP 模型的一对卡”。

资源数字怎样一步步变成容器可访问的设备#

先由节点插件报告设备，再由节点状态呈现可分配数量，调度器绑定 Pod，最后 kubelet 与运行时完成具体设备暴露。每一步都有独立失败方式。

Pod 尚未绑定时检查调度事件；绑定成功但容器看不到设备时检查 Allocate、运行时和驱动库。跳过阶段区分而反复重启应用，会丢失有价值的现场。

MIG、Time-slicing 与 MPS#

MIG#

支持的硬件可划出具有特定资源配置的实例。实例规格限制显存和计算份额，也影响能否承载某个模型。硬件分区带来的隔离与运维约束，需要结合设备支持及 profile 规划。

Time-slicing#

多个逻辑使用者轮流共享设备执行机会。增加可声明份额有利于低负载复用，但通常不构成独立显存容量保证，也不使物理带宽成倍增加。

MPS#

MPS 协调多个 CUDA 进程共享执行资源，可能改善并发效率。支持条件、限制和错误影响范围与 MIG 不同，需要使用真实应用验证，不能把三者一概称作同一种虚拟卡。

DaemonSet 与节点准备#

插件通常通过 DaemonSet 覆盖 GPU 节点。节点还需要可用驱动、兼容的容器运行时和工具包、正确网络，以及必要监控。自动化 Operator 可以管理其中部分生命周期，但兼容组合仍需验证。

给节点准备建立版本清单，包含内核、驱动、容器 CUDA 运行库、插件配置和通信组件。升级前用代表性单卡与多卡任务做检查，而不只确认 Pod 正常。

共享份额不应被当成显存承诺#

假设物理卡有 16 GiB，两份任务各需 11 GiB。即使调度层暴露两个共享槽，也没有 22 GiB 物理空间可供它们同时驻留。

若需要确定的显存边界，必须选择满足条件的隔离方案，并用真实模型峰值验收。共享利用率提升与容量保证是两种不同目标。

一个 Pod 能用多卡，不等于多节点#

单个 Pod 的设备请求由一个节点满足，不能靠申请更多 GPU 自动跨越多个节点。多节点训练通常由多个 Pod 加上 rendezvous、rank 和进程组配置组成逻辑作业。

这组进程还需要网络连通、共同版本及足够的启动资源。每个 Pod 各自拿到卡，不代表整个 world 已经可以执行 collective。

排障顺序#

在节点上确认设备与驱动，再查插件是否报告健康资源，随后查看 Pod 申请和调度事件。容器启动后核对设备与库可见性，最后进入应用的 local rank、初始化和通信。

这条路线由下层事实逐步走向应用，不会把节点故障、资源不足和模型 OOM 混成一个 CUDA 问题。保留事件和首错后再执行重启。

用故障所在层选择检查命令#

nvidia-smi 用来检查主机设备，节点资源和 Pod event 用来解释分配，容器内设备与库检查解释运行时，rank 日志解释协作初始化。某层结果正常，只能排除相应问题，不能顺便证明下一层正确。

若多节点挂起，先确认全部参与者是否进入同一 rendezvous，再核对网络和 collective。无需因为最后显示通信超时，就重新安装整个设备插件。

源码入口#

启动注册可查 k8s-device-plugin/cmd/nvidia-device-plugin/，分配路径在 k8s-device-plugin/internal/plugin/，资源发现与 MIG 组织分别参考 internal/rm/ 和 internal/mig/。结合 Kubernetes 的 Schedule GPUs 文档，把代码职责放回节点选择与容器启动的阶段中理解。

批作业调度：为什么要一起开跑

夜间训练需要多个进程协作。如果只给其中部分进程设备，它们可能一直等待其他成员，已经分到的卡却无法交付任何训练结果。作业级准入要避免这种半组占用。

普通逐 Pod 调度的问题#

考虑两个作业，各要求三个协作 Pod，而当前只能容纳四个。若各启动两个，就出现两组都缺最后成员、却没有剩余槽位的状态。单个 Pod 看起来分配成功，作业整体没有前进。

平台需要根据真实协作下界判断是否准入，再安排成员，而非仅优化每个独立 Pod 的放置成功率。

Gang Scheduling#

gang 策略将最小成员或资源需求作为启动条件。不满足时等待，满足时让必要成员获得资源。这能减少无效半启动，却可能为大组保留资源并产生暂时空闲。

准入条件应来自运行时合同，例如必须同时存在的训练 worker 数，而不是把日志收集或辅助容器也机械计入计算门槛。

一起获得资源，不等于同一瞬间开始计算#

资源满足后，成员仍要拉取镜像、加载模型、读取数据和加入 rendezvous。某一个准备缓慢，其他 rank 仍会等它。作业监控应拆开“等待准入”和“已准入但等待协作”。

若一个辅助服务失败就应阻止开跑，也需显式写入启动条件。调度数量正确不能替代业务就绪检查。

Volcano 的基本对象#

Job 描述任务角色与生命周期，PodGroup 描述需要协同的成员，Queue 表达资源组织和策略范围，调度插件实现 gang、公平、优先级或装箱等规则，控制器负责把期望转换成实际对象。

这些对象管理资源进入条件，不执行模型梯度或 collective。运行时与批调度器之间要约定故障、重启和保存信号。

队列、公平与利用率#

FIFO#

按顺序容易让用户理解等待，但队首大作业可能暂时无法运行，后面较小的作业也被挡住。若采用绕过规则，应把它说明为策略，而非暗中改变顺序。

Priority#

优先级可支持紧急校对任务，但需定义是否允许抢占、最长等待和普通任务的保障。否则高优任务持续到来时，低优队列可能长期没有进展。

DRF#

主导资源公平用于协调多资源份额，不能简单等同于平均 GPU 张数。不同卡型、显存和网络拓扑会使同一数量具有不同可用能力，资源分类仍需平台定义。

Binpack#

将兼容任务尽量集中，可以留下完整节点或互联域给大作业。集中也可能带来电力、温度或故障域风险，因此应把设备可用性与基础设施约束一起考虑。

Backfill#

大作业等待资源窗口时，可以让能在窗口前退出的小作业暂时利用空闲容量。前提是时长估计可信，或任务具有可接受的抢占和恢复合同。

训练时长受数据、保存和故障影响，用户填写“几分钟”并不是保证。可以使用明确最大运行时，超出时按约定退出，而非让临时任务无限拖延已承诺的大作业。

公平、碎片和等待为什么不能同时简单最大化#

立刻填满所有空卡有利于短期利用率，却可能一直凑不齐大组。为大组保留资源会产生眼前空闲，却可能缩短它的整体等待。评估策略要同时看用户等待、有效计算与拓扑碎片。

公平份额和紧急优先级也可能冲突。平台应公开它选择保护的目标，并用真实或可重放作业序列检查长期饥饿。

抢占不是 kill -9 就结束#

可恢复抢占需要一条完整协议：发出终止通知，停止开始新步骤，在规定时间内完成一致保存，退出并释放资源，后续再选择可用状态恢复。宽限期与保存能力不匹配时，会损失未提交进度。

平台要定义超时后怎样处理，也要避免同时驱逐过多作业形成 checkpoint 写入风暴。抢占延迟应包括保存与设备真正释放，而非只记录信号发送。

拓扑约束#

协作组可能要求同一高速域、相同设备规格或特定网络亲和。数据本地性与故障域也会影响选择。每增加一种约束，调度可行空间都会缩小。

向用户提供经过验证的少量模板通常比任意 affinity 组合更可靠。模板中同时固定镜像、通信配置和恢复方式，防止资源看似满足却无法运行。

抢占回收的是资源，损失的是已做计算#

假设最新可用保存点之后已训练 12 分钟，此时强制退出会丢掉这段工作。若愿意等 40 秒完成新保存，可以减少重算，但紧急任务也多等这 40 秒。两种成本都应记录。

真正恢复后核对选择了哪份 checkpoint、损失多少步及数据位置。只统计“几秒释放 GPU”会隐藏被抢占方的计算损失。

源码入口#

从 volcano/pkg/scheduler/ 追作业与队列决策，gang 条件可进入 volcano/pkg/scheduler/plugins/gang/。实际 Job 与 PodGroup 的生命周期分别查 volcano/pkg/controllers/job/ 和 volcano/pkg/controllers/podgroup/，结合架构与插件文档核对当前快照的策略配置。

在线服务：网关、队列、副本与扩缩容

开放档案问答后，工作量会随着读者人数、日志长度与生成要求变化。可靠服务需要在接入前限制不可能完成的工作，在副本间分配负载，并为缓慢启动的新容量留出时间。

数据面组件#

Gateway#

入口建立身份与额度边界，验证输入和输出上限，并选择模型。应尽早拒绝明显不支持的长度，避免让请求排了很久后才发现无法运行。拒绝结果也要有明确可重试语义。

Replica#

逻辑副本提供一份可服务能力，可能包含前端与一个设备工作组。副本数、Pod 数和 GPU 数没有固定一一对应，应在拓扑图中写出实际关系。

GPU Worker Group#

一个 TP 或 PP 副本可能依赖多个进程。就绪检查应确认必要参与者可以共同执行，而不是只检查前端端口。单个坏 rank 可能影响这组中的全部请求。

Queue#

有界队列可以吸收短突发，但等待本身要计入用户预算。长度、等待时限、租户份额和过载策略都应显式配置。无限排队会把容量不足延迟成大规模超时。

路由的三个层次#

先确定请求允许使用哪个模型或 adapter，再挑选就绪副本，最后由该副本的引擎选择本轮执行。模型权限、整体负载和 token 调度对应不同层，不宜塞进一个模糊的“智能路由”概念。

副本选择可考虑剩余工作、KV 压力和可复用前缀，但采集状态有延迟。多个路由器同时选择看似最空的副本，也可能瞬间制造热点。

两个副本排队条数相同，剩余工作也可能不同#

假设两个副本各等待三条请求，甲的输入合计 600 token，乙的合计 12,000 token。仅按请求数它们相同，实际输入工作显然不同；还需加上正在生成的历史状态与预期输出。

缓存亲和可能节省输入计算，却也可能把同类请求集中到一处。应测“命中收益减去新增等待”的净效果，而不是追求最高命中率。

Autoscaling 看什么#

可以把等待 token、首字分位数、活跃状态和完成能力作为主要信号，再结合设备与 CPU 指标解释原因。设备利用率低可能是需求少，也可能是输入或通信供给不畅。

扩缩决策需迟滞和稳定窗口，避免短抖动反复创建与删除昂贵副本。就绪容量与正在准备容量应分列，否则 replicas 上升会被误认为用户已经获得帮助。

冷启动决定提前量#

假设教学部署下载、加载和预热合计需要 5 分钟。若到首字目标已经失守才申请新副本，现有突发不会被立刻吸收。可以维持最小热容量、提前在候选节点缓存模型，并按周期需求预扩。

同时限制准备并发，防止所有副本争抢同一远端存储。扩容链的最慢阶段可能随并发而变化，应测从申请到可接真实请求的完整时间。

扩容来不及的时候，队列必须有上限#

若用户可接受等待只有数秒，新副本要几分钟才能就绪，当前过载必须通过限流、降级或转异步处理应对。无限接收只会把未来几分钟的工作堆成无法兑现的承诺。

拒绝策略应考虑租户公平和客户端退避，避免一个同步导入任务占尽全部交互队列。扩容解决后续容量，不替代当下的入口保护。

KubeRay 与 Operator 模式#

KubeRay 用 RayCluster、RayJob、RayService 等对象管理 Ray 相关生命周期。需要 Ray 分布式运行时的方案可以利用它表达期望与调和；单机模型副本则可能用普通 Deployment 就能满足需求。

选用控制器应基于明确生命周期问题，如整组准备与版本切换，而非因为项目名称里带 AI。新增控制层也意味着新的升级与排障职责。

滚动升级的 drain#

新组完成验证后逐步接入，旧组先退出接入集合，再等待已有生成结束或触及 deadline。超过期限时应明确返回失败和重试语义，不能默认已流出文本会被新组无缝续写。

保留旧版本产物与回退配置，并确认更新期设备容量足够。切换成功不仅是新副本出现，还包括旧连接得到一致处理。

容量规划的单位#

将输入与输出长度分开，按代表性类别测每副本可承受的到达率和延迟。请求速率仍有业务意义，但无法脱离长度与成功率单独描述资源需求。

一份副本容量表应给出达到目标的工作点，而非只列灌满时的峰值 tokens/s。还需保留至少一种故障或突发余量假设。

缩容为什么要先停止接新请求#

准备删除的副本若仍接新工作，排空时间会不断向后推。停止接入后，活跃工作才有机会单调减少。要区分连接还在、引擎已完成和客户端已收到结束三个状态。

按整组排空多 rank 副本，避免部分参与者先退出破坏所有剩余请求。缩容验收还应确认块、连接和计费状态最终得到清理。

源码入口#

HTTP 接入看 vllm/entrypoints/openai/，引擎接口看 vllm/v1/engine/，协作组看 vllm/distributed/。Ray 相关生命周期与监控入口可从 kuberay/ray-operator/ 和 kuberay/config/prometheus/ 查起，核对实际部署启用了哪些组件再进入对应代码。

可观测性、SLO 与成本

读者说“问答卡住”，值班人员需要判断是尚未开始、生成中断，还是网络没有送到。指标应帮助还原这个过程，而不只是证明监控系统采集了很多数字。

用户层指标#

TTFT#

首 token 或首个可见增量的时间需定义起止点。它包含接入、分词、排队、输入执行与回传。客户端和服务端测得的值可以不同，仪表盘应标明测量位置。

TPOT / ITL#

TPOT 描述生成阶段平均每输出位置的耗时，ITL 关注相邻输出之间的间隔。均值适合量级比较，分位数和单请求时间序列更容易暴露停顿。网络聚合会影响客户端所见间隔，不能直接等同设备 token 间隔。

E2E latency#

从开始到最终完成的时间受到输出长度强烈影响。按输入、输出长度和任务类别分组，再比较分位数，避免长回答比例上升被误认为系统退化。

成功率与取消率#

分别记录入口拒绝、排队超时、设备错误、客户端主动取消和内容策略结果。响应状态码不是完整业务语义，返回 200 但流中断也不应被记成成功完成。

引擎层指标#

等待与运行序列、输入输出速率、块池占用、抢占重算、前缀命中和每轮耗时，可以把用户症状连接到引擎状态。指标命名随版本变化，先确认定义再聚合。

特别区分“本轮有执行”和“本轮交付了有效结果”。重算与反复抢占可能使设备很忙，但用户完成率不升。

同样 TTFT 上升，可能需要完全不同的行动#

若等待增长、执行速率稳定且设备饱和，考虑容量或入口负载；若输入执行随长度上升，考虑分桶与分块；若设备空闲而分词队列繁忙，查 CPU 与文本处理。三个现象都能产生同一条首字告警。

对正在生成的请求，再核对抢占与 ITL 尾部。总体 token 速率稳定并不能排除某个租户被长期推迟。

GPU 与系统指标#

设备执行、显存带宽、allocated 与 reserved、互联流量和硬件错误帮助解释资源。CPU、NUMA、磁盘及远端存储则解释供给和保存。把这些曲线与版本、运行和阶段事件关联，才知道某次尖峰对应什么工作。

同一图上不要混合无法相加的口径，例如把 allocator reserved 与驱动总占用当作两项独立内存。对每个指标写明层级、单位和采样周期。

Little's Law#

在符合稳定平均条件、边界一致的系统中，L = λ × W：平均在内数量等于平均到达率乘平均停留时间。

假设引擎每秒进入 6 条请求，平均停留 3 秒，平均在内约 18 条。它适合做量级检查，不会自动给出 GPU 数或尾延迟，更不能用平均值保证最坏情况。

Little's Law 的时间范围要对应同一个系统#

若 L 只计引擎内请求，W 就应是进入到离开引擎的时间，而非浏览器完整体验。到达率也要用相应边界的计数。持续过载、队列不断增长时，短窗口内的测量不满足稳定平均条件。

如果预测和观测差很多，先查边界、时间窗口与失败请求是否被漏计，再考虑更复杂模型。

SLO 不能只有一个数字#

可以为档案目录交互设一个教学合同：输入不超过 1500 token、输出不超过 300 token，按一个月统计，99.5% 成功完成；在对应流量类中，p95 首字小于 1.2 秒，生成间隔采用独立目标。数字只是示例，应由实际产品与压测决定。

明确是否排除主动取消，以及如何计入服务过载拒绝。长卷宗可单独进入异步类别，不能在坏结果出现后临时把它们从分母删除。

成本指标#

设备小时价格只是单价，实际成本还包括热备闲置、冷启动、存储、传输和失败重算。可分别计算每百万有效输入、有效输出以及每类成功任务的成本，并保留分母定义。

训练侧可以报告完成一定有效 token 的总成本，以及故障损失。不要把峰值吞吐换算成长期账单，而忽略保存与恢复。

成本分母也应该代表有用结果#

如果同一段输入因抢占计算三次，总处理量变大，却没有三倍业务产出。将重算位置计入有效交付，会让低效系统显得更便宜。应把实际消耗与去重后的有用结果分列。

为了首字目标保留热副本，可能提高低流量单位成本。比较两种容量策略时固定体验目标与流量，不让较慢策略靠违反 SLO 获得表面优势。

Cardinality 警告#

请求 ID、任意用户标识、完整提示词和动态字符串不宜直接作为 metrics label。高基数可能拖垮监控并泄露资料。受控日志和 trace 保存细粒度关联，指标使用有界维度，并配合保留与访问策略。

一张最小 Dashboard#

第一行显示到达、完成、拒绝和用户延迟；第二行连接等待工作、活跃状态、有效 token 与缓存压力；第三行看设备供给、错误阶段和版本变化；最后显示准备中的容量及单位成功成本。

每个面板应对应一个可执行问题，例如“增加副本是否有用”或“刚才发布是否改变了生成间隔”。若无法据此区分行动，就先补测量定义，而不是继续加图。

故障恢复：把失败当作正常路径

档案处理会遇到坏输入、进程异常、设备错误和半写入的保存状态。可靠性需要规定每类失败的处置边界，避免将一次局部问题放大成整组反复重启。

先划分故障域#

失败位置 首先保护什么 可能的后续动作
单条请求输入 其他请求的资源与延迟 明确拒绝或转异步
进程执行 首错现场与请求结果 清理或重启相应副本
协作组成员 组内一致性 终止并重建必要成员
GPU 或节点 不再把新工作送入故障点 标记、隔离和诊断
保存链 最近已知完整状态 不发布坏版本并回退
控制器 期望状态的最终收敛 重试幂等调和动作

这张表不是自动恢复算法。每个动作都需要触发条件和权限，破坏性设备重置或节点排空应遵守平台流程。

首错比连锁错误重要#

组内某个进程先失败，其他进程往往稍后才在同步处报错。统一 run、step、rank 标识，并保存首个异常及相关形状，能避免被最后一屏 timeout 带偏。

清理时出现的错误应作为附加信息，不能覆盖最初异常。重试前保存必要现场，否则下一轮可能只复现同一个模糊症状。

最后报错的进程，不一定是首先失败的进程#

假设 rank 5 在反向阶段出现非法数值并退出，rank 1 直到等待 collective 超时才报告错误。只看主进程会怀疑网络，查看 rank 5 的前置事件才能发现真正起点。

跨节点时钟可能有偏差，除时间戳外还要看 step 和事件依赖。先发生的业务阶段错误与后发生的依赖失败，不一定能靠孤立时间排序完整还原。

在线推理的重试#

首个输出之前失败与已经输出半段答案不同。后者重试可能产生重复文本或另一份续写，应向客户端传递 attempt 与结果状态。外部工具写入还需业务幂等键和结果查询，不能由模型生成重试策略保证安全。

客户端、网关和后端应共同限制重试预算，并采用退避。三层各重试几次会相乘放大流量，尤其在容量不足时容易使故障持续更久。

训练恢复#

先停止或重建一致的协作组，再选择最近完整且兼容的状态，加载参数、优化器、数据与随机状态，最后做小步验证。若改变并行布局，先确认格式和运行时支持所需重分片。

恢复完成条件应包括可继续更新和可再次保存。只把进程启动起来，仍可能在下一次 collective 或 checkpoint 暴露不一致。

恢复的第一步，是找到完整且匹配的状态#

最新目录可能属于未完成尝试，需根据提交记录与 metadata 选择。模型配置、数据版本和代码兼容同样重要，否则完整文件也可能不适合当前运行。

演练应包括缺失一个 shard、旧格式状态和成员替换。明确哪些组合支持恢复，哪些必须回滚环境或转换格式，避免事故中临时试错。

Operator Reconciliation#

控制器比较期望与观测，再补足差异。例如期望两组就绪副本而实际只有一组，就创建或修复缺失组。重复执行应能收敛，而不依赖控制器一直记得某条命令是否完成。

status 和清理机制帮助表达长期动作进度。但这种幂等收敛不适用于任意业务动作，重复发送通知或提交外部交易需要自己的去重协议。

GPU 健康与隔离#

持续设备错误时，记录设备 UUID、错误码和受影响运行，再按流程阻止新工作落入该设备或节点。收集诊断后决定维修、重置或替换，验证通过才解除隔离。

插件上报健康状态是信号之一，平台仍需明确负责人和节点处置。若仅重启容器，新副本可能再次落到同一故障点。

控制器可以重新创建 Pod，不能直接重放业务#

控制器让缺失副本重新存在，不代表之前的读者已收到完整答案，也不代表外部操作尚未发生。恢复组件后，还需要完成请求、计费和工具结果的业务收尾。

设备恢复也不能以 Running 结束验收。至少确认代表性执行和必要通信正常，再逐步恢复流量，避免坏卡在重启循环中不断消耗新任务。

Runbook 最少包含#

写清可见症状、分类步骤、现场采集以及安全缓解动作。每个动作标出会中断什么、可能损失多少进度、怎样撤回和何时升级处理。

例如“停止给一组路由并保留运行日志”与“重建整组并回退保存点”有不同影响，不应混成一句重启建议。演练后更新实际恢复时间与遗漏检查，让手册能被另一位值班人员执行。

端到端：设计一个小型 AI 平台

将前面的机制合成一份档案馆平台草案。假设有 16 台服务器，每台 4 张同规格 GPU，白天提供问答，夜间进行校对训练。所有容量与目标都是教学设定，尚未在真实集群验收。

第一步：定义负载#

交互目录请求输入大多在 1500 token 以内，输出通常不超过 300；长卷宗另走异步入口，避免其延迟目标与交互混用。候选首字目标为 p95 小于 1.2 秒，入口允许有界拒绝。

训练提供 4、8、16 GPU 三种模板，允许有条件抢占，要求能保存并恢复数据位置。数据与检查点使用远端存储，节点可保留缓存。先确认这些合同，再选择组件。

六十四张卡，不等于六十四张随时可借的卡#

部分设备必须给在线热容量，维护和故障也要留余量。训练即使可以借用夜间空闲设备，也需要约定白天回收通知、保存时限和不响应时的处理。

先列受保障池、可借池与隔离池，再统计满足拓扑的可用组。总卡数相同，分散空闲与完整节点空闲对 gang 的意义不同。

第二步：节点层#

固定驱动、运行时、设备插件与监控组合，建立设备和互联标签。验收包括单卡执行、节点内外通信、存储读取以及设备错误上报，不只检查系统能识别卡。

把模型和数据缓存视为可失去的加速层，远端保留权威来源。缓存失效或节点替换后，平台仍需能重新建立可运行状态。

第三步：训练队列#

使用支持作业级准入的调度能力管理组、队列与优先级。三个模板分别约定成员数、每成员设备、网络和 checkpoint 行为，避免用户自行拼接复杂 affinity。

抢占能力要通过实际保存与恢复演练。平台不能只因为发得出终止信号，就向调度策略声明任务可安全抢占。

第四步：推理服务#

先用教学 3B 模型建立单卡基线，确认实际显存余量与延迟，再考虑复制更多副本。每个副本使用合适的缓存和连续批处理，网关施加租户与长度边界。

若模型装不下才研究必要分片；若单卡已满足容量但总吞吐不足，独立副本可能更直接。不要为使用全部卡数而引入额外协作。

用两种流量找到第一版副本工作点#

分别重放目录快问和长卷宗输入，逐步提高到达率，记录首字、ITL、有效速率和 KV。以满足相应目标的最高稳定区间作为候选，不拿过载峰值作为承诺。

再混合两类并注入一个副本退出，观察入口是否有界、剩余副本是否被重试压垮。容量表应说明故障余量，而不是只列正常时均值。

第五步：扩缩容#

最小热副本承担低流量体验，等待工作和预测流量触发提前准备。模型下载与预热有并发上限，准备中的副本不计入可接流量容量。

缩容前先退出路由，再排空或到期终止。若夜间要回收设备给训练，必须把排空时间与训练准入窗口一起规划。

第六步：可观测与成本#

每次问答可追溯模型版本、长度、阶段等待和结果类别；训练可追溯数据、代码、mesh 和保存点。细粒度标识进入受控日志，有限维度进入指标。

定期比较体验达成率、有效交付成本、排队来源与失败回退量。若成本下降来自拒绝更多困难请求，应在同一份结果中显式显示，而非包装成单纯优化。

用本地实验室算第一版容量#

python3 examples/infra_lab.py memory \
  --parameters 3 --weight-bits 16 \
  --layers 24 --kv-heads 4 --head-dim 96 \
  --context 6144 --concurrent-requests 6
python3 examples/infra_lab.py simulate
python3 examples/infra_lab.py check

权重与逻辑 KV 小计约 6.85 GiB，仍需工作区、块浪费和运行时。若该下界已超设备容量，就无需先做昂贵部署；若低于容量，也只是值得继续验证。

模拟器能检查预算与生命周期，不能给出每副本真实到达率。工作点仍需在目标硬件上用代表性输入实测。

上线顺序#

先验证单卡正确性与固定形状，再扩大到真实长度分布。随后增加副本或必要并行，演练保存、故障和排空，再接小流量并逐步开放扩缩容。

每阶段只改变能解释的因素，保留已知可用配置。若同时换模型、量化、引擎和拓扑，即使结果退化也很难定位责任项。

最小平台也要演练一条完整失败路径#

中断一个训练成员，核对整组退出、完整保存点选择、数据位置恢复以及下一次保存。让一个推理组退出接入，检查旧流结束与新流分配，并测剩余容量是否还能兑现目标。

记录恢复时间、损失步骤、重复请求与人工动作。这些结果比“已安装高可用组件”更接近平台可恢复性的证据。

最终架构原则#

采购依据是字节和实测工作点，布局依据是实际通信路径，扩缩依据是可兑现的用户等待。少量模板只要能解释启动、运行、保存和失败，就比大量未经演练的配置更适合作为第一版平台。

推理术语#

Prefill 处理已知输入并建立历史，decode 使用历史逐步续写。KV cache 保留各层历史 key/value，分页将其逻辑位置映射到物理块；连续批处理则在轮次间改变被执行的请求集合。这几个术语分别描述计算、状态、分配和调度，不宜互相替代。

TTFT 关注开始输出之前，ITL 关注相邻输出间隔，TPOT 描述生成阶段的平均口径。前缀命中省去部分已知输入计算；抢占则可能暂时释放资源并在之后重复计算。两者对延迟的影响方向不同。

并行术语#

方式 工作归属变化 需要检查的代价
DP 不同副本拿不同数据或请求 训练梯度一致性与副本容量
TP 一层内的矩阵被拆开 层内频繁交换和小矩阵效率
PP 不同 stage 负责不同层 激活交接、失衡与起止空泡
CP 序列位置分给参与者 注意力跨位置所需交换
EP 专家分布在不同设备 token 分发及专家热点
FSDP 训练状态分片驻留 按需组装、梯度归约与保存格式

显存公式#

权重#

参数个数 × 每参数位数 ÷ 8 给内容字节下界。例如 30 亿参数、8 位约为 2.79 GiB，未包含尺度、对齐与未量化部分。

KV Cache#

常规同配置全注意力模型可用 2 × L × Hkv × D × 元素字节 × 保留位置数。本书的 24 层、4 个 KV head、96 维、2 bytes 得每位置 36 KiB。分页容量、共享与混合架构须另算。

常见混合精度 Adam 教学估算#

一种示意配置为每参数 2 + 2 + 4 + 8 = 16 bytes，分别对应低精度参数、梯度、主参数与两份 moment。30 亿参数约 44.70 GiB，不含激活和临时空间；实际以状态 tensor 为准。

Global batch#

在简单同步 DP 条件下，每数据副本 micro-batch × DP 度 × 累积次数。3 份样本、4 个副本、5 次累积得到 60 份。TP、PP 不额外贡献独立样本。

Little's Law#

L = λW 要求平均边界一致，并在适当稳定条件下使用。每秒 6 条进入、平均停留 3 秒，对应平均在内 18 条，不是 p99 或设备需求保证。

建议的源码阅读顺序#

vLLM 请求执行#

从 entrypoints/openai 找请求如何成为引擎输入，沿 v1/engine/llm_engine.py、v1/engine/core.py 到调度器。随后检查 v1/core/kv_cache_manager.py 的资源行为，以及 v1/worker/gpu_model_runner.py 怎样消费调度结果。

带一条会等待、推进并最终取消的请求，记录它跨边界时哪些字段发生变化，再深入模型实现。

TorchTitan 训练#

以 train.py 或对应训练引擎定位更新边界，接着查数据组件、并行维度、模型 parallelize、优化器和 checkpointer。每个模块都标注在当前步骤的什么时候运行，哪些状态会跨步延续。

Megatron 多维并行#

先画 parallel_state.py 形成的组，再读 tensor_parallel 和 pipeline_parallel 的数据映射。模型配置可在 transformer/transformer_config.py 核对，分布式状态相关实现再进入 distributed。

NCCL#

先理解公共操作的输入输出合同，再跟随 enqueue、拓扑规划和 transport。只有需要分析具体设备执行时才深入 device 代码，否则容易丢掉“谁需要从谁得到什么”的原始问题。

Kubernetes GPU#

沿 cmd/nvidia-device-plugin 到 internal/plugin 与资源发现模块，区分发现、注册和 Allocate。另用 kubelet 与调度器职责补全节点选择过程，避免把插件误读为集群调度器。
