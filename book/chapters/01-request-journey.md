# 一条请求穿过哪些系统

用户点击发送后，GPU 并不会立刻开始计算。请求通常要经过网关、服务副本、引擎队列、tokenizer、调度器和 GPU worker。集群控制面则在旁边保证这些组件存在于合适的机器上。

## 数据面：请求真正走过的路

### 1. 网关

网关处理 TLS、身份、限流、配额和路由。它不应理解 GPU kernel，但需要知道模型名、租户和请求大小，以便拒绝明显超限的输入。

### 2. API 服务

服务副本解析 OpenAI 兼容请求或内部协议，应用 chat template，并把文本变成 token IDs。tokenizer 主要在 CPU 上工作。高并发时，CPU tokenizer 也可能成为瓶颈。

### 3. 引擎调度器

调度器维护等待和运行中的序列，决定本轮处理谁、处理多少 token、分配哪些 KV block。vLLM 当前源码中，`EngineCore`、`Scheduler` 和 `KVCacheManager` 分别承担运行核心、请求调度和 KV 资源管理。

### 4. GPU worker

worker 加载模型并执行 kernel。单卡时它是一个 GPU 进程；张量并行时，一次逻辑推理需要多个 rank 协同。任何一个 rank 卡住，整体步骤都可能等待。

### 5. 流式回传

生成 token 经 detokenize 后成为文本增量，再穿过服务与网关回到客户端。客户端看到“流式”，不代表 GPU 每生成一个 token 就发一个独立网络包，中间层可能聚合或缓冲。

### 请求进入副本，不等于已经得到 GPU 时间

假设用户发送一篇长文。网关检查身份与长度，API 将文字转成 token，调度器才判断这一轮是否有 token budget 和 KV block。连接已经建立、服务也健康，请求仍可能在引擎等待。若只测 HTTP 建连时间，就会漏掉用户实际感受到的等待。

GPU worker 处理完成后，输出还要经过采样、文本解码和网络缓冲。用户一秒没有收到文字，可能是模型慢，也可能是回传被缓冲。排查时记录各层时间，而不是把最后可见的卡顿全部归给 GPU。

## 控制面：谁让服务存在

Kubernetes 或其他调度系统负责选择节点、创建 Pod、挂载模型和重启失败实例。Device Plugin 把节点 GPU 注册成可调度资源。Operator 将“我要一个推理集群”翻译成 Deployment、Service、配置和状态调和。

控制面通常不参与每个 token 的热路径，但它的决定影响数据面：

- Pod 被放到没有高速互联的 GPU 上，张量并行会变慢；
- 模型下载没有本地缓存，冷启动会很长；
- 健康检查太激进，长 prefill 可能被误判为卡死；
- 扩容只看 GPU 利用率，排队已经上升却不触发。

## 两个调度器

这是全书最重要的区分之一。

| 调度层 | 调度对象 | 时间尺度 | 典型约束 |
| --- | --- | --- | --- |
| 集群调度器 | Pod、节点、GPU | 秒到分钟 | 数量、拓扑、队列、优先级 |
| 推理调度器 | 请求、序列、token | 毫秒级迭代 | token budget、KV block、抢占 |

请求排队可能发生在网关、服务副本或引擎内部。只看 Kubernetes Pending Pod 无法判断用户为何等待，只看 vLLM 队列也看不到集群是否缺卡。

### 两个调度层可以分别健康，整体仍然慢

集群已经给副本分配足够 GPU，但长请求占满 KV，新请求会在引擎里排队。反过来，引擎参数合适，扩容 Pod 因无卡 Pending，增加引擎 token budget 也不能创建新容量。前者要查活跃序列和内存，后者要查资源与拓扑。

控制面修复通常需要秒到分钟，token 调度却每轮都发生。扩容决策必须有提前量，不能指望创建 Pod 像移入一个短请求一样即时完成。

## 第一个排障方法：画时间线

一次请求慢，先拆成：

```text
网络与网关 -> 服务排队 -> tokenize -> 引擎排队
-> prefill -> decode 多轮 -> detokenize -> 网络回传
```

给每段打时间戳，不要先猜 GPU 不够。短请求的延迟常被排队和框架开销主导，长生成才更可能由 decode 主导。

## 离线与训练路径有什么不同

批量推理可以提前分桶、容忍更长等待，目标偏总吞吐。训练没有逐请求网关，但多了数据加载、反向传播、优化器和 checkpoint。两者共享 GPU、通信和存储基础，调度目标却不同。

### 训练为什么没有网关，仍然会等待

训练 step 先等数据 batch，再做计算和通信，周期性还等待 checkpoint。用户请求队列消失了，但数据队列和 rank 同步依赖仍存在。吞吐低时，沿 batch 从存储到 GPU 的路追踪，和沿在线请求追时间线使用的是同一种方法：找出谁已经准备好、谁还没准备好。
