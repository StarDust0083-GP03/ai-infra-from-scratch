# 一条请求穿过哪些系统

读者请求“比较两份航海日志里的气压记录”。系统已经接受连接，屏幕却迟迟没有文字。这个现象至少涉及接入、分词、引擎等待、模型计算与回传，不能仅凭客户端计时判断是哪一层忙。

## 数据面：请求真正走过的路

### 1. 网关

入口为读者确认身份，检查可用模型与额度，并把请求送到适当副本。限流应同时考虑请求条数和输入大小。十个短问题与十份长篇档案的工作量差异很大，仅按连接数限流会掩盖后者的压力。

### 2. API 服务

服务将角色消息套入目标模型的聊天模板，再分词形成整数序列。模板版本也会改变 token 数，因此预估长度和最终入队长度可能不同。若 CPU 分词已经积压，增加 GPU 的调度预算并不能消除这段等待。

### 3. 引擎调度器

一份输入只有同时满足本轮计算预算、序列上限和 KV 空间条件，才有机会被选中。vLLM 的 `EngineCore` 驱动引擎循环，`Scheduler` 决定工作分配，`KVCacheManager` 管理相关内存资源。它们操作的是请求状态，不负责给 Kubernetes 分配节点。

### 4. GPU worker

worker 根据调度结果执行模型。采用张量并行时，多张卡共同完成一个逻辑步骤；不能把它理解成每张卡独立回答一位读者。某个参与者尚未到达通信点，其他参与者即使计算完成也可能继续等待。

### 5. 流式回传

采样后的 token 经文本解码形成增量，经应用协议返回浏览器。一个 token 可能只构成半个可显示片段，代理也可能合并若干增量发送。应分别记录设备生成时间和客户端收到时间，检查缓冲造成的间隙。

### 请求进入副本，不等于已经得到 GPU 时间

假设教学轨迹中，请求在 0 ms 被入口接受，18 ms 分词完成，直到 96 ms 才进入第一次模型执行。18 到 96 ms 的 78 ms 属于引擎排队。服务的存活检查全部正常，也不会使这段等待消失。

若设备在 140 ms 已生成首个可用片段，而浏览器到 200 ms 才显示，另有 60 ms 位于设备之后。应检查文本拼接、应用刷新和反向代理缓冲，不能把这 60 ms 再记为 prefill。

## 控制面：谁让服务存在

副本运行前，需要节点、设备、模型文件和网络服务。控制器根据期望状态创建或修复这些资源，调度器挑选合适节点，Device Plugin 协助 kubelet 暴露设备。准备过程发生在请求热路径之外，却决定副本是否真正可接流量。

例如新副本已经处于 Running，但仍在读取权重。若此时过早宣布 Ready，入口会把读者送入一条尚不能执行的路径。反过来，存活探针若把正常长初始化误认为死锁，会使加载永远无法结束。

## 两个调度器

| 决策问题 | 执行者 | 可观察结果 |
| --- | --- | --- |
| 哪个节点承载这组进程 | 集群调度层 | Pod 被绑定或继续 Pending |
| 这轮给哪份输入多少计算份额 | 引擎调度层 | 请求被执行、暂停或留在队列 |

前者面对 GPU 数量、标签与拓扑，后者面对 token 和 KV 块。两个等待队列应分别测量；把它们统称“服务排队”会使扩容和调参混在一起。

### 两个调度层可以分别健康，整体仍然慢

档案馆有两个空闲节点，但引擎副本数固定，空闲卡不会自动参加现有副本的计算。另一种情况是全部副本都已就绪，却被长上下文占据 KV，入口仍不断积累请求。第一种需要改变服务容量，第二种要检查负载和引擎资源边界。

引擎的一轮选择能很快改变；创建新副本还要等待设备与权重。扩容应基于未来一段时间的压力，并配合有界排队，不能把控制面的动作当作即时救援。

## 第一个排障方法：画时间线

为同一请求 ID 记录入口接受、分词完成、首次被调度、首个生成片段、最后生成片段和客户端结束。计算相邻时间点的差，而非把每层各报的“总耗时”相加，后者可能重复计算重叠区间。

上例中的 78 ms 排队可以与活跃 KV、等待 token 一起查看。若分词耗时增长而引擎空闲，则应回到 CPU 和输入处理链。时间线让优化动作对应到一段可验证的等待。

## 离线与训练路径有什么不同

夜间批量整理档案时，任务可以按长度分桶，延后短任务的交付换取更好的设备复用。训练则用数据 batch 驱动，不逐条等待读者提问，还会进行反向计算、参数更新和状态保存。它们共享设备，却不应沿用同一组用户延迟目标。

### 训练为什么没有网关，仍然会等待

如果校对数据尚未从对象存储读出，GPU 会等待下一批；若一个 rank 读盘较慢，同步训练中的其他 rank 还可能在 collective 处等它。应把数据可用、计算开始和同步结束画到各 rank 的泳道上，才能区分慢网络和慢输入。

## 源码入口

从 `vllm/v1/engine/core.py` 追请求进入引擎，再看 `vllm/v1/core/sched/scheduler.py` 如何产生本轮工作。涉及块的申请和释放时转到 `vllm/v1/core/kv_cache_manager.py`。准备设备的代码则在 `k8s-device-plugin/internal/plugin/`，服务调和可从 `kuberay/ray-operator/` 查起。读这些路径时，以同一对象的创建、使用和释放串联调用关系。
