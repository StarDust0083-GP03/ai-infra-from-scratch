# 多卡不是一个开关

夜间校对模型装不进一张卡，白天问答又需要更多吞吐。这是两类需求：前者可能要拆开一个模型，后者可能只要复制更多独立副本。先确定切分对象，才能知道哪些卡必须共同参与同一步。

## 数据并行 DP

不同副本处理不同样本或请求。在线推理时，副本通常独立完成自己的请求，主要扩大总服务能力；同步训练时，各副本在更新前还要对梯度达成一致。

每个未分片副本仍需完整模型。因此增加 DP 不能解决单份模型装不下的问题，训练中还要为梯度同步付出通信成本。

## 张量并行 TP

把同一层的矩阵运算拆给多个参与者。每张卡产生完整逻辑结果的一部分，中间需要按算子布局进行归约或收集。它减少部分每卡权重和计算，却增加频繁的层内通信。

矩阵尺寸、注意力头和 kernel 对划分有具体要求。TP 越大，每张卡的工作可能越小，通信与启动成本占比反而升高，因此不是越多越快。

### 两卡切矩阵，与两卡各跑请求有什么不同

设输入长度为 6，矩阵输出宽度为 10。把输出列切成两组，每卡得到宽度 5 的结果，后续计算需要按布局组合，单个请求离不开双方。若两卡都保留完整宽度 10 的矩阵，各处理不同日志，则是独立副本。

故障影响也不同：前者丢一张卡会破坏这个逻辑副本，后者通常只损失一个独立服务者。部署与健康检查要按实际副本边界设计。

## 流水线并行 PP

把层划为多个 stage，激活依次传递。每个 stage 只保留自己的层，但单条数据仍要经过完整顺序。多个 micro-batch 可交错填流水线，开始和结束阶段仍会有空泡。

选择 stage 时既看参数大小，也看实际计算耗时。均分层数不保证均分工作，嵌入、输出头和不同层结构都可能造成失衡。

## 上下文并行 CP

超长序列可以沿位置维度拆分，使每个参与者保存或计算部分序列。注意力仍需获得跨分片的信息，因此需要专门交换与计算组织。它并非把一句话机械拆成几个互不相关的小问题。

具体能减少哪些激活或 KV、怎样通信，要核对目标框架和模型实现，不应凭名称推导全部状态都均分。

## 专家并行 EP

MoE 将专家分布到不同设备，router 决定 token 发往哪些专家，执行后再组合结果。常见传输涉及 AllToAll 类型的数据分发。

如果很多 token 集中到少数专家，某些设备会成为热点，其他设备即使有空也要等待。容量评估应包含实际路由分布与失衡，而非只用平均专家负载。

## 并行可以组合

简单的 DP、TP、PP 布局可用三个坐标表达。例如 `(数据副本, stage, 张量分片)` 确定一个 rank 的职责。长序列和 MoE 加入后，维度的依赖与分组规则由框架决定，不能不加条件地相乘所有缩写。

先列每张卡保存哪些参数、处理哪些样本，再列它属于哪些通信组。随后把这些组映射到节点内外的真实链路。

### device mesh 的坐标决定谁和谁通信

假设 DP=2、TP=2，每个副本内部的两卡执行层内通信，两个副本中对应分片还可能在训练中同步。编号连续只是命名，不能保证物理上相邻。

把频繁通信的 TP 组放到快链路内通常更合理，但仍要实测。设备数量满足乘积只是必要条件，拓扑和显存峰值同样约束布局。

## 一个 8 卡例子

考虑教学模型含 180 亿参数，16 位权重下界约 33.53 GiB，目标卡各有 24 GiB。单卡放不下，理想 TP=2 时每卡权重约 16.76 GiB，剩余还要容纳缓存与工作区。

八张卡可以候选组成四个两卡副本，但这只是待测试布局。若组内互联差，或长输入峰值超过余额，仍需调整并行、精度或负载。图中的八卡不对应特定产品。

## 推理与训练的同名差异

训练往往用规律 micro-batch 持续执行，在线服务则不断接入、退出和改变长度，还要保护用户延迟。相同 TP 和 PP 名称不会使两者拥有相同最佳参数。

训练可用许多 micro-batch 填流水线；在线单请求的每个生成位置都需经过各 stage，其逐 token 延迟可能不理想。应分别评估吞吐与单请求体验。

### 只做权重除法会漏掉通信和峰值

上例每卡 16.76 GiB 只是理想权重分摊。某些参数或状态可能复制，层内归约还需 buffer，缓存能否均分也依赖实现。加载成功后，还需测长上下文、批次峰值与必要 collective 的时间。

若增加卡后更慢，检查每卡工作是否变得过小、通信频率是否过高，或 stage 是否不平衡。继续增加同类资源可能放大原来的等待。
