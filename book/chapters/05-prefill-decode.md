# 推理的两幕：Prefill 与 Decode

读者给出一份日志，要求生成一句日期摘要；另一位只给一个题目，却要生成长篇目录。它们分别把工作集中在读取和续写阶段，不能只用总 token 数判断执行体验。

## Prefill 做什么

模型先处理已有输入，在各层形成后续生成需要的 K/V。输入的多个位置可以组织成较大的矩阵工作，通常具有较多并行机会。因果掩码仍然约束每个位置可读哪些前文，批量处理并未允许它看到未来答案。

首字时间还包括接入、分词和调度等待。若长卷宗的 prefill 实际只占首字等待的一小部分，继续优化这一段会遇到明显收益上限，应先按请求时间线拆解。

## Decode 做什么

后续新位置依赖先前已经选出的 token。每轮用新位置的输入和已有缓存完成模型计算，再采样决定下一个 token，直到停止标记或长度上限。多个请求可以一起推进，但单条序列的生成依赖仍在。

相邻输出间隔可以用 ITL 的分布描述，单请求平均生成时间可用 TPOT 描述。若输出超过一个 token，常见计算口径为 `(最后 token 时间 - 首 token 时间) / (输出数 - 1)`，具体看测量工具定义。短输出不适合盲目比较这个平均数。

### 读取长题目和续写长答案，是两种压力

设教学负载甲有 6000 输入、80 输出，乙有 300 输入、1800 输出。甲可能在开口前花较多时间；乙可能很快开始，却连续占据许多生成轮次。相同总耗时也可能呈现完全不同的用户感受。

把请求按输入和输出二维分桶，能看出首字与持续生成分别受谁影响。仅按总长度分桶会把这两种负载混在一起。

## 为什么不能只优化一个阶段

正在生成的读者希望下一片段准时到达，新来的读者希望尽快开口。若本轮给新长输入过多计算，已有生成可能被推迟；若一直照顾生成，新输入会在队列里等待。

产品需要分别指定首字和生成间隔目标，并考虑长输入不能永久挨饿。调度器只能在这些目标和资源边界之间取舍，无法通过单个 batch 参数同时消除所有等待。

## Chunked Prefill

引擎可把长输入分几轮处理，让尚未完成的输入工作与生成共同使用每轮 token 预算。这样能控制单轮工作量，代价是更多调度边界以及长请求跨轮驻留。

例如 `max_num_batched_tokens` 影响每轮可处理的位置数，而不直接给出这一轮耗时。相同 token 数放在不同模型和形状下，执行时间仍会变化，需要测量而不能把预算当作毫秒限额。

### 切小 prefill 怎样帮助正在生成的用户

假设本轮有 6 条生成序列，各需推进 1 个位置，另有 960 个输入位置待处理。预算设为 102 时，先为生成分配 6，再给输入 96。输入大约需要十次这样的份额才能读完，期间生成有机会持续推进。

这只是调度账，没有声称一轮固定多长。若极小分块引入很多管理和执行开销，总吞吐可能下降；应测首字改善是否值得这些成本。

## Prefill/Decode 分离

分离部署把输入处理和持续生成安排到不同工作组，完成输入处理后再交接历史状态。两边可以采用不同并发和扩缩策略，但也引入状态传输、配对路由和交接失败的处理。

采用前应证明混合执行确实造成干扰，并测量交接后的排队。负载较低时，两组分别空闲可能比一个共享池更浪费，新增链路也会增加运维复杂度。

## 一个简单类比

整理档案时，先为一份日志建立索引，再根据索引逐条写注释，类似两类不同形状的工作。这个类比只说明先读取、再依赖历史推进，不能用来推导注意力运算或真实内存占用。

### 分离前先算 KV 交接的成本

沿本书模型，6144 个位置、每位置 36 KiB，交接约为 216 MiB 的逻辑 KV。若可用链路吞吐仅 3 GiB/s，忽略其他开销的传输下界也约为 70 毫秒。传几个 token ID 无法替代这份历史状态。

还需加入源端整理、目标端分配、网络竞争和失败清理。只有独立调度节省的等待与计算超过这些代价，分离才可能带来净收益。

## 观测建议

给每条请求保留输入长度、输出长度、入队等待、输入阶段执行时间和生成间隔。标注是否分块、是否命中前缀缓存以及是否发生状态交接。这样才能区分“读取变快”“不再排队”和“后续写得更平滑”三种不同改善。
