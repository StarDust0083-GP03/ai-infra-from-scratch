# 连续批处理：GPU 如何同时服务很多人

目录查询只需几个输出位置，档案摘要可能要生成几百个。若整批请求必须等最长的一条结束才换人，已经完成的短任务会留下不可利用的空位。连续批处理在执行边界重新选择工作，让这些位置及时被接替。

## iteration-level scheduling

每轮开始，引擎根据上轮结果移出已完成项，评估等待项，安排新的输入或生成位置。随后分配缓存、组装设备输入，执行后再更新长度和停止状态。

这个循环对单条序列仍遵循自回归依赖，但批次成员可以改变。所谓“动态”体现在每轮重组，不是把一个 HTTP 请求重复提交给多个副本。

## 三个约束

### Token budget

本轮处理的位置总数有上限。已有生成序列通常各贡献一个新位置，一段输入块可能贡献许多位置。预算限制的是工作数量，并不保证各轮耗时相同。

### Sequence 数量

同时维护的序列数影响 metadata、调度和状态容量。即使本轮 token 尚有预算，达到序列数上限后也可能不能接纳新请求。监控要分开显示两个计数。

### KV block

执行新增位置前，需要有相应缓存空间。尾块可用槽位与是否需要领取新块也有区别。KV 受限时，增加 token 预算未必能带来任何进展。

### 这一轮有 token 预算，为什么还是进不了新请求

假设本轮预算 48，已有 5 条生成序列，占用 5 个位置。等待中的输入可取 24 个位置，但块池只剩一块，无法容纳它所需的全部新块。剩余 43 个计算名额并不能代替内存。

已有请求结束并归还可回收块后，新请求才可能进入。还要检查共享引用或缓存保留，不能把逻辑结束数直接当作立刻释放的物理块数。

## 策略不是只有 FIFO

到达顺序容易解释，却未必满足所有延迟目标。短任务优先可能改善平均完成时间，代价是长卷宗等待更久；优先保障正在生成的请求，则可能推迟新读者的首字。

为避免高优任务持续涌入导致饥饿，可以设置等待老化、配额或保留份额。具体规则属于产品合同，应通过可重放请求序列验证，而不只把参数写成“高优”。

## 为什么吞吐和延迟会冲突

更大的批次可能提高权重复用，但为凑批新增的等待会进入用户延迟。低到达率下，等待凑满往往比实际计算更久；高到达率下，积压本身又会形成大批次。

有效工作点应满足目标长度分布下的首字、生成间隔和成功率，再比较吞吐。不能先把设备灌满，再用最大输出速度代表所有流量。

### 最大吞吐实验为什么不代表真实等待

封闭式固定并发测试中，一条结束立即补一条，到达节奏随服务完成而变化。开放式固定到达率测试则可能不断积压。两种测试回答的问题不同，应记录采用哪一种，并检查是否存在遗漏过载等待的测量偏差。

例如平均到达很低却偶有集中导入，稳定阶段高吞吐不足以证明突发首字达标。应保留突发形状和队列长度曲线。

新版实验用“目录快问、日志摘录、长卷校对”等虚构请求，记录逐轮处理位置与块占用。轮数只比较调度规则，不换算真实时间。

尝试减少块数并保持 token 预算不变，观察请求为什么等待；再增加预算，检查是否仍受同一块池限制。若没有任何序列可以推进，程序应明确报告资源条件，而不是无限空转。

## vLLM 源码地图

`vllm/v1/core/sched/scheduler.py` 组织调度选择及输出，`vllm/v1/engine/core.py` 把选择与执行、结果更新连起来，`vllm/v1/worker/gpu_model_runner.py` 处理设备侧输入和执行。三者之间的数据对象比某个单独函数名更值得追踪。

### 读调度源码时追一条请求的资源变化

从等待请求开始，记下选中时已处理长度、本轮分配位置数与新增块数；执行结果返回后再检查长度是否前进，停止时检查资源如何退回。若选中却无进展，查执行或更新；若完成后占用不降，查释放及缓存引用。

模拟器也应遵循这些不变量，但它没有设备输入布局、通信或真实 kernel，不能代替引擎性能实验。

## Benchmark 应记录什么

为每次实验固定模型与精度、模板、输入输出分布、到达方式、并发上限、每轮预算、块池和缓存策略。结果同时给出完成请求速率、有效输入输出 token 速率及延迟分位数。增加重试、拒绝和取消统计，防止靠丢弃困难请求获得漂亮平均数。
