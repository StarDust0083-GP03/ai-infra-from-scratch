# 在线服务：网关、队列、副本与扩缩容

开放档案问答后，工作量会随着读者人数、日志长度与生成要求变化。可靠服务需要在接入前限制不可能完成的工作，在副本间分配负载，并为缓慢启动的新容量留出时间。

## 数据面组件

### Gateway

入口建立身份与额度边界，验证输入和输出上限，并选择模型。应尽早拒绝明显不支持的长度，避免让请求排了很久后才发现无法运行。拒绝结果也要有明确可重试语义。

### Replica

逻辑副本提供一份可服务能力，可能包含前端与一个设备工作组。副本数、Pod 数和 GPU 数没有固定一一对应，应在拓扑图中写出实际关系。

### GPU Worker Group

一个 TP 或 PP 副本可能依赖多个进程。就绪检查应确认必要参与者可以共同执行，而不是只检查前端端口。单个坏 rank 可能影响这组中的全部请求。

### Queue

有界队列可以吸收短突发，但等待本身要计入用户预算。长度、等待时限、租户份额和过载策略都应显式配置。无限排队会把容量不足延迟成大规模超时。

## 路由的三个层次

先确定请求允许使用哪个模型或 adapter，再挑选就绪副本，最后由该副本的引擎选择本轮执行。模型权限、整体负载和 token 调度对应不同层，不宜塞进一个模糊的“智能路由”概念。

副本选择可考虑剩余工作、KV 压力和可复用前缀，但采集状态有延迟。多个路由器同时选择看似最空的副本，也可能瞬间制造热点。

### 两个副本排队条数相同，剩余工作也可能不同

假设两个副本各等待三条请求，甲的输入合计 600 token，乙的合计 12,000 token。仅按请求数它们相同，实际输入工作显然不同；还需加上正在生成的历史状态与预期输出。

缓存亲和可能节省输入计算，却也可能把同类请求集中到一处。应测“命中收益减去新增等待”的净效果，而不是追求最高命中率。

## Autoscaling 看什么

可以把等待 token、首字分位数、活跃状态和完成能力作为主要信号，再结合设备与 CPU 指标解释原因。设备利用率低可能是需求少，也可能是输入或通信供给不畅。

扩缩决策需迟滞和稳定窗口，避免短抖动反复创建与删除昂贵副本。就绪容量与正在准备容量应分列，否则 replicas 上升会被误认为用户已经获得帮助。

## 冷启动决定提前量

假设教学部署下载、加载和预热合计需要 5 分钟。若到首字目标已经失守才申请新副本，现有突发不会被立刻吸收。可以维持最小热容量、提前在候选节点缓存模型，并按周期需求预扩。

同时限制准备并发，防止所有副本争抢同一远端存储。扩容链的最慢阶段可能随并发而变化，应测从申请到可接真实请求的完整时间。

### 扩容来不及的时候，队列必须有上限

若用户可接受等待只有数秒，新副本要几分钟才能就绪，当前过载必须通过限流、降级或转异步处理应对。无限接收只会把未来几分钟的工作堆成无法兑现的承诺。

拒绝策略应考虑租户公平和客户端退避，避免一个同步导入任务占尽全部交互队列。扩容解决后续容量，不替代当下的入口保护。

## KubeRay 与 Operator 模式

KubeRay 用 RayCluster、RayJob、RayService 等对象管理 Ray 相关生命周期。需要 Ray 分布式运行时的方案可以利用它表达期望与调和；单机模型副本则可能用普通 Deployment 就能满足需求。

选用控制器应基于明确生命周期问题，如整组准备与版本切换，而非因为项目名称里带 AI。新增控制层也意味着新的升级与排障职责。

## 滚动升级的 drain

新组完成验证后逐步接入，旧组先退出接入集合，再等待已有生成结束或触及 deadline。超过期限时应明确返回失败和重试语义，不能默认已流出文本会被新组无缝续写。

保留旧版本产物与回退配置，并确认更新期设备容量足够。切换成功不仅是新副本出现，还包括旧连接得到一致处理。

## 容量规划的单位

将输入与输出长度分开，按代表性类别测每副本可承受的到达率和延迟。请求速率仍有业务意义，但无法脱离长度与成功率单独描述资源需求。

一份副本容量表应给出达到目标的工作点，而非只列灌满时的峰值 tokens/s。还需保留至少一种故障或突发余量假设。

### 缩容为什么要先停止接新请求

准备删除的副本若仍接新工作，排空时间会不断向后推。停止接入后，活跃工作才有机会单调减少。要区分连接还在、引擎已完成和客户端已收到结束三个状态。

按整组排空多 rank 副本，避免部分参与者先退出破坏所有剩余请求。缩容验收还应确认块、连接和计费状态最终得到清理。

## 源码入口

HTTP 接入看 `vllm/entrypoints/openai/`，引擎接口看 `vllm/v1/engine/`，协作组看 `vllm/distributed/`。Ray 相关生命周期与监控入口可从 `kuberay/ray-operator/` 和 `kuberay/config/prometheus/` 查起，核对实际部署启用了哪些组件再进入对应代码。
